# 食序管家跨版本产品行为约束

本文档记录已经由用户明确确认、后续迭代不得静默删除或弱化的产品行为。它不是某个
历史版本的功能清单，而是持续有效的兼容边界。

## 0.7.4.0 候选的明确授权修订

本节只适用于从 0.7.3.6 / 0.7.9 复制出的 0.7.4.0 / 0.8.0 连续变更批次。用户已
明确批准按核心账本简化设计直接实施；授权不得扩张为删除其他受保护能力。

- 日常运行所需规则必须进入工具 Schema、服务端校验器、确定性渲染器或主 Skill；普通
  用户请求不得读取 reference、源码、报告、数据库目录或 node_modules 来寻找调用方法。
- 默认工具名仍为七个。精简是否有效以精确动作清单和供应商归一化 Schema 字节共同判断，
  不得为了满足任意动作数量删除已确认的日常能力。
- “最终没吃/没喝”只在纠正尚未提交的事实、未来计划或假设时零调用；如果用户是在否定
  一条已经成功提交的记录，必须通过定位、修改、删除或撤销纠正账本。
- 营养未知继续不得写成零。日累计含未知记录时，已知小计必须标记为“至少”及 partial；
  没有可信数值时标记 unknown，不能显示为精确完成度。
- diet_meal update 改变数量、营养、库存或发生时间时必须先预览再确认；默认保留原
  occurred_at，只有用户明确纠正时间时才修改。提交必须原子反转旧营养/库存再应用新值。
- 当餐食或饮水成功改变日进度且目标已确认时，完整用户回执由插件从同一个最终提交快照
  确定性生成；宿主必须原样转发。纯库存、体重、目标、偏好、预览和失败不得伪造六项进度。
- 候选可以在同一个连续变更批次中持续编辑，但每个被安装测试的 RC 制品必须使用完整
  SHA-256 作为不可覆盖身份。正式发布仍必须同时递增产品和技术版本。
- 本批次优先不新增 migration。如果正确持久化必要状态确实需要 migration，必须停止并
  请求用户对最小增量 migration 的明确授权，不能退化为进程内临时状态。
- 0.7.3.6 原目录、约束文件和制品保持不可变；所有实现只发生在隔离候选和后续新版本目录。

## 变更门禁

- 每一个变更批次开始前，维护者必须完整阅读本文件；阅读必须发生在设计、审查、编辑、
  测试、打包或部署之前。不得以记忆、摘要、旧版本或他人转述代替。
- 重构、压缩提示词或追求“更简洁”都不能覆盖本文件中的行为。
- 删除、改序、缩减或改变语义前，必须先取得用户明确确认；不能仅因开发者或模型认为
  功能“不重要”而移除。
- 获得确认后，必须在同一次变更中更新本文件、运行时 Skill 规则、自动化测试和用户示例。
- `SKILL.md` 与 reference 冲突时不得自行选择较短版本；修复冲突并让测试覆盖唯一规则。
- 发布前必须运行保护这些约束的测试；测试失败时不得打包或上线。

## 用户指定保留功能的登记与修改授权

- 当用户明确表示某项功能、格式、流程或行为需要保留，维护者必须把该表达视为长期保护
  指令，不能只留在聊天记录、计划或记忆中。
- 必须在同一个变更批次、开始实现前，将该项按用户确认的语义登记到本文件的“受保护行为”
  中，并同步运行时规则、自动化测试和用户可见示例；不得以“以后再补文档”为由延期。
- 未经用户针对该受保护项作出的明确修改许可，不得删除、弱化、改序、缩减、替换或改变语义。
- “整体优化、重构、简化、提升体验”等一般性请求不构成修改授权，也不能从新版本开发、
  时间紧、实现困难或维护者认为“不重要”推定授权。
- 有效的修改许可必须明确点名受保护项、具体修改内容和允许范围；授权只适用于该范围，
  不得扩张、复用或解释为放弃其他保护。
- 如果用户表达可能影响受保护项但授权范围不清楚，保持该项原样并询问；不得先修改后确认。
- 用户明确授权修改后，必须在同一新版本中同步更新本文件、运行时规则、测试和示例，并在
  更新说明中记录新的受保护语义；旧版本仍保留原始约束作为历史证据。

## 强制版本迭代

- 版本目录一经创建即视为不可变。不得在原版本目录中追加修复后继续沿用原版本身份。
- 只要版本内容发生实质修改，无论是否已经上传、安装或发布，都必须创建新的产品版本目录。
- 实质修改包括文档、Skill、reference、规则、配置、源码、测试或构建脚本的新增、删除或
  内容变化；“只改提示词”“只改测试”“只改文档”“数据库没变”都不是免于迭代的理由。
- 必须创建新的产品版本目录，并从上一版本复制完整基线；上一版本目录和已生成制品保持
  原样，作为审计、比较和回退依据。
- 产品版本和技术版本必须同时递增，并同步更新包元数据、Python 版本、插件元数据、锁文件、
  当前发布文档、导入兼容列表、制品文件名和版本合同测试。
- 不得以相同版本号或相同制品文件名覆盖、替换或重新解释已经存在的版本内容。
- 一次连续实现中的多次编辑属于同一个变更批次，只需要形成一个新版本；该变更批次完成、
  通过验证或交付为候选后，后续新增需求或修复必须再创建下一版本。
- 仅清理未纳入版本内容的缓存、字节码、临时依赖链接或测试临时目录，不算产品修改；只要
  被发布或安装的文件字节发生变化，就必须迭代版本。

当前版本必须在 `tests/test_version_contract.py` 中声明前一产品版本和前一技术版本，并证明
当前两个版本均已递增。发布检查不得通过弱化或删除这项测试来规避版本迭代。

## 受保护行为

### 成功记录后的六项进度回执

当餐食或饮水写入成功且目标已确认时：

1. 回执只使用最终成功工具结果中的 `daily_progress`，不得复用上一轮总量或进度快照，
   也不得为了重建回执额外调用 `diet_report progress`。
2. 固定显示热量、蛋白、脂肪、碳水、纤维、饮水，顺序不得改变或缩减。
3. 每项固定两行；第一行仅含 Emoji、名称、10 格 `█`/`░` 进度条和真实百分比，第二行
   显示当前值、目标值以及本次真实增量。
4. 超目标时进度条封顶 10 格，但百分比不封顶；小于 1% 的正增量显示 `+<1%`，零增量
   省略，增量不得放进括号。
5. 纤维未知保持“未知”，不能当作 0；饮水使用“当前 ml / 目标 L”。
6. 成功写入回执不加 `📊 今日进度：` 等摘要标题，不压缩成单行指标，也不主动追加评价、
   警告、剩余额度或饮食建议。
7. `inventory_effects` 为空时不显示库存区块；不为空时只显示本次提交实际改变的库存。

规范入口是 `skills/personal-diet-pantry/references/water-and-progress.md`；保护测试是
`tests/test_skill_progressive_disclosure.py::test_post_commit_progress_receipt_preserves_the_legacy_renderer`。

### 泛化时间范围与查询完整性

- 时间表达必须先解释为通用范围描述，再由插件按用户时区解析；当前用户时区为
  `Asia/Shanghai`。不得把“昨晚”或任何单个示例写成特殊分支，也不得把示例词表当成
  封闭关键词白名单。新的等价说法、日历范围、滚动范围、跨日范围和用户明确给出的本地
  起止时间，必须复用同一套范围语义。
- 范围统一采用左闭右开区间；查询尚未结束的“今天、本周、本月”等当前周期时，结束点
  截止到当前时刻，不能误含未来记录。显式本地时间在夏令时规则下不存在或不唯一时，
  必须返回可解释错误，不能静默猜测。
- 数据库存储时间保持 UTC；餐食、饮水、体重的公开结果必须提供用户本地时间投影和时区
  名称。写入、读取、日报、餐次分类、跨日判断和临期计算不得各自采用不同时间基准。
- 按时间询问摄入时，范围内的正餐、加餐、营养饮料和补剂都属于候选结果，不能把自然
  语言中的“晚”“早餐”等字样直接缩减为单一餐次字段。返回结果必须携带已解析范围与
  完整性信息，使调用方可以判断查询是否覆盖了用户所问范围。

规范入口是 `skills/personal-diet-pantry/references/time-and-query-scopes.md`；保护测试覆盖
`tests/test_temporal_scopes.py`、`tests/test_local_time_projections.py` 与
`tests/test_skill_stabilization.py`。

### 模糊数量的估算、预览与确认

- 数量处理按事实充分度和估算不确定性推理，不能靠“一点、一些、几口、一把”等固定词
  决定唯一流程；这些表达只是测试样例，不是封闭关键词列表。
- 数量和单位明确且其他写入条件已满足时可以直接记录。数量模糊但存在足够的食物、容器、
  包装、历史份量或常见份量依据时，必须先展示可解释的估算并请求一次确认，在确认前保持
  零业务写入；不能擅自选择一个点值直接落库，也不能只因出现“一点”就放弃估算。
- 估算应保留范围、建议值、依据和会受影响的食材；同一消息有多个待确认项时，必须形成
  一次合并预览和一次整体确认，不能逐项追问、局部写入或制造多次库存变动。
- 如果现有事实不足以形成有意义的估算，最多询问一个最能缩小范围的缺失事实，并保持零
  写入。用户修改任何食物、数量、时间或库存事实后，旧预览失效，必须重新评估。
- 只有仍有效的确认句柄可以提交一次；确认不能覆盖目标歧义、库存不足、阻断状态或无效
  数据。否定、计划、假设和“最终没吃/没喝”的事实优先于数量估算，必须在估算前以零工具
  调用短路。

规范入口是 `skills/personal-diet-pantry/references/estimation-and-confirmation.md`；保护测试
覆盖 `tests/test_quantity_estimates.py`、`tests/test_skill_stabilization.py` 及相应 TypeScript
Schema 测试。

### 有界工具调用、失败熔断与证据边界

- 每种用户意图必须先形成有界调用计划：普通读或写通常只调用一次；需要定位目标、修正、
  撤销或预览时，只能在该路由明示的预算内增加调用。只有工具返回的续页游标或有效工作流
  句柄才能延长既定步骤。
- 成功、需要用户确认、业务拒绝或无法安全恢复的错误都是终止结果，得到后必须立即停止。
  不得原样重试相同错误指纹；连续两次不同失败后必须熔断并给出一个用户可执行的下一步。
- Diet 工具失败后，不得降级到 Exec、Shell、SQL、文件遍历或报告文件来猜测、补写或绕过
  失败，也不得向用户暴露内部命令、路径、调用次数、堆栈或原始诊断载荷。
- 偏好查询失败不能解释为“没有忌口”；库存包含、加工品与原料关系必须以工具返回的关系
  证据为准；库存变化只能根据成功提交返回的 `inventory_effects` 宣称。
- 过期与库存报告必须声明覆盖范围和完整性；报告缺失完整性证据时不能宣称“只有这些”，
  也不能把聚合报告当成完整库存的唯一事实来源。

规范入口是 `skills/personal-diet-pantry/references/tool-budget-and-recovery.md` 与
`skills/personal-diet-pantry/references/pantry-and-expiry.md`；保护测试覆盖
`tests/test_skill_stabilization.py`、失败轨迹、报告完整性和库存关系测试。

### 当前轮次的写入授权与删除安全

- 是否允许写入必须由宿主提供的当前用户消息与当前 `runId` 决定，不能只相信模型生成的
  工具参数。没有可信当前轮次、轮次已经结束/中止，或意图不能安全判定时，所有业务写入
  必须失败关闭；上一轮的确认、失败任务或待办不得在新一轮复活。
- 纯查询、状态核对、解释和查看类消息只能调用读操作。即使查询结果显示“尚未记录”，也
  不得自动补写；只有用户在当前消息中明确追加“没记就补记”等写入要求才产生写入授权。
- 一条消息同时要求两个或更多业务域写入时，在没有跨域原子事务以前必须在第一次写入前
  整体阻断，保持所有业务域零写入，并请用户拆分确认；不得采用“能写的先写、失败的再说”
  或在回复中用文字掩盖部分提交。餐食内部的做饭、扣库存和剩菜仍按既有单域原子事务执行。
- 单域明确写入只授权该域和该次意图需要的动作。像“我在上海”这样的资料事实，不构成
  修改用户资料、目标或偏好的权限；额外副作用必须另行说明并取得明确授权。
- “确认、就按这个记、撤销刚才”等省略式表达只能消费当前轮次可验证、未过期、未消费的
  工作流句柄；不得把裸确认转换为新的直接写入。句柄跨会话失效后，必须查询候选并再次确认。
- 当前轮次累计出现两次终止性工具失败后，后续 Diet 工具调用必须熔断；中间插入成功的
  只读调用不得重置计数。不得改变参数反复试探、扫描源码或切换到文件系统来寻找调用方式。
- 体重删除必须先返回包含精确体重与测量时间的零写入预览，再通过一次性确认句柄提交；
  提交时必须重新核对目标版本。错误、过期、已消费或不匹配的句柄不得删除任何体重记录。

规范入口是 `skills/personal-diet-pantry/SKILL.md`、
`skills/personal-diet-pantry/references/tool-budget-and-recovery.md` 与体重路由说明；保护测试覆盖
`src-tests/turn-guard.test.ts`、Meal 参数归一化测试及
`tests/contracts/test_body_weight_contracts.py`。

### 数据、库存和事务

- SQLite 是正式业务事实；不得直接改报告、导出或数据库文件来模拟业务操作。
- 外食、餐馆和外卖不扣家庭库存；只有本次提交返回的 `inventory_effects` 可以被宣称为
  库存变化。
- 已过期库存始终不得进入计划、菜谱或推荐候选；但用户明确报告已经食用、且同步宿主上下文
  已证明这是本轮已发生摄入时，必须如实记录餐食，并用精确库存选择在同一餐食事务中产生
  `consume` 变动。该授权不得由模型参数或 `source_text` 自行声明。不得拒绝事实、伪装成
  丢弃或损耗，也不得把这项追溯性例外扩张成未来食用许可。
- 做饭、食用与剩菜保存保持原子事务；熟食后续食用只扣熟食批次，不再次扣原料。
- 营养标签缺失值保持未知，不得为了让写入成功而强制猜测。
- 已承诺的撤销/重做、幂等和失败不冒充成功的语义不得移除。

### 公共入口、体重和隐私

- 七个公共工具入口保持为 `diet_meal`、`diet_water`、`diet_weight`、`diet_pantry`、
  `diet_transaction`、`diet_report`、`diet_system`；兼容动作不能无迁移直接删除。
- 裸数字不能直接当作体重写入；普通体重回执不暴露内部记录编号。
- 不向用户输出内部 ID、绝对路径、SQL、堆栈、原始错误载荷、密钥、令牌或控制面状态。

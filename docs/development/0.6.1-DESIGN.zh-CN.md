# v0.6.1 数据正确性设计摘要

## 目标

v0.6.1 将“记录成功”重新定义为四项同时成立：输入口径明确、计算可重放、正式写入幂等、用户可见副作用能由数据库事实证明。

## 核心不变量

1. 每个营养输入只有一个口径，口径与食用维度一一匹配。
2. `consumed_total` 永不按重量、体积或份数再次缩放。
3. 隐性水分不超过明确消费体积；按克食品的水分不超过其质量。
4. 同一个业务餐食事件最多产生一个活动餐食。
5. 只有已提交 `pantry_movements` 才能证明库存变化。
6. 餐食总量等于所有营养叶子餐项之和。
7. 字段完整性、计算有效性和来源可追溯性是三个独立状态。
8. 用户回复不暴露内部 ID、诊断细节或完整会话标识。

## 模块边界

- TypeScript schema 负责阻止缺少口径/维度的请求进入业务核。
- Python 营养归一化模块只接收明确口径并输出规范化整份值与证据。
- 餐食服务负责事务、幂等指纹、餐食/餐项写入和汇总。
- 库存服务以 movement 为唯一副作用事实。
- 进度与审计模块只读同一 SQLite 事实并分开展示质量状态。

## 数据演进

迁移 013 以增量方式加入事件时区、本地日期、餐食指纹、会话摘要、质量状态、消费体积/份数和 `meal_item_nutrition_evidence`。旧数据不被推断性重算；缺少证据时保持 `unverified`/`untraceable`。

## 失败策略

口径冲突、无效缩放和水分物理不可能属于写入前校验错误；整个事务不提交。数据库完整性错误继续触发写入熔断。历史异常由只读审计报告，不做静默修复。

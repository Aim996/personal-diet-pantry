# 食序管家用户指南

食序管家用自然语言帮你保存已经发生的饮食、饮水、体重和食品库存变化。SQLite 是唯一的正式事实来源；每日报告和 Markdown 文件都可以根据 SQLite 中的记录重新生成。下面的说明面向日常使用，不需要知道内部编号或数据库细节。

> 先决条件：在 OpenClaw 中安装、配置并完成自检后才能写入。图片中的营养标签或订单信息需要由**独立的图片识别 Skill**先提取；食序管家负责校验这些结构化信息并写入业务记录，不负责识别图片本身。

## 先看这张决策表

| 你说的话或意图 | 食序管家的处理 | 会不会写入 SQLite |
| --- | --- | --- |
| 询问、建议或计划，例如“晚饭吃什么”“可能晚上吃黄焖鸡” | 回答问题或帮你规划 | 不会 |
| 明确刚喝了白水，例如“刚喝了 300ml 水” | 只记录饮水 | 会，且只写饮水 |
| 明确当前体重，例如“体重 104.6kg，空腹” | 用系统时间记录体重和可选状态，并计算 7 日均值/趋势 | 会，且只写体重 |
| 明确已经吃了食物或营养饮料，例如“吃了两个玉米饼，喝了 330ml 豆浆” | 记录饮食；可安全匹配到家中库存时才扣库存 | 会 |
| 做饭、吃掉一部分并保存剩菜 | 用一笔原子事务处理原料、已吃部分和剩菜 | 会；任一环节不能成立就整笔不写 |
| 吃掉之前保存的熟食剩菜 | 定向找到熟食批次，复用做饭时保存的营养并只扣熟食库存 | 会；不会再次扣原材料 |
| 明确买了或入库，例如“买了 6 盒豆浆，每盒 330ml” | 一次入库 | 会 |
| 明确使用或丢弃某种库存，例如“扔了三盒豆花” | 定向找到商品后按包装数量跨批次扣减 | 会；库存不足时整笔不写 |
| 外食、外卖或餐厅饮食 | 记录饮食和其中的水分 | 会，但绝不扣家庭库存 |
| 短确认，例如“好，记录吧” | 仅在本次对话已有真实、未过期的待确认记录时继续 | 视该待确认记录而定；不会凭空新建 |

“打算吃”“可能吃”“没有吃”“别记录”等非发生表达优先于其他词：即使句子里出现水、豆浆或确认语，也不会写入。未收到正式成功结果前，系统不会说“已记录”。

## 怎样说最省事

把已经发生的事说清楚即可。时间、餐次、食物、数量、单位、是否外食、储存位置和包装信息越完整，结果越准确。

```text
早餐吃了 1 个鸡蛋和 250ml 牛奶。
刚喝了 300ml 水。
体重 104.6kg，空腹
买了 6 盒豆浆，每盒 330ml，放冷藏。
煎了 6 个蛋，吃 4 个，剩 2 个冷藏。
午饭在店里吃了一份牛肉面。
看看未来 3 天快到期的食材。
撤销刚才那次饮水记录。
```

清楚、已经发生的饮食通常直接记录，不会再追问“是否记录”。只有会实质影响结果的歧义才最多问一次，例如同名但不同的商品都可能被扣减、没有办法形成合理份量，或需你在多个对象中选一个。相同商品的多个物理批次不需要你选择，系统按库存策略处理。

### 计划不是记录

“可能晚上吃黄焖鸡”“帮我规划明天午饭”只会得到建议，既不增加营养，也不扣库存。等实际吃完后再告诉食序管家。这样可以避免计划被误当成事实。

### 白水与饮料要分开说

白水是独立饮水事件：`刚喝了 300ml 水`只记录饮水。豆浆、牛奶、茶、咖啡、汤、粥等是饮食或营养饮料：它们会作为饮食记录，食物本身的水分会合并到当天饮水进度，但不会再额外创建一条白水记录。因此“喝了 330ml 豆浆”不等于“喝了 330ml 白水”。

### 外食不会动家里的库存

餐厅、外卖和其他外部来源可以记录热量、营养和隐性水分，却不会减少冰箱或橱柜中的任何批次。若一顿家庭餐无法安全对应到某件库存，系统会优先保留饮食记录，必要时询问一次或不扣库存，而不会猜测商品。

### 体重只保留必要信息

直接说 `体重 104.6kg，空腹`、`记录体重 104.6` 或 `我 104.6kg，睡前` 即可。必须有明确体重措辞或清楚的体重单位；只有一个裸数字时不会写入，而会询问单位或用途。明确为体重且没写单位时默认千克。记录时间始终取系统当前时间，不需要也不能手动填写。

状态是可选自由文字，可以写“空腹”“睡前”“早餐后”，也可以不写。成功后显示本次体重、7 日均值，并在前一个 7 日窗口有数据时显示 `⬆️`、`⬇️` 或持平趋势。没有足够历史数据就省略对应行，不显示月均、BMI 或目标体重。

示例：

```text
已记录：105kg（空腹）
7日均值：105.0kg
趋势：⬇️ 0.5kg
```

## 份量、营养和保质期

### 何时会估算

已明确吃过、但没给数量时，系统会结合原话、容器、食物形态、当前包装大小、上下文和你已保存的习惯给出一个具体估算。例如“一口豆浆”按当时语境估算为一口，而不是擅自当成整杯；“两口蘑菇”也不会固定换算成某个克数。能够形成合理数值时会继续记录，并在食品名称后标出“（估算）”；实在无法形成合理数值才会问一次。

营养数据逐字段按以下顺序优先采用：剩菜营养快照 → 库存批次标签营养快照 → 有效的 `nutrition_cache` 本地缓存 → 内置 `rules/nutrition-foods.yaml` → 当前请求提供的 C/D 模型估算。高优先级来源已知的字段不会被低优先级覆盖，低优先级只补齐未知字段。没有标签并不等于不能记录；估算营养会如实标记，不展示内部等级或置信度。

液态或流动食物的隐性水分会计入当天饮水进度，但不是单独的饮水记录。纤维标签缺失表示“未知”，不是零。

### 包装、总量和单件均重

包装信息请尽量一次说完整：件数、每件数量和单位。例如“6 盒，每盒 330ml”会精确入库为 **1980ml**，同时保留“6盒”和“每盒330ml”，不会被凑整为 2000ml。对于“1 盒 435g”，系统会同时保存包装数量、基础总量和单包装规格。以后使用“两盒”时，由库存工具按已保存规格换算并更新剩余盒数；不会让模型临时手算。液体基础库存会保持 `ml`，包装展示仍可使用盒或瓶。

新入库批次会保存营养快照。若你提供的是图片识别出来的营养标签，请把识别结果连同包装数量和重量一并交给食序管家；标签会绑定到该库存批次，而不是塞进备注文字。

### 保质期与临期

每个新库存批次都需要具体有效期。来源优先级是：你明确给出的日期、包装或营养标签上的日期、结合食物状态、储存位置和当前时间作出的保守估算。你说“8月5日到期”时，系统保存本地日历日期并按当前时区解析当天结束，不会让模型自行拼接时区。信息不足时可以估算，不必为此再确认一次。

过期或已到期食品不会被自动当作吃掉、清空或丢弃；请明确说“丢掉”“冷冻”“解冻”等操作。查询库存或临期食品时，默认只显示紧凑结果；只有你明确需要营养、重量或备注时才会展开某一类食品的详情。

## 做饭、剩菜与再次食用

做饭时请把“做了多少”“吃了多少”“剩下多少、放在哪里”分开说。例如：`煎了 6 个蛋，吃 4 个，剩 2 个冷藏`。

- 原料：6 个生鸡蛋都会从库存扣除；
- 已吃：当天只记入 4 个煎蛋对应的营养；
- 剩菜：2 个煎蛋成为新的冷藏熟食批次，并带着这道菜的营养快照。

这三件事由一笔事务完成。原料不足、无法生成或校验有效营养数据且允许的一次营养估算重试也失败、有效期不合法等事务前校验失败时，整笔不提交且不会执行 `BEGIN`；进入事务后的异常才执行 `ROLLBACK`，撤销本次事务内变化。单纯缺少包装营养标签不会阻止提交，系统会按既定来源优先级尝试结构化估算。以后吃掉这份剩菜时，系统使用熟食引用复用当时的营养快照，只扣这份熟食批次，绝不会再次扣原来的生鸡蛋；撤销后也只恢复熟食批次。

“做了”“煎了”“炒了”“用了”只说明准备了食材，不自动代表吃过；没有明确食用时，系统会依上下文处理或问一个简短问题。

## 库存匹配、别名和纠正

家中餐食可自动匹配准确名称或唯一的库存简称。新鲜食材别名优先于子串匹配：`番茄`可以匹配库存中的`西红柿`，但不会误匹配`番茄罐头`，除非你明确说“罐头”。`蘑菇`在只有一种可用蘑菇时可匹配该品种；若香菇、口蘑等多种都合理，系统只会问你一次选哪一种。

如需更正，请直接说明“把刚才的豆浆改成 250ml”“删除午饭那条记录”或“撤销刚才那次饮水”。系统会定位可由人辨认的最近操作；你不必提供内部编号。撤销和重做只处理已找到的操作，不会猜测目标。恢复备份或批量删除属于高风险操作，必须明确指出目标和范围后才会执行。

## 今天进度与标准回执

进度和报告从 SQLite 的正式记录直接计算。每次成功饮食记录的普通回执只包含以下顺序：记录内容、六项进度、以及（仅发生库存变化时）库存变动。六项固定为**热量、蛋白、脂肪、碳水、纤维、饮水**，不夹带其他指标；库存区只列本次成功提交造成的变化，不展示完整库存或内部信息。

下面是格式示意，数值仅说明排版；实际数值以当次返回的 SQLite 结果为准。

```text
已记录！330ml 豆浆（估算）

🔥 热量 █████░░░░░ 50%
🔥1000 / 2000 kcal +120kcal +6%
🥩 蛋白 ██████░░░░ 60%
🥩48 / 80g +10g +13%
🧈 脂肪 ████░░░░░░ 40%
🧈20 / 50g +4g +8%
🌾 碳水 █████░░░░░ 50%
🌾125 / 250g +15g +6%
🥬 纤维 ███░░░░░░░ 30%
🥬9 / 30g
💧 饮水 █████░░░░░ 50%
💧1000ml / 2L +260ml +13%

📦 库存变动：
- 豆浆 -330ml，剩余 1650ml
```

如果当次没有库存变化，`📦 库存变动：`及其内容会完全省略。没有设置已确认目标时，也不会编造目标或画进度条，而会提示“目标尚未设置，暂不生成进度条”。查询、分析和历史报告不会假装有“本次新增”。

## 成功、失败与安全边界

食序管家只依据七类业务工具的正式结果确认写入，绝不直接修改 SQLite、报告或库存文件。若数据库完整性检查出现问题，会停止本次会话的所有写入，并提示你先修复再重新说出请求；不会把失败请求排队，也不会自动重放。

每个结果会区分“已正式写入、预览待确认、读取完成、状态本来就满足、失败”。一般参数问题只有在获得安全、可重试的字段指引时才修正；相同参数和相同确定性错误不会反复调用。如果仍不能写入，系统会说明本次未记录、库存未改变。数据库忙、句柄过期或结果不确定时仍会按新的状态证据检查，不会被失败缓存卡住。普通回复不会泄露内部编号、数据库路径、预览令牌、诊断细节或完整库存。

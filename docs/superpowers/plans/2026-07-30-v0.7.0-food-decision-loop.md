# 食序管家 v0.7.0 FoodDecisionModule Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 建立统一的 `FoodDecisionModule`，完成安全菜谱推荐、菜谱元数据和证据评分、`planned → purchased → stocked/cancelled` 购物闭环，以及按用户本地时区计算且可重建、可校验、可降级的可靠指标。

**Architecture:** `service.py` 仅负责输入适配、opaque handle 解析、调用 module 和公开响应过滤；`FoodDecisionModule` 通过 `answer(decision_query, profile_context)`、`transition(decision_handle, transition_command)`、`rebuild_metrics(scope, profile_context)` 三个接口收口菜谱、购物、库存安全、成本、浪费、趋势和指标口径。SQLite 正式业务表是事实源，`metric_snapshots` 只是带事实摘要的可删除加速层；快照不可用时报告直接查询正式事实。

**Tech Stack:** Python 3.11–3.13、SQLite、`Decimal`、IANA timezone/`tzdata`、pytest 8、TypeScript 5.9、TypeBox、Vitest、contract v2 生成器。

## Global Constraints

- 目标版本为 `0.7.0`，基线为 `0.6.7` / `f1a39d97edf657a3230c72dd8d9aa1e179a64857`。
- 必须在 Wave 1 / Migration 019 通过后开始本计划；`transactions` 已具有 `undo_policy` 和 `effect_count`。
- 七个顶层工具名保持不变；新增动作只加入现有 `diet_pantry`。
- v0.6.7 数据必须原地迁移；001–021 空库迁移和重复 migration 必须通过。
- 所有用户可见日、月、年标签与查询 UTC 边界必须使用同一个 profile timezone。
- 成本按 currency 分别守恒；禁止自动换汇或跨币种合计。
- `expires_at <= now` 的普通冷藏/常温批次不得进入可用库存或临期推荐。
- 在没有正式冻结延期证据时，frozen batch 保守排除；thawed batch 使用正式 thaw movement 与 expiry 判断。
- 菜谱评分只能引用 SQLite 正式事实；缺失维度必须返回 `unknown`，不能自动给满分。
- shopping item 状态只允许 `planned/purchased/stocked/cancelled`。
- purchased 不等价于家庭库存；只有 stocked 创建或链接 pantry batch。
- `stock_shopping_item` 的 item、batch、movement、link、事务和 receipt 必须在同一 SQLite 事务中提交。
- metric snapshot 必须可删除、可全量重建、可校验；损坏时降级为直接查询且不阻断业务写入。
- 所有比例指标在分母为 0 时返回 `not_available`，不能返回 `0%`。
- v0.7.0 不展示无法由正式 stockout fact 证明的缺货频率。
- 不全面重写 `service.py`，不改写稳定的餐食、饮水、体重和库存核心。
- 所有新错误必须经过公开响应过滤，不能泄露 SQL、表名、绝对路径、stack trace、内部快照或凭据。
- 对外 `DecisionQuery` 与 `MetricScope` 只接收本地 `start_date/end_date`；
  timezone 只来自 `ProfileContext`，UTC 半开区间只在 module 内派生。
- 对外 shopping transition command 只含领域输入；operation id、handle 消费、
  receipt 持久化和 `MutationContext` 只能存在于 module 私有 commit adapter。
- waste avoidability 只允许 `avoidable/unavoidable/unknown`，缺省固定为
  `unknown`；unpriced event 只进入 metric 级 coverage，不能归属任一 currency。
- row identity 必须由 `row_identity.py` 的单一、显式、fail-closed 注册表定义；
  journal allowlist 与所有 portability v1/v2 表的并集必须逐表登记，未知表不得
  fallback 为 `id`。journal insert/update、snapshot replay、portable export/import
  不得各自假设主键列恒为 `id`。
- `pantry_movements.id` 从 Migration 021 起由同事务 high-water allocator 分配，
  已提交过的 ID 在 undo、删除、隐私清理或失败重试后都不得回收。
- 所有新 identity 只能经
  `reserve_identity(connection, table, count=..., linked_identities=...)`
  分配；该 API 只允许在调用者已经取得 `BEGIN IMMEDIATE` 的同一事务内使用，
  `MutationContext` 与 portability importer 不得复制 allocator SQL。
- v0.7.0 portability export 固定使用 export schema v2；import 必须继续接受规范的
  v0.6.7 schema v1 bundle。portable payload 不保存 raw SQLite PK 或原始
  `transaction_id`，关系只能通过 external handle 重建。
- FD Task 1 是 `migrations/020_recipe_shopping_lifecycle.sql` 的唯一 schema
  owner，并一次创建 recipe、shopping、`meals.consumption_location`、
  `meal_items.inventory_provenance` 与 `cooking_preparation_losses` 最终 schema；
  SkillBehavior SB4 只消费 Migration 020，不再修改该文件。
- contract v2 生成器必须先由 SkillBehavior 计划完成；本计划按其稳定字段登记三个
  shopping item action。`src/schemas.ts` 仍串行：FoodDecision 先加入
  recipe/shopping schema，SkillBehavior SB4 后加入 cooking/provenance schema，
  两者不得并行编辑。

FD1 在同一个 020 文件中一次创建最终 meal/cooking schema；以下 SQL 与 SB4
已确认的 schema contract 逐字一致：

```sql
ALTER TABLE meals
    ADD COLUMN consumption_location TEXT;

ALTER TABLE meal_items
    ADD COLUMN inventory_provenance TEXT NOT NULL DEFAULT 'unknown'
    CHECK (
        inventory_provenance IN ('home_pantry', 'external', 'unknown')
    );

CREATE TABLE cooking_preparation_losses (
    id INTEGER PRIMARY KEY,
    meal_id INTEGER NOT NULL
        REFERENCES meals(id) ON DELETE CASCADE,
    normalized_name TEXT NOT NULL,
    quantity TEXT NOT NULL
        CHECK (
            quantity <> ''
            AND quantity NOT GLOB '*[^0-9.]*'
            AND quantity NOT GLOB '*.*.*'
            AND CAST(quantity AS NUMERIC) > 0
        ),
    unit TEXT NOT NULL,
    created_at TEXT NOT NULL,
    transaction_id TEXT NOT NULL
        REFERENCES transactions(id) ON DELETE RESTRICT,
    UNIQUE (meal_id, normalized_name, unit)
);

CREATE INDEX idx_cooking_preparation_losses_meal
    ON cooking_preparation_losses(meal_id);
```

`cooking_preparation_losses` 是可撤销的正式事实，不是派生摘要。把它加入
`transactions._MUTABLE_TABLES`，所有业务写入只允许通过 `MutationContext.insert()`
完成，由 context 自动补写 `transaction_id`。迁移测试中的正向插入也必须先创建
一笔 committed 测试 transaction 并显式引用它；零数量、重复事实和不存在
transaction 的插入分别保持失败。新增

```python
def _upgrade_snapshot_row(
    table: str,
    row: dict[str, Any] | None,
) -> dict[str, Any] | None:
    if row is None or table != "shopping_list_items":
        return row
    lifecycle_fields = {
        "purchased_at",
        "stocked_at",
        "cancelled_at",
        "purchased_transaction_id",
        "stocked_transaction_id",
        "cancelled_transaction_id",
    }
    status = str(row.get("status"))
    if status != "pending" and lifecycle_fields <= row.keys():
        return row
    upgraded_status = "planned" if status == "pending" else status
    updated_at = row.get("updated_at")
    transaction_id = row.get("transaction_id")
    return row | {
        "status": upgraded_status,
        "purchased_at": updated_at if status == "purchased" else None,
        "stocked_at": None,
        "cancelled_at": updated_at if status == "cancelled" else None,
        "purchased_transaction_id": (
            transaction_id if status == "purchased" else None
        ),
        "stocked_transaction_id": None,
        "cancelled_transaction_id": (
            transaction_id if status == "cancelled" else None
        ),
    }
```

两个具体函数签名固定为：

- `mark_item_purchased(connection: sqlite3.Connection, manager:
  TransactionManager, *, item_id: int, expected_version: int, source_text:
  str, purchased_at: datetime, internal_id: str, after_update:
  Callable[[MutationContext, ShoppingListItem], None] | None = None) ->
  ShoppingListItem`
- `cancel_item(connection: sqlite3.Connection, manager: TransactionManager,
  *, item_id: int, expected_version: int, source_text: str, cancelled_at:
  datetime, internal_id: str, after_update: Callable[[MutationContext,
  ShoppingListItem], None] | None = None) -> ShoppingListItem`

合法跳转严格为：

```text
planned -> purchased
planned -> cancelled
purchased -> cancelled
```

两者都用 `manager.execute("reminder_manage", normalized_source, mutate,
internal_id=internal_id)`。`mutate` 先以 `item_id` 读取 item，比较
`expected_version`，再执行 `context.update`：

- purchase 写 `status="purchased"`、`purchased_at=timestamp`、
  `purchased_transaction_id=internal_id`、`updated_at=timestamp`、
  `version=expected_version + 1`；
- cancel 写 `status="cancelled"`、`cancelled_at=timestamp`、
  `cancelled_transaction_id=internal_id`、`updated_at=timestamp`、
  `version=expected_version + 1`，并保留已有 purchase 字段。

update 后从 row 构造 `ShoppingListItem`，再调用可选 `after_update`。当一个 list
不再有 planned/purchased item 时，以 `context.update` 将 list 标为
`completed`、更新时间并递增 version；显式 `cancel_shopping_list` 仍标为
`cancelled`。现有 `cancel_list()` 将 `status='pending'` 查询改成
`status IN ('planned','purchased')`，并为每个被取消 item 写
`cancelled_at/cancelled_transaction_id`。

`FoodDecisionModule.transition()` 从
`self._transition_commit.operation_id` 取得两个 helper 的 `internal_id`，并把
一个 module 私有 callback 传入 `after_update`；callback 构造
`DecisionReceipt` 后只调用 `self._transition_commit.commit(context, receipt)`。
该 callback 不得进入 command dataclass 或 handler payload。service adapter
先以原子条件消费 handle，再保存 canonical public receipt；消费失败时抛冲突并让
整笔 domain mutation rollback。

该表不是用户业务事实，不进入 transaction snapshot、portable export 或

```sql
UPDATE pantry_movement_id_sequence

RETURNING next_id - 1;
```

返回值显式写入 `pantry_movements.id`。业务 transaction rollback 会连同 reservation
一起 rollback；但后续 undo 只删除 movement row，不改 sequence，所以已提交 ID
永不回收。redo 按 snapshot 恢复旧 ID，也不得递减或重置 sequence。portable import

```python
from __future__ import annotations

from dataclasses import dataclass
import sqlite3
from typing import Literal


class UnknownRowIdentityError(ValueError):
    """Raised when a journal/portable table has no explicit identity contract."""


@dataclass(frozen=True)
class RowIdentitySpec:
    column: str
    allocation: Literal["sqlite", "monotonic", "linked", "fixed"]
    linked_table: str | None = None
    linked_output_name: str | None = None
    sequence_table: str | None = None
    sequence_column: str | None = None
    fixed_value: int | None = None


_SQLITE_ID_TABLES = frozenset({
    "meals",
    "meal_items",
    "meal_item_nutrition_evidence",
    "water_logs",
    "body_weight_logs",
    "pantry_batches",
    "pantry_cost_allocations",
    "nutrition_cache",
    "nutrition_profiles",
    "pantry_nutrition_links",
    "prepared_food_profiles",
    "personal_rules",
    "learning_events",
    "pending_inventory_links",
    "recipe_profiles",
    "shopping_lists",
    "shopping_list_items",
    "cooking_preparation_losses",
    "shopping_item_links",
})
_ROW_IDENTITIES: dict[str, RowIdentitySpec] = {
    **{
        table: RowIdentitySpec("id", "sqlite")
        for table in _SQLITE_ID_TABLES
    },
    "pantry_movements": RowIdentitySpec(
        "id",
        "monotonic",
        sequence_table="pantry_movement_id_sequence",
        sequence_column="next_id",
    ),
    "waste_classifications": RowIdentitySpec(
        "pantry_movement_id",
        "linked",
        linked_table="pantry_movements",
        linked_output_name="pantry_movement_handle",
    ),
    "nutrition_goal_profiles": RowIdentitySpec(
        "id",
        "fixed",
        fixed_value=1,
    ),
}


def identity_spec(table: str) -> RowIdentitySpec:
    try:
        return _ROW_IDENTITIES[table]
    except KeyError as error:
        raise UnknownRowIdentityError(
            f"Table {table!r} has no registered row identity"
        ) from error


def registered_identity_tables() -> frozenset[str]:
    return frozenset(_ROW_IDENTITIES)


def reserve_identity(
    connection: sqlite3.Connection,
    table: str,
    *,
    count: int = 1,
    linked_identities: tuple[int, ...] = (),
) -> tuple[int, ...]:
    """Reserve exact identities inside the caller's BEGIN IMMEDIATE."""

    if not connection.in_transaction:
        raise RuntimeError("Identity reservation requires an active write transaction")
    if count < 0:
        raise ValueError("Identity reservation count must be non-negative")
    spec = identity_spec(table)
    if count == 0:
        if linked_identities:
            raise ValueError("Zero-count reservation cannot carry identities")
        return ()
    if spec.allocation == "linked":
        if len(linked_identities) != count:
            raise ValueError("Linked identities must be supplied exactly")
        return linked_identities
    if linked_identities:
        raise ValueError("Linked identities are valid only for linked allocation")
    if spec.allocation == "fixed":
        if count != 1 or spec.fixed_value is None:
            raise ValueError("Fixed identity permits exactly one row")
        return (spec.fixed_value,)
    if spec.allocation == "sqlite":
        maximum = connection.execute(
            f"SELECT COALESCE(MAX({spec.column}), 0) FROM {table}"
        ).fetchone()[0]
        start = int(maximum) + 1
        return tuple(range(start, start + count))
    if spec.sequence_table is None or spec.sequence_column is None:
        raise RuntimeError("Monotonic identity has no sequence contract")
    next_after = connection.execute(
        f"""
        UPDATE {spec.sequence_table}
        SET {spec.sequence_column} = {spec.sequence_column} + ?
        WHERE singleton = 1
        RETURNING {spec.sequence_column}
        """,
        (count,),
    ).fetchone()
    if next_after is None:
        raise RuntimeError("Monotonic identity sequence is unavailable")
    start = int(next_after[0]) - count
    return tuple(range(start, start + count))
```

`count=0` 是统一的合法空表契约：调用仍须位于 caller 的
`BEGIN IMMEDIATE` 内，仍先经过 `identity_spec(table)`，所以未知表不会借零行绕过
registry；但在 registry lookup 后立即返回 `()`，不得查询 `MAX(id)`、读取或更新
sequence、解析 fixed/linked allocator，也不得携带非空 `linked_identities`。
`count<0` 才是参数错误。

```python
def _upgrade_snapshot_changes(
    connection: sqlite3.Connection,
    changes: list[_RowChange],
) -> list[_RowChange]:
    classification_table_exists = connection.execute(
        """
        SELECT 1
        FROM sqlite_master
        WHERE type = 'table' AND name = 'waste_classifications'
        """
    ).fetchone()
    if classification_table_exists is None:
        return changes

    captured_movement_ids = {
        int(change.after["pantry_movement_id"])
        for change in changes
        if change.table == "waste_classifications"
        and change.after is not None
    }
    synthetic: list[_RowChange] = []
    for change in changes:
        movement = change.after
        if (
            change.table != "pantry_movements"
            or change.before is not None
            or movement is None
            or movement.get("movement_type") not in {"discard", "expire"}
        ):
            continue
        movement_id = int(movement["id"])
        if movement_id in captured_movement_ids:
            continue
        synthetic.append(
            _RowChange(
                table="waste_classifications",
                row_id=movement_id,
                before=None,
                after={
                    "pantry_movement_id": movement_id,
                    "category": (
                        movement.get("waste_category") or "unspecified"
                    ),
                    "avoidability": "unknown",
                    "classified_at": movement["created_at"],
                    "transaction_id": movement["transaction_id"],
                },
            )
        )
    return [*changes, *synthetic]
```

- [ ] **Step 4: 实现六项精确口径**

1. `waste_rate`：
   - `by_currency` 只使用有正式 `pantry_cost_allocations` 的事实，逐 currency
     计算 `waste_minor / (consume_minor + waste_minor)`；
   - `pricing_coverage` 在整个 local-date scope 只计算一次，不应用可选 currency
     filter；eligible event 只包括 scope 内 discard/expire movement，
     `priced_event_count` 为存在 `allocation_kind='waste'` allocation 的 distinct
     movement 数，`unpriced_event_count` 为不存在该 allocation 的 distinct
     movement 数；
   - coverage 比率为 `priced / (priced + unpriced)`；没有 eligible event 时返回
     `not_available/no_observations` 且两个 count 都为 0；
   - currency leaf 不得包含两个 count，unpriced event 不进入任何 currency 的
     分子、分母或 event count。
2. `purchase_frequency`：窗口内 `purchased_at` 落入 scope 的 item，以
   `purchased_transaction_id` join `transactions.id`，只计
   `transactions.status='committed' AND effect_count>0` 的 distinct
   purchase transaction；没有 purchase 时 count 0 合法。不得使用会被 stock 或
   cancel 更新的 `shopping_list_items.transaction_id`。
3. `expiry_handling_rate`：
   - denominator 是 `expires_at - expiry_window_days` 落入 scope 且 batch 在该时刻已入库的 distinct batch。
   - numerator 是临期起点之后且 `expires_at` 之前有 consume/freeze/discard movement 的 denominator batch。
4. `inventory_turnover`：按 currency，窗口 consume cost / 每个 profile-local day 闭市库存成本的算术平均。每日库存成本由该日结束前已入库 price，减去该日结束前 cost allocations 重建；平均库存 0 为 `not_available`。
5. `usage_volatility`：按 `(normalized_name, unit)` 分组，将 scope 内每个本地日的 consume quantity（无消费日补 0）计算总体方差 `sum((x-mean)^2)/N`；无 consume facts 为 `not_available/no_observations`。
6. `nutrition_coverage`：
   - goal profile 未 confirmed 时，整个指标返回
     `not_available/unconfirmed_goals`；
   - confirmed 时 denominator 是 scope 内未删除 meal 数；
   - numerator 是所有 meal items 均有
     `inventory_provenance IN ('home_pantry','external')`，且 meal
     同时满足 `nutrition_calculation_status='verified'` 与
     `nutrition_provenance_status='traceable'` 的 meal 数；
   - denominator 为 0 时返回 `not_available/zero_denominator`；
   - 目标覆盖趋势逐 profile-local day 生成。

每个 UTC timestamp 在形成 day/month bucket 前必须调用
`local_datetime(timestamp, resolved_scope.timezone_name)`。
cost/waste/remaining 继续按 currency 分组，绝不生成 combined total。

返回 mapping 必须始终含六个 metric key。没有任何 currency fact 时，
`waste_rate["by_currency"]` 与 `inventory_turnover` 各返回 `""` currency 的
`not_available/no_observations` sentinel；没有 consume fact 时
`usage_volatility` 返回 `""` dimension 的
`not_available/no_observations` sentinel。sentinel 只用于稳定序列化，不展示为空
币种合计。

- [ ] **Step 4: 实现全量 rebuild 和逐行验证**

`rebuild_snapshots()`：

1. `BEGIN IMMEDIATE`。
2. 查询并 canonicalize source facts。
3. 调用 `compute_metrics()` 并生成 canonical metric rows。
4. 用 facts + metric rows 计算一次 combined `source_digest`。
5. 删除完全相同 scope + definition version 的旧 rows。
6. 每个 metric/dimension/currency 写一行 canonical `value_json`；Task 7 的空
   currency/dimension sentinel 也写入，因此每个 scope 至少有六个 metric name。
   `pricing_coverage` 使用上面固定的独立 row identity。
7. 重新 SELECT，验证 raw `value_json` 已 canonicalize、唯一键、definition
   version，并从 read-back values + source facts 重算 combined digest。
8. `inserted_count != verified_count` 或 digest 不等时 rollback 并抛
   `MetricSnapshotValidationError`。
9. 成功 commit 并返回 `MetricRebuildReport`。

快照写入不通过 `TransactionManager`，因为它是可删除派生数据；不得创建 undo candidate。

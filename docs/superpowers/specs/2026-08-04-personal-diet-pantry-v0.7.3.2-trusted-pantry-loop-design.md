# 食序管家 v0.7.3.2 可信库存饮食闭环设计

日期：2026-08-04
产品版本：`0.7.3.2`
技术包版本：`0.7.5`
基线：产品版本 `0.7.3.1` / 技术包版本 `0.7.4`

## 1. 背景与结论

v0.7.3.1 已修复模型侧液体餐食 Schema 膨胀和缺省记录时间，但真实 OpenClaw 会话仍不能稳定完成“搜索盒装饮品 → 按盒食用 → 自动复用包装营养 → 同一事务扣库存和记餐”的高频流程。

本版本采用兼容式原位修复：保留现有七个公开工具、action 名称和 21 个数据库迁移，复用现有包装字段、营养快照、工作流 JSON 和可空营养列。重点修复包装信息在搜索句柄中的丢失、展示单位被拒绝、缺失营养被强制补猜、包装入库参数重复，以及餐食修正时间漂移。

## 2. 证据范围

本设计合并以下四类证据：

- `v0.7.3.1-LIVE-UAT-2026-08-03.zh-CN.md`
- `v0.7.3.1-DEEP-UAT-2026-08-03.zh-CN.md`
- `OpenClaw-饮食管家-Skill-综合测试报告.html` 及其 `artifact.json`
- v0.7.3.1 源码、自动测试、发布清单和可安装包审查

综合报告中的 29 个案例统计为 16 个通过、7 个部分通过、6 个失败；三项数字合计 29。报告方向与源码和两份 UAT 基本一致，但包装与营养问题的归因需要按本设计修正：

1. 包装字段已经持久化；缺陷位于搜索候选投影和句柄没有传播这些字段。
2. `nutrition_mode=none` 时返回 `nutrition_available=null`、`nutrition_status=not_requested` 属于现有设计，不能单独证明营养链接失败。真正的问题是句柄不绑定营养快照、编排默认不请求营养，以及运行时强制补齐完整估算。

## 3. 目标与非目标

### 3.1 本版本目标

- 搜索结果在包装事实一致时返回现有规范包装字段。
- 搜索句柄绑定产品身份、包装投影、营养投影和库存资源版本。
- `diet_meal record` 接受“1 盒 + inventory_match_handle”，由服务端确定性换算为基础量。
- 一次餐食提交原子完成 FEFO 扣库存、餐食写入、已知营养缩放和水分贡献。
- 包装标签缺失的营养字段保持未知，不要求模型补造完整 C/D 估算。
- 包装入库允许从规范包装字段和显式基础单位推导基础数量。
- 餐食修正保持原 `occurred_at`，并在一个现有事务中完成旧库存恢复和新库存扣减。
- 建立真实工具轨迹回归，区分静态 Skill lint 与行为验证。
- 保持撤销、幂等、FEFO、多批次和 v0.7.3.1 液体 Schema 修复不回退。

### 3.2 本版本非目标

- 不新增第八个公开工具或新的公开 action。
- 不建立全局商品主档，不新增数据库迁移。
- 不自动合并或删除疑似重复餐食。
- 不在本版本解决体重因果分析、临时人物档案与私人记忆隔离。
- 不把整体延迟降到某个未经基准验证的固定秒数；本版本只记录延迟和工具调用数。
- 不自动安装到当前正在使用的 OpenClaw 实例，不修改真实用户数据库。

## 5. 兼容式架构

### 5.1 包装候选投影

新增内部包装投影函数，对搜索命中的所有可用批次进行分类：

- `uniform`：所有相关批次都有相同 `display_unit`、`base_quantity_per_display_unit` 和兼容的 `package_hierarchy`。
- `partial`：只有部分批次存在包装事实。
- `mixed`：批次之间的展示单位或换算因子不一致。
- `none`：没有可验证包装事实。

仅在 `uniform` 时公开确定的包装换算字段，并按总基础余量计算 `remaining_display_quantity`。`partial`、`mixed`、`none` 不根据常识猜盒数、瓶数或单件规格。

### 5.2 选择句柄快照

`pantry_product_reference` 的 `result_json` 保存：

```json
{
  "normalized_name": "小象无糖豆浆",
  "base_unit": "ml",
  "package": {
    "status": "uniform",
    "display_unit": "盒",
    "base_quantity_per_display_unit": "250",
    "package_hierarchy": []
  },
  "nutrition": {
    "status": "uniform",
    "serving_basis": "per_100ml",
    "source_grade": "A",
    "snapshot": {
      "calories_kcal": "32",
      "protein_g": "3",
      "fat_g": "1.6",
      "carbohydrate_g": "1.2",
      "fiber_g": null,
      "sodium_mg": null
    }
  }
}
```

`resource_versions_json` 保存候选中参与投影的批次 ID 和版本。句柄继续使用现有过期机制，不包含用户可编辑业务数据。新句柄字符集限定为 `[a-z0-9_-]`。

公开的 `nutrition_mode` 只控制搜索响应是否展示营养，不控制句柄内部是否保存当时可验证的营养快照。

### 5.3 从展示单位到基础单位

当餐食项目同时提供 `inventory_match_handle`、`amount` 和 `unit` 时：

1. 校验名称与句柄产品身份一致。
2. 若 `unit` 是基础单位，直接使用。
3. 若 `unit` 等于句柄中的 `display_unit` 且包装状态为 `uniform`，计算 `base_amount = amount × base_quantity_per_display_unit`。
4. 用基础量写入 `consumed_weight_g`、`consumed_volume_ml` 或 `consumed_servings`。
5. 餐食持久化使用基础量和基础单位，`raw_name` 与 `portion_expression` 保留用户的“1盒”表达。
6. 若包装事实不完整或混合，返回字段级 `INVALID_INPUT`，要求用户提供基础量或重新选择，不进行常识换算。

模型不再需要传 `nutrition_facts`、`nutrition_basis`、`consumed_volume_ml` 或完整估算来使用已选择的盒装库存。

### 5.4 营养的部分已知语义

现有 `NutritionResult` 和数据库营养列已经允许 `null`，无需新迁移。实现调整为：

- 解析包装标签时只缩放标签实际提供的字段。
- 不用低等级估算填补高等级标签缺失字段。
- 单项与总计按字段传播未知：参与合计的任一项未知时，该总计字段为 `null`。
- `nutrition_status` 根据六个核心字段为 `complete`、`partial` 或 `incomplete`。
- 已知字段计算正确时 `nutrition_calculation_status=valid`；来源不完整时 `nutrition_provenance_status=partial` 或 `untraceable`。
- 部分营养证据以现有 JSON 证据列保存，不强制构造全字段 `NutritionFacts`。
- 缺失水分时保持 `null`；已知水分仍必须满足 `0 <= hydration_ml <= consumed_volume_ml`。

### 5.5 原子餐食与撤销

服务端完成句柄解析和单位换算后，继续进入现有 meal preview/commit 事务。事务必须共同处理：

- 餐食及餐食项写入；
- 营养与营养证据写入；
- FEFO 多批次库存扣减；
- 饮水贡献；
- 操作日志和撤销信息。

任何环节失败均不得留下单独库存变动。一次公开撤销恢复餐食、营养、水分和所有受影响库存批次。

### 5.6 包装入库规范化

TypeScript 边界按以下顺序处理 `add/preview_add`：

1. 校验规范包装三元组是否完整。
2. 校验现有 `unit` 为明确基础单位；单靠数值不能猜测 `g` 或 `ml`。
3. 若三元组完整，计算精确基础数量；`quantity` 缺省时填入计算结果。
4. 若显式基础量与计算值矛盾，返回 `INVALID_INPUT`，指出冲突字段。
5. 通过后再补 `added_at` 和 `source_text`。

旧 `package_count/quantity_per_package/package_unit` 仅作为兼容输入转换为规范字段，不作为新输出或持久化模型。

### 5.7 餐食修正

现有 `update_meal/update_cooking` 已使用单个 `TransactionManager` 恢复旧库存并写入新记录，本版本不增加新 action。服务层在构造 update draft 前读取原记录：

- 未显式提供 `occurred_at` 时继承原值；
- 显式提供时保留用户修正后的时间；
- `updated_at` 使用修正提交时间；
- 修正失败时旧餐食和库存状态不变。

## 6. 错误契约

| 场景 | 错误 |
|---|---|
| 句柄过期或绑定的批次版本改变 | `STALE_PREVIEW` |
| 展示单位与句柄包装单位不同 | `INVALID_INPUT`, `field=items[n].unit`, `reason=incompatible` |
| 包装状态为 partial/mixed，不能确定性换算 | `INVALID_INPUT`, 要求基础单位或重新搜索 |
| 显式基础数量与包装乘积矛盾 | `INVALID_INPUT`, 指向 `quantity` 或 `unit` |
| 库存不足 | `INSUFFICIENT_STOCK`，整个餐食事务回滚 |
| 标签营养字段缺失 | 不报错；字段保持 `null` 并返回数据质量状态 |

错误响应不得要求“完整 C 或 D 估算”，也不得在用户可见文本中输出内部补字段重试过程。

## 7. 测试设计

### 7.1 核心端到端回归

使用隔离数据库：

1. 入库两盒豆浆，每盒 250ml，只提供不完整 A 级包装标签。
2. 入库调用提供 `unit=ml`、省略基础 `quantity`，由包装三元组推导 500ml。
3. 搜索豆浆并断言公开包装双单位正确。
4. 断言句柄内部绑定包装、营养和批次版本，但 `nutrition_mode=none` 的公开响应不泄露完整标签。
5. 仅以 `amount=1`、`unit=盒`、`inventory_match_handle` 记录餐食。
6. 断言只产生一条餐食，剩余库存为 1盒/250ml。
7. 断言已知营养按 2.5 倍缩放，缺失纤维和钠仍为 `null`，没有 C/D 估算。
8. 断言水分为空或位于 0–250ml，不得超过饮用体积。
9. 一次撤销恢复两盒/500ml，并移除对应餐食、营养和水分贡献。

### 7.2 契约回归

- 包装一致、部分、混合、缺失四种搜索投影。
- 旧句柄在库存版本变化后失效。
- 新句柄只包含小写安全字符。
- 基础单位输入和展示单位输入得到相同扣减结果。
- 包装三元组推导基础量；矛盾基础量被拒绝。
- `storage_location` 从 TypeScript Schema 一直传到 Python 查询。
- 修正 2 个为 3 个时保持原 `occurred_at`，库存净变化正确，修正事务可撤销。
- 部分营养、完全未知营养和完整营养均可记录，状态和值符合定义。
- v0.7.3.1 的液体 Schema、显式时间、FEFO、幂等和多批次撤销测试继续通过。

### 7.3 行为轨迹回归

静态 Skill 检查脚本命名为 lint，只检查文件结构、路由文字和示例完整性。行为轨迹用例至少保存并校验：

- 用户输入；
- OpenClaw 会话和模型标识；
- 每次工具名称、参数、结果和顺序；
- 最终用户可见回复；
- 总工具调用数、重试数和耗时；
- 测试前后数据库差异；
- 清理或撤销结果。

首个必测自然语言案例为“剩下那盒我喝了”。成功标准是搜索后一次正常 `diet_meal record` 完成，最终只有一条业务回复，无补字段重试，无手工伪造 250ml 或完整营养表。

# 食序管家 v0.7.1 Skill 可信记录设计

日期：2026-08-01

目标版本：`0.7.1`

基线版本：`0.7.0`

项目定位：食序管家首先是一套可复制、可安装、可迁移的个人饮食与库存 Skill。随附插件和 Python 服务用于执行、校验和测试 Skill 的业务承诺，不是独立产品中心。

用户确认：采用“Skill 优先 + 最小必要工具保护”，不做 OpenClaw、Telegram、Docker 或软路由专属开发。

## 1. 背景

v0.7.0 已解决营养基准重复缩放、基本幂等、做饭数量守恒、体重记录和自然口语路由等问题。新的真实会话暴露出另一类风险：用户事实尚未完整时，模型会提前补全商品、重量、用油或加工损耗并写库；后续补充说明又可能被误当成确认，造成返工和数据可信度下降。

这批问题不能只靠增加更多营养公式解决。v0.7.1 的重点是让 Skill 对“什么时候可以写、什么时候必须先问、补充说明如何进入修正流程”给出可复用的决策合同，并用真实中文口语评测保护这些行为。同时，在不减少事实校验、不降低结果可信度的前提下，消除重复 reference 读取、无效预查询、重复查询和可合并的工具调用，并让稳定提示前缀更利于 DeepSeek 上下文缓存。

## 2. 方案比较与选择

### 方案 A：只修改 Skill 文案

优点是改动最小、复制最方便。缺点是已有工具若存在事务残留或无法表达关键事实，仅靠提示词无法保证数据库正确。

### 方案 B：Skill 优先 + 最小必要工具保护（采用）

Skill 文档和行为评测定义产品行为；工具层只补足无法由语言规则保证的数据不变量，例如做饭修正时撤销旧剩菜、结构化保存加工损耗、返回确定的派生数值。该方案保持可复制性，同时避免把数据正确性完全押在模型服从度上。

### 方案 C：以后端状态机和事件溯源为中心

可以提供最强的强制约束，但会把个人 Skill 扩张为复杂应用平台，增加迁移、维护和部署成本，不符合本项目定位。

## 3. 可复制 Skill 的边界

一个合格的 v0.7.1 包必须满足：

- 新会话无需依赖旧聊天记忆即可根据 `SKILL.md` 命中七个领域工具。
- 同一套规则可用于 OpenClaw WebUI、Telegram 或其他正常工具会话。
- Skill 中不存在机器路径、IP、令牌、用户 ID、容器名或某次会话句柄。
- 自然语言决策由 Skill 和 references 描述；确定性数据不变量由随附工具实现。
- 用户复制完整 Skill 包后，行为评测、Schema 校验和核心回归可以本地重复执行。
- 不依赖特定前端如何展示工具活动；前端重复渲染不属于 Skill 包可直接修复的范围。

## 4. 写入准备度合同

Skill 在任何正式写入前先判断 `write_readiness`，结果只有三种：

1. `ready`：已发生行为、目标唯一、影响结果的数量和来源明确，直接调用一次写工具。
2. `needs_one_fact`：缺少一个会改变目标、库存或营养结果的事实，只问一个最短问题，零写入。
3. `supplement_or_correction`：用户正在补充或修改上一轮事实，不得当作确认；合并新事实后重新判断准备度。

以下事实属于硬歧义，不得用估算值替代：

- 多个不同库存商品都能匹配同一个口语名称；
- 单只/单瓶规格会改变扣减商品或数量；
- 带骨、带壳、去皮等状态会显著改变可食重量；
- “煎、炒、炸”未给出用油量且完整营养需要包含用油；
- 用户明确说明去除了脂肪、皮、骨或其他部分，但损耗尚未进入计算；
- 一次修正会改变已经生成或后来消耗的剩菜批次。

普通数据库营养估算的不精确不是额外确认理由。硬歧义与普通营养估算必须分开处理。

## 5. 确认与补充信息

只有满足下列全部条件才能调用 `commit_record`：

- 当前只有一个未过期的餐食预览句柄；
- 当前用户消息是纯确认语，不包含新的食品、数量、来源、状态、否定或修正事实；
- 预览内容自生成后没有被补充或修改；
- 工具返回的预览仍然有效。

“鸭腿是库存里面”“是带骨的”“其实是120g”“去掉了3–5g脂肪”等消息都是补充或修正，不是确认。Skill 必须把新事实并入完整事件，重新展示仍缺少的一个事实或重新生成预览；不得沿用旧事实直接提交。

当前宿主不会向工具提供一份不可由模型改写的“本轮用户原文”，因此 v0.7.1 不虚构后端能够独立证明纯确认。这里采用两层保护：Skill 行为评测必须阻止补充信息调用 `commit_record`；工具继续要求单个未过期句柄、未消费状态和显式 `confirmed:true`。如果未来宿主提供可信原文上下文，再把纯确认校验下沉到工具层，本版不引入 OpenClaw 专属接口。

## 6. 模糊库存商品

Skill 必须保留用户原始名称，不能先把“小瓶牛奶”改写成某个品牌 SKU 再查询。

处理顺序固定为：

1. 使用原始口语名称执行只读库存查询。
2. 没有匹配时按非库存餐食处理，除非用户明确说来自库存。
3. 只有一个不同商品匹配时使用该商品；同一商品的多个物理批次交给既有批次策略。
4. 多个不同商品匹配时列出简短候选并询问一次，零写入。
5. 用户选择后使用工具返回的候选/批次句柄完成一次写入，不凭名称重新猜测。

工具层不实现通用中文语义理解，但必须拒绝明显不一致的“模糊原名 + 未经选择的精确 SKU”库存扣减请求，或要求显式选择证据。

## 7. 重量、用油与加工损耗

### 重量

库存若有已确认的单只重量、包装净含量或可食率，Skill 可先查询并使用；只有估算值时必须标记估算。没有可靠依据且差异会明显影响营养或扣库存时，只询问重量/规格，不默认 200g。

### 用油

“煎、炒、炸”需要区分食材自身营养和完整成品营养：

- 用户给出用油量：把油作为独立原料进入同一次 `record_cooking`。
- 已有可靠食谱默认值：明确说明使用该默认值后记录。
- 两者都没有：询问一次用油量，当前轮零写入。

### 加工损耗

加工损耗至少保存名称、数量、单位和类型。骨、壳等非营养部分影响可食率；明确修掉的纯脂肪必须从脂肪和热量中扣除，不能只缩小肉的总重量。若工具尚不能表达该事实，Skill 必须保持营养不完整并询问，不得输出伪精确结果。

## 8. 混合餐次与错误边界

牛奶、咖啡和其他食物可以在同一个餐次请求中记录。每个项目独立声明数量维度和 `nutrition_basis`，不得把某一项的 `ml` 或营养基准复用到其他项目。

遇到结构化且可修复的字段错误时，只修正该字段并重试同一动作一次。相同项目拆开后成功，不能被解释为“临时故障”；回复应说明原请求没有写入，并以最终成功工具结果为准。连续失败后停止，不切换工具强行落库。

## 9. 做饭修正事务

修正一次做饭事件时，旧事件和所有派生数据作为一个整体处理：

1. 定位唯一旧做饭记录。
2. 检查旧剩菜是否被继续食用、丢弃或修改。
3. 若存在无法安全回滚的后续动作，拒绝自动修正并说明冲突对象。
4. 若可回滚，在同一事务内撤销旧原料扣减、旧餐食、旧剩菜批次和营养关联。
5. 使用合并后的完整事实重新计算并写入一次新事件。
6. 任一步失败时保持旧事件不变，不留下幽灵库存。

该事务不通过多次独立的撤销、库存调整和餐食写入来模拟。

## 10. 回复合同

一次用户消息最多产生一段最终业务回复。工具活动是否在前端单独展示不改变这一规则；助手不得再次逐字复制完整工具结果。

成功回复按固定顺序组成：

1. 实际写入的餐食或操作；
2. 简短营养结果，并标明估算或不完整；
3. 工具确认的库存变化；
4. 做饭事件额外显示整锅原料、食用比例和剩菜结果。

所有派生数值使用结构化结果计算：

```text
超出量 = max(当前值 - 目标值, 0)
达成比例 = round(当前值 / 目标值 × 100%)
```

例如脂肪 `77.25g / 55g` 必须表述为“超出22.25g，达到目标的140%”，不能把 140% 中的 40 错写成超出40g。

## 11. DeepSeek 缓存与最小访问合同

优化目标不是“工具调用越少越好”，而是“产生同样正确、完整且可审计的结果时，读取和调用次数最少”。任何会改变目标、数量、库存批次、营养结果或事务安全性的必要查询都不得为了省 Token 被跳过。

DeepSeek 按已落盘且完整匹配的请求前缀命中缓存。Skill 包不能控制所有宿主的请求拼装方式，但必须提供缓存友好的稳定结构。官方规则与命中字段见 [DeepSeek 上下文硬盘缓存](https://api-docs.deepseek.com/zh-cn/guides/kv_cache/)：

1. `SKILL.md` 保留稳定、通用且每次都需要的激活、路由、安全和写入不变量；不为达到长度而填充、改写同义句或复制 reference 细节。
2. 专项规则只保留在唯一 reference 中，按最小充分集合加载；普通单领域消息读取一个 reference，真正跨领域时最多两个。
3. 同一轮已经读取的 Skill/reference 不重复打开；同一轮已经返回且仍有效的只读结果、候选句柄、预览句柄和聚合结果直接复用。
4. 不把系统时间、会话 ID、临时句柄、库存快照、用户本轮文本或版本横幅写入稳定规则正文。宿主允许控制请求顺序时，把这些动态内容放在稳定 Skill/工具合同之后。
5. 不为了缓存增加无业务价值的提示词。更长但变化的前缀只会增加冷启动 Token；只有必要且重复的稳定前缀才有价值。

文件访问预算：

- 每轮以已经加载的 `SKILL.md` 为导航，只加载最小匹配 reference；不“以防万一”遍历全部 references。
- 同一事实的详细规则只存在于一个 reference，主 Skill 仅保留路由和跨领域不变量，避免重复读取和规则冲突。
- 缺少必要 reference 时宁可读取一次，也不得凭记忆猜测计量基准、确认条件或库存规则。

工具调用预算：

- 信息完整且目标唯一的单领域已发生事件：一次正式工具调用，不先做库存、报告、自检或预览探路。
- 模糊库存：一次原名查询；用户选择后复用返回的候选/批次句柄完成一次写入，不再次按名称查询。
- 修正、撤销和重做：一次必要定位读取加一次原子动作；不得拆成多次独立库存和餐食写入。
- 日报、周报和进度：优先一次聚合报告调用，不分别查询餐食、饮水、体重和库存再手工拼接。
- `self_check` 只在安装后、能力确实不确定、用户明确要求或数据库完整性错误后调用；不能作为每个新会话的固定热身。
- 只有字段结构错误且可确定修复时允许修正后重试一次；业务错误、歧义或连续失败不通过换工具、拆请求或重复调用强行成功。

DeepSeek 请求返回 `prompt_cache_hit_tokens` 和 `prompt_cache_miss_tokens` 时，宿主可计算：

```text
cache_hit_ratio = hit / (hit + miss)
```

该指标用于比较相同真实场景的前后版本，不写入用户饮食数据库，也不作为牺牲正确性的优化目标。v0.7.1 不加入供应商专属 API Key、宿主埋点或提示词填充逻辑。

## 12. 测试策略

Skill 行为先写失败评测，再修改文档：

- 模糊“小瓶牛奶”在两个候选 SKU 下必须询问且零写入；
- “鸭腿是库存里面”不得提交旧的 200g 预览；
- 带骨鸭腿无重量时不得默认 200g；
- 补充 120g、可食78g、去脂3–5g 后必须完整重算；
- 四个煎蛋但未知用油时必须询问或保持成品营养不完整；
- 牛奶和咖啡同餐使用各自的 ml 与营养基准；
- 脂肪 `77.25/55` 的超出量和百分比分别正确；
- 成功工具结果只生成一段最终回复。
- 明确非库存餐食只调用一次 `diet_meal`，不先查询库存或执行预览。
- 模糊库存只查询一次，用户选择后复用句柄而不是再次按名称查询。
- 日报/进度使用一次聚合工具调用，不扇出为多领域查询。
- 普通单领域场景只加载一个 reference，同一轮不重复读取。

确定性工具保护使用 Python/TypeScript 契约测试：

- 模糊原名不能在没有选择证据时扣精确 SKU；
- 修正做饭记录后旧剩菜不再作为有效库存存在；
- 已被继续消费的剩菜阻止不安全修正；
- 加工损耗参与营养重算且事务失败不留下部分写入；
- 同一语义重试仍只有一个有效业务事件。

最终运行现有 v0.7 核心门禁、完整 Python 测试、TypeScript 测试、构建、Skill 校验和安装包集成测试。

## 13. 版本与文档交付

- 正式版本统一更新为 `0.7.1`，不生成 partial、dev 或“部分功能”版本。
- 更新 `SKILL.md`、最少量匹配 references、行为评测、工具 Schema/实现、测试和版本说明。
- 更新项目总览和后续路线图中 v0.7.1 的状态；未实施内容必须明确延期，不能写成已完成。
- 生成可复制的 Skill 包和完整源码发布物，但不自动部署生产 OpenClaw。
- 保留 v0.7.0 发布物作为直接回退版本。

## 14. 非目标

- 修复 OpenClaw 或浏览器前端自身的重复事件渲染。
- 修改 Telegram 机器人、Gateway、Lucky、WireGuard、Docker 或软路由。
- 引入多用户、云服务、向量数据库或完整事件溯源平台。
- 用 Python 重新实现通用中文自然语言理解。
- 检查或修改用户当前生产数据库；真实重复写入审计必须使用用户另行提供的数据库副本。
- 为提高缓存指标堆砌重复提示词、加入固定填充文本或修改 OpenClaw/DeepSeek 宿主请求拼装器。

## 15. 验收标准

v0.7.1 只有在以下条件全部满足时才可交付：

- 上述八个真实口语 Skill 场景通过；
- 模糊 SKU 和做饭修正残留具备确定性工具保护；补充信息误确认具备 Skill 行为评测保护；
- 不降低 v0.7.0 已通过的营养缩放、饮水、外食、幂等、库存数量守恒和体重能力；
- 所有写入失败都明确返回未写入，且没有部分库存或餐食结果；
- 完整测试、构建、Skill 校验和安装包验证通过；
- 交付物不含凭据、机器路径或部署环境状态；
- 缓存友好结构不复制规则、不包含动态会话值；简单场景的 reference 和工具预算回归通过；
- 任何调用削减都不绕过模糊库存、修正事务、完整营养或数据库完整性所需的必要读取；
- v0.7.0 回退包保持可用，且本轮不覆盖生产实例。

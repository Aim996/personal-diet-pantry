# 食序管家 v0.7.4.28 可供智能体安装的公开 Release 设计

## 1. 结论

本轮把公开仓库从“源码已经公开、Release 仍在准备”推进为一套可被普通 OpenClaw 用户和其他智能体安全安装、核验、更新与回滚的正式发行项目。

- 产品版本：`0.7.4.28`
- npm / OpenClaw / Python 技术包版本：`0.8.28`
- 正式标签：`v0.7.4.28`
- 分发主路径：GitHub Release 的固定版本可安装包
- 数据库迁移：无，继续使用 migrations `001–021`
- 运行时行为：不修改

本轮只解决公开分发、安装说明和发布闭环，不借机重构饮食记录、饮水、库存、体重、时间解释、进度回执或工具授权逻辑。

## 2. 背景与问题

公开仓库当前代码基线是产品 `0.7.4.27`、技术包 `0.8.27`，但 README 与安装文档仍声称仓库 Private、Release 尚未创建。现有 AI 提示词虽然描述了下载 Release 的动作，远端却没有可下载的正式 Release，智能体无法完成它被要求执行的工作。

这不是业务实现问题，而是分发合同不完整：

1. 用户找得到源码，但找不到被验证的安装制品。
2. 智能体知道“应当校验哈希”，却没有稳定的资产名称和实际校验文件。
3. README、安装手册、升级说明、Release Notes 与 GitHub 远端状态不一致。
4. GitHub Actions 因账户计费锁定不能启动，自动发布链路暂时不可用。

因此，本版采用“本地完整验证与可复现构建 + 人工创建受校验的 GitHub Release”。Actions 仍保留为未来恢复后的标准入口，但本次不能把未运行的 Actions 描述为已通过。

## 3. 目标

1. README 在首屏真实说明项目用途、当前正式版本和推荐安装入口。
2. 普通用户可以只依赖 Release 资产完成安装，不需要克隆源码或现场编译。
3. 其他智能体可以沿一条确定、可暂停、可验证、零业务写入的流程安装和验收。
4. 安装包、源码快照、测试摘要、manifest 和校验清单之间可互相核验。
5. `dataDir` 始终独立于插件安装目录；更新插件不得覆盖个人数据。
6. 初始化属于有状态操作，必须获得用户明确授权；只读验收不得初始化或写入业务数据。
7. 失败时停止，不用源码扫描、反复安装或删除数据来“试出来”。
8. 保留所有跨版本产品行为约束和总项目 Good Flags。

## 4. 非目标

- 不修改 `src/`、`python/`、`skills/personal-diet-pantry/` 的运行时业务语义。
- 不新增、修改或删除 migration；migrations 保持 `001–021`。
- 不修改或读取任何生产 OpenClaw 的 `dataDir`。
- 不部署或重启用户当前 OpenClaw。
- 不发布 npm 包；`package.json` 继续保持 `"private": true`。
- 不把源码压缩包宣传为插件安装包。
- 不增加 Docker 镜像、ClawHub 分发、多用户托管或远程数据库。
- 不覆盖 `0.7.4.27` 目录、Tag、制品或历史文档。

## 5. 单一正式分发路径

正式安装以 GitHub Release `v0.7.4.28` 为单一入口。Release 必须恰好上传五个资产：

1. `personal-diet-pantry-0.7.4.28-installable.tgz`
2. `personal-diet-pantry-0.7.4.28-source.tar.gz`
3. `release-manifest.json`
4. `TEST-SUMMARY-v0.7.4.28.zh-CN.md`
5. `SHA256SUMS`

其中只有 `installable.tgz` 可以交给 OpenClaw 插件安装器；`source.tar.gz` 只用于审阅和复现。`SHA256SUMS` 必须覆盖前四个资产，并由发布后复核再次确认。

不把 `git clone` 或 GitHub 自动生成的 Source code 归档列为普通用户主路径，因为公开仓库不跟踪已编译的 `dist/`，源码检出不是可直接安装成品。

## 6. 人与智能体共用的安装状态机

### 6.1 发现与下载

1. 固定仓库为 `Aim996/personal-diet-pantry`。
2. 固定 Release 为 `v0.7.4.28`，不追随 `latest` 的未来漂移。
3. 下载 `installable.tgz` 与 `SHA256SUMS`；需要审计时再下载 manifest、测试摘要和源码快照。
4. SHA-256 不一致时立即停止，不安装、不“重新打包”。

### 6.2 环境前置检查

安装前确认：

- OpenClaw `>=2026.5.17`
- Node.js `>=22.22.3 <23 || >=24.15.0 <25 || >=25.9.0`
- Python `>=3.11,<4`
- Python 锁定依赖可以安装
- 有一个位于插件目录之外、权限受控的专用 `dataDir`

环境不满足时报告缺项并停止。智能体不得私自升级整个宿主、改变其他插件或扩大权限范围。

### 6.3 安装与配置

1. 从安装包或可信源码中的 `requirements.lock` 安装 Python 运行依赖。
2. 创建专用外部 `dataDir`，但不创建虚假的业务记录。
3. 执行：

   ```text
   openclaw plugins install npm-pack:/absolute/path/personal-diet-pantry-0.7.4.28-installable.tgz
   openclaw plugins enable personal-diet-pantry
   ```

4. 在 `plugins.entries.personal-diet-pantry.config.dataDir` 中设置该 `dataDir`；Python 解释器由 OpenClaw 进程的 `PYTHON` 环境变量选择，不伪造插件不存在的配置字段。
5. 通过目标实例既有方式重启或重新加载；默认命令是 `openclaw gateway restart`，但不得把它套用到无法确认的容器或远程实例。

### 6.4 运行时验收

先运行：

```text
openclaw plugins inspect personal-diet-pantry --runtime --json
```

必须确认七类工具均来自真实运行时：`diet_meal`、`diet_water`、`diet_weight`、`diet_pantry`、`diet_transaction`、`diet_report`、`diet_system`。文件存在、插件元数据存在或 shell 退出码为零，都不能代替真实工具注册证据。

全新数据库只有在用户明确同意初始化后，才执行 `diet_system initialize`。随后执行 `diet_system self_check`。验收默认只做版本、工具注册、健康状态、schema/migration 状态和只读查询；不得为了证明“能写”而写入真实餐食、饮水、库存、体重、目标或偏好。

## 7. 更新、失败与回滚

更新前必须：

1. 确认目标实例、当前产品/技术版本和真实外部 `dataDir`。
2. 停止实例并制作校验过的一致 SQLite 冷备份。
3. 记录只读表计数和健康状态，不导出个人数据到聊天或日志。
4. 校验 v0.7.4.28 资产，再只替换插件包，保留 `dataDir`。
5. 重启后比较版本、七类工具、自检和只读数量。

本版没有新 migration，直接技术回退点仍是 `0.7.4.19`；它只代表可恢复运行，不代表已通过产品 UAT。若只是插件注册失败且数据未变化，可以重装已校验旧包；若数据库或记录数量异常，保持停止并从升级前冷备份恢复。在线 `diet_system backup` 不能替代升级前冷备份。

## 8. 受保护行为影响矩阵

以下能力均为“无行为变化，必须通过既有门禁”：

- CORE-01～CORE-10：摄入、饮水、库存、体重、目标、查询、建议、回执和确定性业务语义。
- SAFE-01～SAFE-07：只读不写、当前轮次授权、原子性、删除定位、任务失效、时间一致性、数据安全。
- GOV-01：已完成版本不可变，本版从 0.7.4.27 新开。
- GOV-02：用户明确保留的能力未经许可不得修改。
- UI-01：纯饮水只显示饮水反馈，不强制展示热量等五项营养进度。
- GF-001～GF-005：历史被确认表现良好的功能标记继续有效。

本轮允许变化的只有：当前版本文字、公开 Release 状态、资产名称、安装/更新/验收说明、发布自动化参数和相应测试合同。

## 9. 测试与发布门禁

### 9.1 测试顺序

1. 先更新版本、公开仓库表面和 Release 工作流测试，使它们因实现尚未同步而失败。
2. 再更新文档、元数据和发布配置使定向测试通过。
3. 运行完整 `ci/verify.ps1`，其中包括受保护核心测试、Python/Vitest 全量测试、构建、Skill 验证、敏感信息扫描、Release 审计、安装 E2E 和依赖审计。
4. 在 Git 工作树之外构建一次性 `0.7.4.28` 版本目录；目标若已存在必须停止，不覆盖。
5. 复核构建目录顶层、manifest、安装包成员和 SHA-256。

### 9.2 GitHub 发布顺序

1. 通过隔离分支提交并推送。
2. 创建 PR，使差异可审计；由于 Actions 计费锁定，远端自动检查预计无法启动，必须如实记录。
3. 只有本地完整门禁通过后才合并到 `main`。
4. 在合并后的精确提交重新完成发布构建和哈希核验。
5. 确认远端没有同名 Tag/Release 后创建 annotated tag `v0.7.4.28`。
6. 上传恰好五个资产，创建正式非草稿 Release。
7. 从公开 Release API/页面复核 Tag 目标、资产名称、大小和可下载 URL。

## 10. 验收标准

- README 不再出现“Private”“发布准备中”“GitHub Release 尚未创建”等过期状态。
- 中英文版本、包元数据、Python 版本、插件元数据、更新文档和资产名称完全一致。
- AI 安装提示词没有占位符以外的模糊决定点，且明确哪些步骤需要用户授权。
- 发布资产恰好五个，SHA-256 全部匹配。
- 可安装包在隔离环境中完成插件包语义和安装 E2E 验证。
- migrations 仍恰好是 `001–021`，运行时源文件没有业务性变化。
- 全部受保护行为门禁通过。
- GitHub Release `v0.7.4.28` 为公开、非草稿、非预发布，并指向公开 `main` 的已验证提交。
- Actions 计费锁定被记录为基础设施限制，不被伪装为测试通过，也不否定本地门禁证据。

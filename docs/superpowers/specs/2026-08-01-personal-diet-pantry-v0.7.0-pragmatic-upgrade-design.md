# 食序管家 v0.7.0 务实升级设计

日期：2026-08-01

目标版本：`0.7.0`

可回退版本：`0.6.1.5.1`（内部包版本 `0.6.2-dev.6`）

用户选择：方案 A——保留有效成果，停止低收益的底层安全循环，优先完成日常使用价值。

## 1. 背景与决策

`0.6.1.5.1` 目前仍可勉强满足实际使用。原 v0.7.0 计划逐渐扩大为企业级文件安全与崩溃恢复工程，投入集中在 Windows 原生句柄、AST 写入扫描和多轮安全复审，偏离个人饮食 Skill 的核心价值。

v0.7.0 改为务实升级：不要求逐项复刻 `0.6.1.5.1` 的全部 55 个动作；不适合、低使用率或维护成本过高的能力可以明确退化或延期。不可退让的底线是核心日常流程可用、升级不会静默破坏数据、错误不会制造重复记录，并且用户能用备份完整回退。

本设计取代原总控计划中尚未完成的细粒度工作包和无限复审要求。已经提交且有实际价值的代码保留；只有妨碍核心体验或维护的内容才删除。每个工作包最多经历一次实现和一次回归验证，只有出现明确可复现的核心缺陷才继续修复。

## 2. 产品目标

用户在 OpenClaw、Telegram 或其他正常会话中，用日常中文描述已经发生的行为，食序管家应当完成正确记录，并给出简短自然的结果。

v0.7.0 优先解决：

1. 营养值和饮水量不再因“整份值/每 100g 或每 100ml”混用而重复缩放。
2. 明确说“吃了、喝了、买了、扔了、做了、体重……”时直接记录；仅在信息冲突、不可逆高风险操作或无法确定对象时确认。
3. 重试、短确认和网络波动不得造成重复记录。
4. 外食不扣家庭库存；做饭、剩菜和丢弃按实际数量修改库存。
5. 体重按系统时间记录，自由保存“空腹、睡前、餐前”等状态文字，并在有数据时给出 7 日或 15 日均值及升降趋势。
6. 用户回复不暴露函数名、缩放规则、工具错误或调试过程。

## 3. 兼容与退化边界

### 必须保留

- `0.6.1.5.1` 的 SQLite 数据目录能够在备份副本上完成升级，核心饮食、饮水、库存和体重数据可查询。
- 七个顶层工具名称保持不变：`diet_meal`、`diet_water`、`diet_weight`、`diet_pantry`、`diet_transaction`、`diet_report`、`diet_system`。
- 核心记录、查询、修改/删除、撤销、目标与自检入口仍可使用。
- 所有写操作具备基本原子性；失败时不能返回成功，也不能留下同一行为的重复记录。
- 生产实例在部署前保留软件包与数据目录备份，回退时同时恢复旧包和旧数据。

### 允许退化或延期

- 很少使用的维护动作、复杂恢复证据、跨进程极端竞争和企业级发布扫描。
- Windows 原生 parent-handle 目录创建、覆盖全部未来写入器的 AST scanner 等低收益防御。
- 无法在本轮稳定完成、且不影响日常记录的高级洞察、复杂导入导出或历史维护细节。

任何退化必须写入 v0.7.0 发布说明；不得通过静默吞错或伪造成功来实现。

## 4. 简化架构与数据流

保持现有七领域工具与 Python 服务结构，不进行全面重写：

```text
自然语言输入
  → Skill 识别领域与已发生/计划语义
  → 生成规范化业务参数
  → 服务层校验与幂等写入
  → SQLite 核心事实
  → 简短自然语言回执
```

营养数据只允许两种明确基准：`per_100_unit` 或 `total_portion`。进入持久层前统一换算成一次记录的总量，饮水贡献不得不合理地超过实际饮用体积。无法可靠估算时保存低置信度或缺失值，不用夸大的精确数字填充。

会话中的确认只负责补齐不确定信息，不作为第二次业务提交。重复请求通过现有操作指纹、提交句柄或等价幂等键合并。

## 5. 五个工作包

### P1：收口现状与建立核心门禁

- 停止 TW4 的第三轮底层安全扩展。
- 保留已提交的有价值成果；不继续未提交的过度审查测试。
- 从真实使用方式建立小型核心回归集。
- 修复当前全套测试中的日期耦合、迁移版本硬编码和旧升级夹具问题。

### P2：饮食、营养、饮水与幂等正确性

- 统一营养计量基准。
- 限制液体水分贡献。
- 清晰已发生行为直接写入。
- 修复确认、重试和网络重复提交。
- 外食不扣库存。

### P3：自然口语与七领域路由

- 保留 `0.6.1.5.1` 的自然口语触发优势。
- 明确体重、饮水、饮食、库存、做饭、撤销、报告的优先级。
- 新会话和 Telegram 会话均依靠 Skill 自身说明命中，不依赖某个旧会话状态。
- 用户回复隐藏内部工具和调试痕迹。

### P4：库存、体重与报告闭环

- 校验入库、扣减、丢弃、做饭和剩菜数量守恒。
- 完成体重记录、自由状态文字、7/15 日均值与趋势。
- 日常报告只展示有数据且可信的内容。
- 撤销/重做只覆盖确实可逆的普通业务写入。

### P5：发布、备份回退与文档

- 在 `0.6.1.5.1` 数据备份副本上演练升级。
- 跑核心场景、Python/TypeScript 主测试和安装包验证。
- 对主动退化的动作更新 README、更新说明和路线图。
- 生成一个完整 `0.7.0` 发布物，不生成 partial/dev 版本。
- 本轮只准备发布物，不自动部署或覆盖当前生产实例。

## 6. 核心验收场景

v0.7.0 至少通过以下真实语言场景：

1. “早餐吃了两个小红薯，喝了 500ml 豆浆。”营养和饮水量合理且只记录一次。
2. “中午在公司吃了两个煎蛋，喝了一瓶 300ml 牛奶。”不扣家庭库存。
3. “煎了 6 个鸡蛋，用了 10ml 油，吃了 2 个，剩 4 个放冰箱。”数量守恒。
4. “苹果有一个坏了，我刚扔了。”只减少一个，不出现工具报错风暴。
5. 同一句已吃记录重试两次，数据库仍只有一次业务结果。
6. “喝了 500ml 水。”直接记录且可查询、修改、删除。
7. “105，空腹。”按系统时间记录体重与状态；有历史时显示 7/15 日趋势。
8. “刚才记错了，撤销。”只撤销最近可逆操作。
9. 日报/周报不展示不存在的均值，不混合低置信度营养为精确结论。
10. `0.6.1.5.1` 数据备份副本升级后，饮食、饮水、库存和体重核心记录仍可查询。

## 7. 错误处理

- 参数缺失但不影响基本记录时采用保守默认并在回复中简短说明。
- 对象冲突、不可逆删除和明显异常数值才请求确认。
- 写入失败返回明确失败，不生成成功话术。
- 重试使用同一个幂等语义，不创建第二条记录。
- 估算不可靠时宁可少报或标记估算，也不输出明显错误的高精度数据。

## 8. 验证与交付标准

每个工作包只执行：目标测试 RED、最小实现 GREEN、相关回归一次。最终统一执行完整测试和真实场景验收。高级能力的测试若因明确退化不再适用，应同步删除或改写契约并在发布说明记录，不能简单跳过失败。

v0.7.0 可交付条件：

- 十个核心场景通过；
- 无已知数据破坏、重复提交或营养数量级错误；
- 备份副本升级与回退步骤验证完成；
- 主测试、构建和安装验证通过；
- 所有主动退化均有文档；
- 当前 `0.6.1.5.1` 生产实例在用户决定部署前保持不变。

## 9. 非目标

- Docker/OpenClaw/软路由生产部署。
- 多用户、云端托管和凭据管理。
- 自动图片识别模型集成。
- 企业级跨进程文件系统安全证明。
- 为了测试数量或形式完整而继续无边界扩展。

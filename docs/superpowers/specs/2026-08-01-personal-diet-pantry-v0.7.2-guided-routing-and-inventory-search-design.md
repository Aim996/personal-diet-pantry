# 食序管家 v0.7.2 Skill 定向工具导航与库存检索设计

日期：2026-08-01

目标版本：`0.7.2`

基线版本：`0.7.1`

状态：设计已分段确认，等待文档审阅

补充决策日期：2026-08-02

## 1. 项目定位

食序管家首先是一套可复制、可安装、可迁移的个人饮食与库存 Skill。`SKILL.md`、按需 references、工具能力契约、配套 Schema、确定性服务和测试共同组成 Skill 产品；OpenClaw、Telegram、Docker、软路由和某一次会话不属于本轮优化对象。

本轮不是给模型增加一堆限制，也不是为了追求更少调用而牺牲正确性。目标是给模型一张清楚、稳定、可适配工具升级的路线图：正常情况走最短路径，出错时依据新证据自救，同一条死路不重复；简单库存使用先定向搜索，不能把宽泛库存结果交给模型逐项阅读。

## 2. 已确认的问题

### 2.1 工具路线存在“过硬”和“过松”两种风险

当前主 Skill 已经要求清晰单领域请求直接调用一次正式工具、避免预查询和错误风暴，但仍有以下缺口：

- 工具就绪规则偏向一次确认全部七个领域；一个无关领域缺失，不应阻止当前可用领域工作。
- 工具名称、action、参数和错误恢复分散在主 Skill、references、Schema 与契约中，可能发生漂移。
- 固定重试次数会妨碍有新证据时继续自救；完全开放尝试又会产生重复调用和错误风暴。
- 部分 `INVALID_INPUT` 没有足够的结构化字段，模型无法确定应该修正什么。
- 餐食文档与 Schema 对 `per_unit` / `per_serving` 等计量基准存在冲突风险。

### 2.2 工具 Schema 本身增加模型负担

基于当前构建产物的序列化测量，`MealParametersSchema` 约为 1,000,414 字节，明显高于其他领域 Schema。具体供应商计费 Token 仍取决于宿主如何封装工具，但这一体积会增加上下文负担、降低模型理解工具参数的稳定性，并可能降低稳定前缀的实际收益。

### 2.3 库存查询仍不够定向

当前 `diet_pantry query` 支持 `normalized_name` 精确过滤、最多 20 条分页和精简/详细输出；没有名称时会返回一页宽泛库存。餐食库存匹配内部还会读取相同单位下所有可用商品名称，再在进程内进行精确、已学习别名、语义组和包含关系匹配。它不会把所有数据库行直接发给模型，但库存名称集合会随数据增长而扩大；模型若主动发起无名称查询，还会把不相关库存结果带入上下文。

用户确认的目标是：先以原始食品关键词执行定向检索，只返回少量相关候选；同一商品的多批次由后台确定性扣减。只有用户明确询问完整库存时，才允许分页浏览库存。

## 3. 方案比较与选择

### 方案 A：只增加提示词

改动小，但不能解决 Schema 膨胀、文档/契约冲突、模糊错误和数据库检索范围问题。

### 方案 B：Skill 优先的混合式优化（采用）

主 Skill 提供稳定导航和恢复原则，领域 references 保存按需细节，机器契约统一能力映射，配套 Schema/服务只补足无法由提示词可靠保证的确定性能力。该方案兼顾可复制性、适配性、成本和数据正确性。

### 方案 C：新增通用动态路由器

工具变化适配能力最强，但会增加发现调用、依赖和新的故障点，不符合本轮减少无效调用的目标。

## 4. Skill 分层结构

### 4.1 稳定总控层：`SKILL.md`

主 Skill 只保留每轮都需要的内容：

- 自然语言触发和排除边界；
- 七个业务能力域的快速路由；
- 写入准备度与确认规则；
- 能力优先的工具选择；
- 进展驱动的恢复原则；
- 最小 reference 加载规则；
- 用户可见回复和数据可信边界。

主 Skill 不复制领域参数大全，不为达到行数而填充同义规则。现有“主文件必须 350～450 行”的人工下限应取消，保留可读性上限、必需章节和行为契约检查。

### 4.2 按需领域层：references

餐食、库存、饮水、体重、做饭、事务、报告、目标和维护规则分别保存在唯一 reference 中。正常单领域请求只读取一份；跨领域请求读取完成当前意图所需的最小集合；同一轮不重复打开已经读取的 reference。

### 4.3 机器契约层：`contracts/tools.yaml`

契约是能力路由的机器可校验事实源。每项能力至少描述：

- `capability`：业务能力，而不是工具品牌；
- `preferred_tool` 与 `preferred_action`；
- 关键必填字段和写入/只读属性；
- 允许替代工具的等价条件；
- 不允许通过替代工具绕过的业务错误；
- 对应 Schema、实现和契约测试。

Skill 中的人类可读工具路线应由该契约生成或由测试核对，避免手工维护两份不一致清单。

### 4.4 确定性支撑层

TypeScript Schema、桥接层和 Python 服务只承担必须由程序保证的能力，例如输入边界、幂等写入、操作状态核验、索引检索、候选句柄、批次扣减和结构化错误。它们服务于可复制 Skill，不扩张成独立应用平台。

## 5. 能力优先的工具导航

每次请求使用稳定路线：

```text
理解完整意图
  → 定位业务能力
  → 读取最小 reference
  → 选择首选工具/action
  → 一次组装完整参数
  → 调用并使用结构化结果
  → 成功后停止
  → 失败时进入分类恢复
```

工具选择规则：

1. 当前可见工具中存在首选工具/action 时直接使用。
2. 首选工具缺失或明确改名时，才允许解析替代能力。
3. 替代项必须由当前工具说明或 Schema 明确证明能力、输入输出与安全语义等价。
4. 找不到可靠等价项时停止并说明缺少的能力；不猜工具名、不跨业务域碰撞。
5. 业务校验失败不是工具缺失，不能为了强行成功而切换工具。
6. 就绪检查按当前所需能力执行，不因无关领域工具缺失而阻塞。

## 6. 进展驱动的后台自救

本轮不设置“最多调用几次”的固定上限。每个后续动作必须至少满足一个进展条件：

- 获得新的事实或候选；
- 修正错误明确指出的字段；
- 消除目标歧义；
- 核验不确定的写入状态；
- 发现经契约验证的等价能力；
- 系统状态确实发生了可验证变化。

本轮内部维护轻量尝试指纹：

```text
业务能力 + 工具 + action + 规范化参数 + 错误特征
```

相同指纹不得原样重复；指纹不写入饮食数据库，也不展示给用户。参数、目标、证据或系统状态发生有效变化后，可以继续自救。

错误恢复合同如下：

| 错误类型 | 恢复动作 |
|---|---|
| 工具不存在或改名 | 在当前可见工具中解析明确等价能力 |
| 结构化字段错误 | 只修正被指出的字段，继续原能力 |
| 信息不足 | 先利用现有上下文；仍不足时只问缺失事实 |
| 商品或批次歧义 | 定向搜索候选；唯一则继续，否则询问 |
| 超时、损坏响应、结果未知 | 先按操作标识查询状态，不盲目重复写入 |
| 预览/句柄过期 | 读取最新必要状态，按原始用户意图重建 |
| 数据库繁忙 | 保持幂等标识，在状态未改变时安全重试 |
| 库存不足、低置信度、不可撤销 | 作为业务结果汇报或询问，不换工具绕过 |
| 完整性或维护错误 | 停止写入，执行可用自检或说明阻塞 |
| 相同参数与相同错误 | 判定无进展，停止原样尝试 |

安全的修参、状态查询和可靠等价替代在后台完成。用户只接收最终成功结果，或真正无法继续时的一条清楚说明，不接收调试日志和工具错误风暴。

## 7. 库存定向检索

### 7.1 查询层级

库存相关的简单吃用请求采用逐级扩大、结果受限的检索：

```text
原始食品名称
  → 索引化精确名称
  → 已学习别名/静态别名
  → 索引化前缀或关键词候选
  → 唯一商品则返回句柄
  → 多个不同商品则询问用户
```

不得从“鸡蛋”直接进入无条件库存列表。只有前一级没有足够结果时才进入下一级；每一级必须保留用户原始名称，不先把“小瓶牛奶”改写成某个具体 SKU。

### 7.2 工具接口方向

`diet_pantry` 保持一个顶层工具，避免增加模型发现成本。库存只读能力明确区分两个 action：

- `search`：接受原始 `search_text`、可选 `unit`、`statuses`、`storage_location` 和 `limit`；`limit` 默认 5 且最大 5，返回聚合商品候选。
- `query`：保留现有 `normalized_name` 精确过滤、详细字段开关和分页；只在已知规范名称，或用户明确询问库存、临期和详情时使用。

定向候选只返回完成识别所需的信息：显示名称、规范名称、单位、可用总量、批次数、必要规格、匹配依据和不透明候选句柄。营养、价格、全部批次和完整元数据按需读取，不能作为默认候选负载。

精确 `normalized_name` 继续保持向后兼容；原始 `food_name` 兼容入口转为 `search_text` 语义，不再被桥接层无条件转换成精确规范名。Schema 必须让模型能够区分“已知规范名使用 `query`”和“用户原话使用 `search`”。

### 7.3 数据库与批次行为

- 精确名称、别名和常用前缀使用索引优先查询；不以读取全部可用商品名称作为常规解析入口。
- 不引入必须依赖云服务、向量数据库或特定模型的搜索方案。
- 同一商品存在多个批次时，候选阶段返回聚合结果；正式扣减仍由后台按已定义的 opened-first、临期优先和入库时间顺序处理。
- 多个物理批次不等于多个商品，不要求用户逐批选择；多个不同商品才需要选择。
- 解析成功后复用候选/商品句柄，不能再次按名称搜索。
- 用户明确要求“查看全部库存”时使用分页，不能一次无界返回。

### 7.4 与餐食工具的关系

明确的非库存餐食仍只调用 `diet_meal`，不预查库存。用户明确说明来自库存，或餐食动作包含库存扣减时，由餐食工作流调用同一确定性定向解析能力；模型不需要先单独读取一遍库存，再把结果手工拼进餐食写入。

### 7.5 库存与营养一次组合返回

营养数据不物理合并进 `pantry_batches`。当前的库存批次、营养档案、批次营养快照和营养缓存都位于同一个 `diet.sqlite`，不是需要模型分别读取的多个数据库文件。保留分层结构可以避免同款商品每次入库都复制一套可变营养档案，同时保留来源、版本和历史计算口径。

工具返回需要消除“数据库分表等于模型多读一次”的假象：

- `diet_pantry search` 增加可选 `nutrition_mode`：`none`、`summary`、`full`，默认 `none`。
- 普通库存定位返回 `nutrition_available`，不默认展开营养字段。
- 用户询问热量或主要营养时使用 `summary`，在同一次定向搜索中返回计量基准、热量和主要宏量营养。
- 用户明确查看完整营养标签时才使用 `full`。
- `diet_meal` 消耗库存时在服务内部读取批次营养快照并完成缩放，不要求模型先调用一次库存营养查询。
- 同一商品的多批次可复用营养档案，但每个已关联批次继续保留自己的营养快照，防止档案修订静默改写历史。
- 营养档案没有变化时不重复上传或重建；修订产生新版本，并由明确的重新关联决定哪些现存批次采用新版本。

因此，本轮减少的是模型读取、工具往返和返回负载，而不是通过反规范化牺牲营养来源与历史可信度。

## 8. DeepSeek 与上下文成本

增加提示词本身不会提高缓存命中。只有必要、重复且字节稳定的前缀才可能在宿主和供应商支持时受益。本轮采用：

- 主 Skill 保持稳定顺序，不注入时间、会话 ID、库存快照和本轮原文；
- 路线卡保持短小并尽量由机器契约校验；
- 领域细节只在对应 reference 中出现一次；
- 正常请求不读取无关 reference；
- 库存搜索只返回少量候选，避免把库存快照带入模型上下文；
- 压缩餐食 Schema 的递归/组合展开，保留所有 action 和校验语义；
- 对各工具序列化 Schema 体积加入回归预算，防止再次异常膨胀。

若 DeepSeek/宿主返回缓存命中与未命中 Token，可在相同场景、相同请求结构下比较前后版本；缓存指标不能凌驾于数据正确性，也不写入用户饮食数据库。

## 9. 测试驱动实施策略

本轮所有行为变更遵循 RED-GREEN-REFACTOR。先在 v0.7.1 基线上建立会失败的最小场景并确认失败原因，再修改 Skill 或实现。

### 9.1 Skill 行为 RED 场景

- “吃了一个鸡蛋，来自库存”：不得先读取宽泛库存列表。
- “吃了一个已关联营养的库存鸡蛋”：一次餐食操作同时完成定向扣减和营养计算，不先读取营养档案。
- “喝了小瓶牛奶”，库存有两个不同 SKU：只返回少量相关候选，零写入。
- “查询这瓶牛奶的主要营养”：一次定向 `search` 使用营养摘要，不再追加第二次营养文件/全表读取。
- 首选工具改名，但存在描述和 Schema 明确等价的工具：允许继续；不存在等价项时停止。
- 原工具返回库存不足：不得切换其他工具强行写入。
- 结构化错误指出 `unit`：只修正单位，不能重建无关字段或换工具。
- 写入超时：先查询操作状态，不能盲目重放。
- 完全相同的工具、action、参数和错误：不能再次原样调用。
- 复杂请求在获得新证据后仍可继续，证明没有被固定次数限制绑死。
- 明确单领域请求只加载对应 reference；同一轮不重复读取。

### 9.2 确定性工具 RED 场景

- 原始名称定向搜索只返回相关候选且数量不超过约定上限。
- 精确规范名、静态别名和已学习别名均能命中同一商品。
- 多批次同商品聚合为一个候选，正式扣减顺序保持现有确定性规则。
- 多批次同商品可复用营养档案，同时各自的批次营养快照保持独立和稳定。
- `nutrition_mode=none` 不展开营养，`summary` 返回有界摘要，`full` 只在明确请求时返回完整标签。
- 多个不同商品返回歧义候选，不自动选择具体 SKU。
- 大量不相关库存存在时，候选负载和查询结果数量保持有界。
- 原始 `food_name`/`search_text` 与精确 `normalized_name` 的行为可区分且向后兼容。
- 操作结果未知时，可靠性层不产生重复业务记录。
- Schema 压缩前后的有效/无效请求集合保持契约一致。

受当前协作环境约束，不使用未经用户要求的子代理。Skill 行为基线优先通过项目现有 `skill-evals`、契约测试和可重复场景夹具记录；具备真实宿主和模型评测条件时，再补充同场景的多次模型回放，并保存评分标准而非用户数据。

## 11. 风险与控制

| 风险 | 控制 |
|---|---|
| 导航过硬导致无法自救 | 用进展条件代替固定调用上限 |
| 替代工具语义不一致 | 只有能力、输入输出和安全语义均明确等价才替代 |
| 搜索太窄漏掉口语名称 | 精确、学习别名、静态别名、索引关键词逐级扩大 |
| 搜索太宽再次带回全库 | 默认候选上限、精简字段、显式全库浏览条件 |
| 把营养字段塞入每个批次造成重复和漂移 | 保留档案与批次快照，通过工具一次组合返回 |
| Schema 压缩破坏功能 | 压缩前先写 action/有效性契约，逐项保持通过 |
| 提示词重复反而增加成本 | 单一事实源、按需 references、取消人工行数下限 |
| 优化调用数损害正确性 | 必要的歧义、事务和完整性查询不纳入“无效调用” |

## 12. 非目标

- 不限制模型只能调用一次或两次工具。
- 不允许模型无依据地自由猜测替代工具。
- 不把通用中文自然语言理解重新实现到 Python 中。
- 不引入云搜索、向量数据库或供应商专属 API Key。
- 不修复外部前端重复渲染或消息事件消费问题。
- 不把完整库存、营养库或调试日志写进主 Skill。
- 不自动部署或覆盖任何现有 OpenClaw 实例。

## 13. 验收标准

v0.7.2 只有在以下条件全部满足时才能交付：

- 七个业务域及 v0.7.1 已通过的营养、饮水、体重、库存、批次、事务和报告能力不回退。
- 清晰单领域请求不执行无关预查询，成功后立即停止。
- 相同调用指纹和相同错误不会原样循环；有新证据时仍可继续自救。
- 工具替代只发生在首选能力缺失且存在可验证等价项时。
- 写入结果未知时先核验状态，不生成重复记录。
- “吃一个鸡蛋”等简单库存场景不读取宽泛库存列表。
- 定向库存候选默认有界、字段精简、支持别名，并能区分多批次同商品与多个不同商品。
- 库存与营养仍在同一正式数据库内分层保存；一次定向工具操作可以按意图返回无营养、摘要或完整标签。
- 餐食消耗已关联库存时在一次 `diet_meal` 操作内使用批次营养快照，不要求模型额外读取营养档案。
- 完整库存只在用户明确要求时分页读取。
- 工具文档、action、Schema 与实现由契约测试保持一致。
- 餐食 Schema 显著压缩且所有现有 action/校验行为通过回归测试。
- 主 Skill 不依赖人工最小行数，不复制领域细节，不包含动态或部署专属内容。
- 完整 Python、TypeScript、Skill、构建、发布和安装测试通过，发布物不包含凭据和机器路径。
- 只交付一个完整版本 `0.7.2`；保留 `0.7.1` 作为直接回退版本，不自动部署生产环境。

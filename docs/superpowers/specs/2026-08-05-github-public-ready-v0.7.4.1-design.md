# 食序管家 GitHub 公开就绪设计（产品 0.7.4.1 / 技术包 0.8.1）

## 1. 背景与结论

食序管家已经具备较强的业务实现、发布构建和本地验证能力，但当前 GitHub 仓库仍以开发记录为中心：普通 OpenClaw 用户打开首页后，需要阅读较长的版本历史和工程说明，才能找到安装、数据安全、升级与回滚入口；仓库也缺少独立许可证、统一变更日志、社区安全说明以及从版本标签生成可下载 Release Assets 的正式自动化流程。

本轮把仓库内容整理为“未来可以直接公开”的模式，但仓库继续保持 Private。本轮不修改仓库可见性，不合并 `main`，不创建正式 Git Tag 或 GitHub Release，也不触碰已安装实例和真实用户数据。

采用以下版本身份：

- 产品版本：`0.7.4.1`
- npm / OpenClaw / Python 技术包版本：`0.8.1`
- 开发分支：`codex/github-public-ready-v0.7.4.1`
- 基线提交：产品 `0.7.4.0` / 技术包 `0.8.0` 的提交 `73496bf180eea44304b2b6d84b4021606780be3c`

现有 `0.7.4.0` 分支、归档和制品保持不变。

## 2. 目标

本轮必须同时实现以下结果：

1. 普通 OpenClaw 用户在一分钟内理解项目用途、当前状态、推荐安装入口和数据安全边界。
2. 普通用户默认从固定版本 GitHub Release 的预构建包安装，不需要克隆源码、安装开发依赖或现场编译。
3. 安装、更新、备份、健康检查和回滚各有清晰入口，并共享同一套事实，避免多份文档漂移。
4. 未来推送正式版本标签时，GitHub Actions 只有在完整验证成功后才创建 Release 和上传资产。
5. Release Assets 包含可安装包、源码快照、清单、测试摘要和 SHA-256 校验信息。
6. 任何发布流程都不能包含数据库、真实用户数据、凭据、日志、缓存或本地环境。
7. 为使用其他 AI 运维 OpenClaw 的用户提供三套可直接复制的安装、更新和验收提示词。
8. 保留所有跨版本产品行为约束，不修改食序管家的业务语义、数据库结构和迁移历史。

## 3. 非目标

本轮明确不做：

- 不把 GitHub 仓库从 Private 改成 Public。
- 不合并现有 Draft PR 或 `main`。
- 不创建、移动或覆盖任何既有 Tag。
- 不创建正式 GitHub Release，也不上传本地 `0.7.4.0` 制品冒充新版本资产。
- 不发布 npm 包；`package.json` 继续使用 `"private": true` 防止误发布。
- 不增加数据库 migration，不修改 migration 001–021。
- 不改变七类公开工具、40 个日常动作或任何受保护产品行为。
- 不修改、迁移、删除或读取生产 `dataDir` 中的个人饮食、库存、体重和偏好数据。
- 不制作无事实依据的截图、下载量、通过率、用户数量或其他宣传数据。
- 不引入托管服务、多用户系统、Docker 生产镜像或远程数据库。

## 4. 用户与信息优先级

首要读者是希望在 OpenClaw 中安装个人饮食与家庭食材管家的普通用户。第二读者才是审阅源码、贡献代码或维护发布流程的开发者。

README 前半部分必须让普通用户依次获得：

1. 一句话定位；
2. 当前产品版本、技术包版本和发布状态；
3. 六至八项可感知的核心能力；
4. 一段真实格式的饮食记录与六项两行进度回执；
5. 推荐安装入口；
6. 运行环境兼容性；
7. 数据保存位置、备份和回滚边界；
8. 当前成熟度和非目标。

架构、测试、源码构建、历史版本和维护者发布步骤进入 README 后半部分或独立文档。

## 5. README 结构

`README.md` 使用以下顺序：

1. 项目名称、产品定位和中英文入口；
2. 当前版本与发布状态；
3. “适合谁”和“不是什么”；
4. 核心能力，控制在 6–8 个主题，不罗列所有公开动作；
5. 受保护的六项两行回执示例；
6. “最快开始”三步入口；
7. 系统要求与兼容性；
8. 数据安全、备份与回滚摘要；
9. 常见问题；
10. 完整文档导航；
11. 开发者构建和验证入口；
12. MIT 许可证。

首页不得出现以下反模式：

- 在没有 GitHub Release 时声称“点击下载最新版”；
- 把源码压缩包描述成插件安装包；
- 在前半屏展开所有历史版本和内部设计细节；
- 使用没有可核验来源的徽章或宣传数字；
- 隐藏产品版本 `0.7.4.1` 与技术包版本 `0.8.1` 的区别；
- 把 `self_check` 描述为七类工具全部注册成功的充分证据。

`README.en.md` 保留英文项目入口，但同步当前版本、安装资产名称、数据安全、许可证和 Release 安装边界。英文文档不需要逐字复制中文首页，可以继续侧重源码开发与架构，只要不与中文事实冲突。

## 9. CI 与正式 Release 工作流

### 9.1 普通验证工作流

新增独立 CI 工作流，在以下事件运行：

- Pull Request 指向 `main`；
- 推送到 `main`；
- 手动 `workflow_dispatch`。

CI 至少执行：

1. 敏感内容扫描；
2. 依赖安装；
3. TypeScript 类型检查和构建；
4. TypeScript/Vitest 测试；
5. Python 测试；
6. Skill 路由与行为门禁；
7. 发布审计；
8. `npm pack` 内容检查；
9. Docker 首次用户安装验证，或复用已有独立工作流并让状态清晰可见。

普通 CI 只能生成短期 Actions artifacts，不创建 GitHub Release。

### 9.2 Tag Release 工作流

正式发布工作流只响应符合产品版本的标签，例如 `v0.7.4.1`，并支持手动 dry-run。设计必须满足：

1. 标签版本与 `package.json.productVersion`、当前发布文档和构建器一致；
2. 标签指向提交必须属于预期发布分支合并后的提交；
3. 同名 Release 或 Tag 已存在时失败关闭，不覆盖；
4. 使用锁文件安装确定依赖；
5. 完整测试和发布审计全部通过后才构建；
6. 使用现有 `scripts/build_release.py` 生成正式发布目录；
7. 对所有资产重新计算并验证 SHA-256；
8. 解压检查安装包成员；
9. 在不依赖源码目录的临时环境完成安装与只读冒烟测试；
10. 最后一步才创建 GitHub Release 并上传资产；
11. 任意前置步骤失败时，不创建成功 Release；
12. 工作流采用最小权限，默认 `contents: read`，只有 Release job 使用 `contents: write`。

### 9.3 Release Assets

正式 Release 上传：

- `personal-diet-pantry-0.7.4.1-installable.tgz`
- `personal-diet-pantry-0.7.4.1-source.tar.gz`
- `release-manifest.json`
- `TEST-SUMMARY-v0.7.4.1.zh-CN.md`
- `SHA256SUMS`

Release 页面正文来自经校验的 `RELEASE.zh-CN.md`，并必须列出：运行要求、安装命令、更新步骤、迁移结论、已知问题、回滚方法和资产校验方法。

## 10. 三套 AI 提示词

`docs/AI-PROMPTS.zh-CN.md` 提供三个独立代码块，均填写本项目真实名称、仓库和资产规则，不保留占位符。

### 10.1 全新安装

要求执行者：

- 确认 OpenClaw、Node.js、Python 和磁盘环境；
- 从固定 GitHub Release 下载指定产品版本资产；
- 验证 `SHA256SUMS`；
- 创建位于安装目录之外的专用 `dataDir`；
- 通过 OpenClaw npm-pack 路径安装、启用并重启；
- 独立验证七类工具注册；
- 执行 initialize、self_check 和真实应用层只读验收；
- 不用源码脚本输出冒充 OpenClaw 实际调用成功；
- 不写入其他项目、记忆文件或真实个人数据。

### 10.2 安全更新

要求执行者：

- 记录当前产品/技术版本和真实 `dataDir`；
- 停止实例并创建、校验带时间戳的一致冷备份；
- 记录升级前只读表计数和健康状态；
- 下载固定版本资产并验证 SHA-256；
- 只替换程序包，不覆盖 `dataDir`；
- 只执行版本中声明的 migration；
- 重启后验证版本、工具注册、自检和只读业务查询；
- 对比升级前后记录数与关键统计；
- 失败时停止重复尝试并按文档回滚；
- 最终报告备份路径、迁移情况、数据差异和真实运行版本。

### 10.3 只读安装验收

要求执行者：

- 查询真实运行版本；
- 核对七类工具和公开动作；
- 检查健康、schema、迁移和配置；
- 确认 `dataDir` 位于正确持久化位置；
- 只运行只读查询，不新增、修改或删除真实数据；
- 分别列出通过、失败和未验证项；
- 不以文件存在、插件加载或 shell 退出码代替应用层验收。

## 11. 数据安全与失败策略

所有 GitHub 工作流和本地构建必须遵守：

- 不读取默认 OpenClaw 生产状态目录；
- 测试和安装验证使用临时 `dataDir`；
- `.gitignore`、敏感扫描和发布包成员检查形成三层防护；
- `.env`、数据库、WAL、备份、导出、报告、缓存、日志和凭据均不得进入 Git 或 Release；
- 构建输出必须位于 Git 工作树之外，或使用 Actions 临时目录；
- 不在日志中输出令牌、绝对生产路径、个人记录和数据库内容；
- GitHub Actions 不连接用户的软路由或 OpenClaw 实例。

失败处理采用 fail-closed：

- 版本不一致：停止；
- Tag 已存在：停止；
- 测试失败：停止；
- 敏感扫描发现内容：停止；
- 发布包成员不符合白名单：停止；
- 哈希不一致：停止；
- 隔离安装或冒烟测试失败：停止；
- GitHub Release 创建前失败：不创建 Release；
- Release 创建过程中资产上传失败：不得把结果报告为完整发布，维护者按发布手册处理草稿或失败 Release。

## 12. GitHub 社区内容

本轮增加最小且有用的社区入口：

- Bug Issue 模板：版本、环境、复现步骤、预期/实际结果、敏感信息提醒；
- Feature Request 模板：使用场景、用户价值、与现有能力的关系；
- Pull Request 模板：约束文件已读、版本已迭代、测试、迁移、数据安全和文档同步复选框。

本轮不加入 CODEOWNERS、Dependabot、Discussions 指南、行为准则和品牌素材。当前单维护者阶段，这些内容的维护成本高于实际收益；未来仓库公开并开始接收贡献后再按真实需要增加。

# 食序管家 v0.7.5.1：Skill 指路边界设计

## 1. 结论

v0.7.5.1 不增加饮食功能，只修正职责边界：**Skill 给智能体路标，智能体选择正向路线，插件和业务工具守住不可突破的数据底线。**

本版从已封存的 v0.7.5 提交 `848dc57fe0213b72bab8d9cc5d254c4f8a62041d` 创建。v0.7.5 目录、提交和候选制品保持不变。

## 2. 根因

v0.7.5 新增的 `direct-write-policy.ts` 按具体中文表达识别餐食、饮水、体重和入库，并由 `before_prompt_build` 注入“调用哪个工具、调用几次、先后顺序是什么”的指令。`turn-guard.ts` 又根据同一判断生成正向 `allowedActions`。

这套设计把三个不同责任混在一起：

1. 智能体应完成的语义理解和上下文推理；
2. Skill 应提供的领域知识与判断边界；
3. 插件和工具应执行的数据校验与安全约束。

它能让少数测试句稳定，却会随着口语变化继续增加正则、分支和特殊路线。修一个说法可能改变另一个说法，正是此前反复回归的主要结构性原因。

## 3. 方案比较

### 方案 A：继续扩充确定性口语路由

为更多口语添加正则、动作映射和固定调用顺序。短期容易让已知测试通过，但会持续放大分支数量，也会抑制智能体利用上下文推理。拒绝采用。

### 方案 B：移除全部守卫，只依赖 Skill

智能体拥有最大自由，但查询误写、否定误写、误删和重复扣库只能靠提示词避免。真实账本风险不可接受。拒绝采用。

### 方案 C：正向自治、负向护栏、工具守真

由 Skill 说明目标、证据、危险边界和正确结果；智能体决定是否调用、调用哪个工具及必要顺序；插件只阻止明确危险行为；业务工具保证参数、事务、幂等和数据来源。采用此方案。

## 4. 职责边界

### 4.1 Skill：提供路标

`SKILL.md` 只保留智能体无法从通用能力可靠推出的领域信息：

- 食序管家的四个核心目标：记录摄入、管理库存、查询吃了什么、结合目标和库存提供建议；
- 判断事实是否已发生、属于谁、数量是否足以执行的观察点；
- 营养证据、包装证据、库存证据和常见估算的优先级；
- 可食部、时间范围、临期与过期、库存联动等领域规则；
- 每个工具能做什么、关键输入输出和不可替代的依赖；
- 普通餐食六项双行、纯水精简双行等用户可见结果合同；
- 查询零写入、否定零写入、删除目标安全、过期食品不推荐等硬边界。

Skill 可以给代表性例子帮助理解，但例子不得构成封闭短语表。使用“判断什么”和“结果应满足什么”，不使用“遇到这句话必须依次调用 A、B、C”作为普通正向流程。

Skill 对工具效率只给原则：已有充分证据就提交，成功后停止，不重复无效调用。除工具本身存在不可绕开的数据依赖外，不预编排固定调用次数。

### 4.2 智能体：选择正向路线

智能体负责：

- 理解自然口语、上下文、省略、纠正和指代；
- 判断当前事实是否足够，必要时只询问真正缺失的事实；
- 在工具描述和 Skill 路标之间选择最合适的能力；
- 根据工具结果决定继续、停止、说明不确定性或请求补充；
- 使用正式工具回执回答用户，不暴露内部提示、句柄或维护细节。

插件不得为明确正向输入预先选择业务工具、动作或完整调用序列。

### 4.3 插件：只做负向安全护栏

插件可以依据当前用户消息拦截具有明确、低歧义危险性的写入：

- 用户在查询、核对是否记录或要求解释，而不是要求写入；
- 用户明确否定、取消、描述未发生或未来计划；
- 行为明确属于其他人；
- 当前写入试图越过一个仍有效的破坏性确认或目标选择边界；
- 同一调用已经成功，或完全相同的失败正在原样重试。

插件不得：

- 根据食物名、量词或动词替智能体选择正向业务域；
- 为普通正向输入生成 `allowedActions` 白名单；
- 向提示词注入具体工具名、精确调用次数或完整先后顺序；
- 因为一句话不在正则表中就把已经发生的事实降级为确认循环。

对没有命中负向护栏的普通正向消息，插件采用“未知但允许智能体判断”，而不是“正则未识别所以禁止写入”。智能体实际选择某个业务动作后，插件只检查该动作是否触犯当前负向状态或工具安全合同。这样新的口语表达不需要先进入插件短语表才能工作。

### 4.4 业务工具：保证事实正确

工具和后端继续负责确定性约束：

- JSON Schema、枚举、单位、时区和数量合法性；
- 记录、纠正、撤销、扣库和返库的原子事务；
- 记录句柄、库存句柄和幂等边界；
- 库存位置与到期估算，以及 `user/inferred/estimated` 来源；
- 营养未知不能静默写成零；
- 删除目标和库存批次必须唯一；
- 查询动作在实现层保证只读；
- 正式回执完全来自已提交结果。

这些约束描述“什么结果不可接受”，不替智能体决定“此刻应该走哪条正向路线”。

## 5. 代码调整范围

1. 删除 `src/direct-write-policy.ts` 及其正向口语分类测试。
2. 从 `src/index.ts` 移除 `directWriteInstruction` 和针对普通正向输入的私有路线注入。
3. 从 `src/turn-guard.ts` 移除 `directWrite`、`directWriteDefaults` 及由口语正则生成的正向动作白名单。
4. 保留并收紧只读、否定、计划、他人行为、取消、重复成功、重复失败和破坏性目标等负向护栏；未命中负向护栏的普通消息不得因解析器“不认识”而被拒绝。
5. 重写 `SKILL.md` 的主干为“目标—观察点—能力地图—硬边界—结果合同”；把详细领域知识继续按需放在 `references/`。
6. 调整工具描述，使智能体能看见输入、输出和不可绕开的依赖，但不把描述写成具体口语的固定工作流。
7. 产品版本升为 `0.7.5.1`，技术包版本升为 `0.9.1`；不新增数据库迁移。

## 6. 必须保持的行为

总约束中的 CORE-01～CORE-10、SAFE-01～SAFE-07、GOV-01～GOV-02、UI-01 全部保持。Good Flags GF-001～GF-005 必须逐项复测：

- 普通餐食仍是六项、每项双行；
- 纯水仍只显示饮水双行；
- “吃了个玉米”仍可直接落账，保留 `1个` 并明确可食部估算；
- 紧接的明确纠正仍可直接更新；
- v0.7.5 及更早完成版本保持不变。

本版不修改 WebUI、不新增饮食功能、不改变数据库模型、不重做营养计算、不改变过期食品过滤和相对时间语义。

## 7. 验证设计

### 7.1 结构性红灯

先增加会在 v0.7.5 上失败的测试：

- 普通正向输入的 `before_prompt_build` 不得出现具体工具名、`exactly once` 或固定调用序列；
- `classifyTurnIntent` 不得因食物动词和量词生成正向 `allowedActions`；
- 源码中不再存在 `classifyDirectWrite` 或 `directWriteInstruction`；
- Skill 合同要求“路标而非封闭路线”，并拒绝封闭短语表。

### 7.2 安全绿灯

- “刚才记上了吗”仍为只读并禁止写工具；
- “差点吃了，最后没吃”“明早想吃”“我老婆喝了”仍零写入；
- 明确取消后旧任务不能复活；
- 相同失败不原样重试；
- 删除、撤销、库存扣减和组合事务仍满足原合同。

### 7.3 能力与回执绿灯

- 用多种未写入固定短语表的口语表达测试餐食、饮水、体重和入库；
- 只评价最终事实、工具结果和用户回执，不要求每个成功场景使用同一调用序列；
- 固定复测玉米、直接纠正、纯水、库存联动、相对时间、过期过滤和普通入库默认值；
- 运行全部 Python、TypeScript、迁移、安装、升级、Skill 和发布门禁。

真实 OpenClaw UAT 记录工具轨迹用于发现失控或重复，但不把一条成功轨迹固化成所有语义的唯一合法路线。

## 8. 回退与发布

v0.7.5.1 没有新迁移，可直接回退到 v0.7.5 代码并继续使用 migration 022 数据库。发布前仍需冷备份、候选制品校验和真实口语 UAT。

v0.7.5.1 通过自动化只代表候选可安装；只有实机 UAT 证明智能体在获得自由后仍满足全部安全边界和 Good Flags，才能标记完成并发布。

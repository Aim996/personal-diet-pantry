# 食序管家 v0.7.3.6 稳定化设计

## 1. 目标

v0.7.3.6 以 v0.7.3.5 为不可变基线，修复小龙虾实机测试中已经能够由源码解释的
时间、查询范围、工具调用、过期库存和模糊份量问题，并为加工库存与偏好降级建立
确定性边界。技术包版本递增为 `0.7.9`，产品版本递增为 `0.7.3.6`。

本版不以提示词重写代替业务事实修复，也不把尚未定位到 Skill 的宿主流式问题宣称为
已解决。每个修复先形成可重复失败用例，再修改最小实现。

## 2. 继承约束

- 完整继承 `docs/PRODUCT-BEHAVIOR-INVARIANTS.zh-CN.md` 的全部受保护行为。
- 固定六项进度回执的顺序、两行结构、10 格进度条、真实百分比、本次增量和库存区块
  语义不得改变。
- v0.7.3.5 目录、版本号和制品名保持不变；v0.7.3.6 使用新目录、新版本号和新制品名。
- 用户测试报告中已经通过的功能继续进入回归测试范围，但在用户明确要求以前，不把整段
  “已经通过的功能”自动登记为新的长期受保护行为。
- 本版不新增 SQLite migration，继续复用 migration 001–021；新增响应字段必须保持向后兼容。

## 3. 已确认根因与待定位边界

| 测试现象 | 源码证据 | 设计结论 |
| --- | --- | --- |
| 普通查询出现 13 次以上工具调用 | 当前恢复规则明确写着“没有任意总调用次数限制” | 改为按意图设定预算，成功立即结束；完整分页使用单独可观察例外 |
| 过期清单漏掉昨天过期的水煮蛋 | `_report_expiring` 只保留 `today <= expiry_date <= cutoff` | 移除过去日期下界，返回所有仍有库存的已过期批次和未来窗口批次 |
| “一点花生”被估成 25g 直接写入 | `infer_portion` 已启用，但 Skill 没有把估算、确认和正式写入分离 | 所有非明确份量先进入非写入估算预览；确认后才提交，无法形成可信估算时再追问 |
| “昨晚”只返回晚餐并漏掉加餐 | 餐食查询只有 `occurred_on`，没有可信自然时间窗口或起止时间 | 建立通用自然时间窗口，不为“昨晚”写单一特例 |
| 时间固定少 13 小时 | 运行层已经保存时区感知时间，配置也为 `Asia/Shanghai` | 不能重写既有 UTC 模型；必须追踪调用参数并给公开结果增加可信本地时间投影 |
| 水煮蛋与原鸡蛋库存关系前后矛盾 | 当前回复规则允许模型在多个库存结果之间自行解释关系 | 只有事务 lineage 和 `inventory_effects` 能证明包含、扣减或转化关系 |
| 忌口查询失败后翻文件并暴露命令 | Skill 已有 `query_preferences`，但降级边界没有禁止外部文件/Exec 扩张 | 偏好读取只走正式工具；失败后停止并输出普通业务错误 |
| 中断续写、整段重复 | 当前报告没有包含宿主流式事件与消息 ID 证据 | 本版只增加可复现实机验收，不改数据库核心，不宣称已经修复宿主问题 |

## 4. 方案取舍

### 方案 A：只修改 Skill 文本

优点是改动小；缺点是过期过滤和查询接口缺失仍然存在，模型即使遵守指令也无法取得完整
事实。该方案不能解决数据正确性问题，不采用。

### 方案 B：重写时间和库存模型

优点是可以重新定义所有接口；缺点是会引入 migration、破坏已经通过的库存与撤销行为，
并扩大回滚风险。现有 UTC、IANA 时区和原子库存模型并未被证实错误，不采用。

### 方案 C：确定性运行层修复加 Skill 预算门禁

保留现有数据库模型，在运行层补足本地时间投影、可信查询窗口、完整过期集合与库存 lineage
投影；在 Skill 层增加可确认的份量估算、调用预算和降级终止规则；用行为轨迹与服务契约
同时验证。在此基础上增加声明式策略注册表和通用事实解析信封，使时间、份量、身份、偏好、
库存关系和报告范围共用同一套“证据—决策—确认—执行”模型。自然语言示例只用于测试，
不成为运行层的封闭关键词清单。该方案改动可分离、可回归且不需要 migration，为本版采用方案。

## 5. 泛化与扩展架构

### 5.1 固定不变量、可配置策略与扩展点

设计把规则分成三层，避免把安全边界和产品偏好混在一起：

| 层级 | 作用 | 示例 | 变更方式 |
| --- | --- | --- | --- |
| 固定不变量 | 防止错误写入、虚假成功和数据损坏 | 估算未经确认不写入；没有完整性证据不声称完整；相同失败不能原样重放 | 需要代码、约束和回归测试共同修改 |
| 可配置策略 | 同一能力在不同用户或环境下的参数 | 本地时段边界、份量证据阈值、路线调用预算、临期阈值 | 修改经过 Schema 校验的 YAML/用户配置，不改算法 |
| 受控扩展点 | 增加新场景或新类型 | 新时间 segment、新证据提供者、新库存 relation、新报告分类 | 注册新描述符并增加合同测试，不改既有类型语义 |

固定不变量不能被配置关闭。配置和扩展值必须经过 Schema、大小、数量、名称和引用完整性校验；
未知策略不得被静默忽略，应返回可修复的配置错误并保持零业务写入。

### 5.2 通用事实解析信封

时间、份量、商品身份、库存关系和偏好值都使用同一概念接口 `resolution`，而不是每个场景
自行发明一套“猜测或确认”规则：

```text
resolution = {
  subject,                  # 受注册表校验的事实类型 key
  state,                    # exact | bounded_estimate | multiple_candidates | unresolved
  normalized_value?,
  interval?,
  candidates?,
  evidence[],               # 有类型、来源、版本和适用范围
  policy_key,
  requires_confirmation,
  confirmation_options[],
  warnings[]
}
```

`subject`、`policy_key`、证据类型和 relation 名称使用受校验的注册值，不用 TypeScript 封闭
联合把所有未来扩展写死；核心 `state` 和确认语义保持小而稳定。一个新场景只有在能够映射为
上述状态、证据和确认政策时才可执行，否则保持 `unresolved`。

扩展能力分为三档，不能把“可扩展”误解为所有新概念都能只改一行配置：

1. **描述符扩展**：新别名、时段边界、已有算子可表达的日历周期、份量规则、报告分类或由
   已有能力组成的路线，只增加声明式条目和合同测试，不改通用算法。
2. **适配器扩展**：新设备、图片识别、外部数据源、新单位换算语义或新的工具能力，需要增加
   一个满足统一输入输出合同的代码适配器、Schema 和测试；计划器、确认模型和安全不变量不改。
3. **核心语义扩展**：只有新场景无法映射到现有 `state`、确认边界、权限或事务语义时，才进入
   单独设计与版本评审，必要时增加 migration；不得把它伪装成普通配置。

实现前先判定所属档位。描述符引用了不存在的算子或能力时按非法配置失败，不能退化为模型
自由推断；适配器缺失或不可用时保持 `unresolved`，不能绕过适配器直接写入。

### 5.3 声明式策略注册表

策略按职责拆分，运行算法读取接口而不是识别具体案例：

- `temporal-scopes`：日历锚点、滚动时长、命名 segment、跨日和本地化别名；
- `quantity-evidence`：包装、餐具、个人规则、食品规则和估算提供者的优先级与适用范围；
- `intent-routes`：一个意图允许的能力步骤、预算成本、继续条件和终止条件；
- `inventory-relations`：库存节点类型、关系方向、守恒字段和用户可见摘要；
- `report-taxonomy`：状态分类、阈值、排序、分页与完整性要求；
- `fact-authority`：目标、偏好、时区、忌口、过敏等事实的正式来源和允许的降级层级。

注册表是有版本的静态规则，不执行用户提供的代码。新增条目必须声明稳定 `policy_key`、输入
约束、输出形状和测试样例；删除或改变已有 key 的语义属于兼容性变更。

每个条目还必须引用允许列表中的 `operator` 或 `capability`。系统默认、部署配置和用户配置
按确定顺序合并，只有条目标记为可覆盖的字段才能被下层配置修改；固定不变量、受保护回执、
权限和正式事实来源不能被用户配置覆盖。合并结果保留来源、版本和命中规则，优先级相同且
结果冲突时返回配置错误，不采用“最后一个碰巧生效”。

### 5.4 通用执行计划

Skill 先根据完整意图和 `resolution` 生成私有执行计划，再调用工具。计划由能力步骤组成，
每一步声明：前置证据、预期新增证据、成本、成功终点、允许的错误转移和是否可能写入。

调用能否继续由“是否沿计划取得新证据”决定，而不是由工具名、固定轮数或模型感觉决定。
成功、正式终止结果、预算耗尽、重复失败指纹或无法满足下一步前置条件都会结束计划。完整分页、
批量预览等多步场景可以声明更多步骤，但不能借扩展路线绕过固定不变量。

### 5.5 组合式推理

一个用户请求可能同时包含操作、对象、时间、数量、来源、库存关系、查询范围和输出要求。
系统先分别解析这些维度，再组合 resolution；不得为“昨晚吃了点花生”“上周哪天喝水少”
之类组合句逐个增加专用分支。

组合遵循以下通用规则：

1. **独立解析**：每个维度保留自己的证据、状态和政策，不让时间置信度污染食品身份，也不
   让库存匹配成功自动证明份量准确。
2. **约束合并**：多个精确维度可以直接合并；区间取可证明的交集；候选组合超过配置上限时
   不做笛卡尔积，优先询问对结果影响最大的一个事实。影响顺序由路线声明的风险维度计算：
   是否决定操作有效性或权限、是否改变目标对象、候选结果差异是否越过库存/营养阈值、以及
   能否用一次回答消除最多候选；不靠模型临时觉得哪个词更重要。
3. **一次确认**：同一写入中的多个 `bounded_estimate` 合并成一个完整预览，让用户一次看到
   时间、份量、营养和库存影响；不得逐字段连续追问，也不得确认其中一个后静默接受其他估算。
4. **冲突显式化**：高权威证据冲突时返回 `multiple_candidates`；低权威证据不能覆盖高权威
   事实。没有可证明合并结果时保持 `unresolved`。
5. **读写分离**：查询时间表达解析成范围，通常不需要确认；历史写入中的模糊发生时间属于
   待写事实，必须作为估算进入预览。相同自然语言在读和写场景中复用解析器，但采用不同确认
   政策。
6. **能力组合**：跨领域请求由多个已有路线组成，计划器共享已取得证据并分别核算预算；
   不允许因为组合请求而重复查询相同事实或扩大任一子路线的写权限。
7. **事件状态先行**：计划器把事件是否已发生解析成独立事实。已发生事件才允许继续形成写入
   或估算预览；计划、假设、否定、未确定和仅讨论的事件保持零写入。修正、撤销和补录进入
   各自受限路线，不能被普通新增路线吞掉。这里依据组合语义与证据，不维护“可能、等会儿、
   差点”等封闭关键词名单。

新增自然语言说法时，优先把它解析成既有 descriptor；新增业务概念时注册新的 subject、证据
提供者或 relation。只有确实出现新的安全语义时才修改核心 state 或执行算法。

### 5.6 Progressive disclosure

主 `SKILL.md` 只保留解析信封、计划执行和安全不变量。时间、份量、库存 lineage、报告完整性
和失败恢复分别放入一层 `references/`；注册表保存在 `contracts/` 或 `rules/`。新增场景优先
增加策略条目和对应 reference，不持续扩大主 Skill，也不在多份文档重复同一规则。

## 6. 设计单元

### 6.1 可信时间投影

数据库继续存储 UTC 时间。公共餐食和饮水结果同时返回：

- 既有 `occurred_at` UTC 字段，保持兼容；
- `occurred_at_local`：使用已确认目标配置中的 IANA 时区转换；
- `timezone_name`：实际转换所用的时区名。

体重结果采用同样语义，但保持既有字段名：保留 `measured_at`，新增
`measured_at_local` 与 `timezone_name`。

当前发生、用户没有明确给时间的事件必须省略 `occurred_at`，由插件可信时钟创建。Agent
Session Status、宿主本地钟、浏览器显示时间和模型推算时间都不能填入该字段。用户明确给出
历史时间时才传 `occurred_at`，且必须包含时区。

时间回归覆盖上海晚上 22:37、凌晨 01:25、跨日、月末，以及一个有夏令时的 IANA 时区；
上海仍是产品默认时区，但时间工具不得写死 `+08:00`。

### 6.2 自然时间查询窗口

时间查询不能只支持“昨晚”。餐食、饮水、体重和需要按时间筛选的报告共享一个结构化窗口
解析器，由插件使用可信当前时间和用户配置时区生成 UTC 半开区间。自然语言只负责选择窗口
语义，不能让 Agent Session Status 或模型自行构造绝对时钟。

查询接口保留既有单日字段，并提供三种基础描述符；这些描述符表达时间关系，不枚举全部
自然语言说法：

1. **相对日历窗口**：`calendar_window` 使用已注册日历单位、整数 `offset` 和可选
   `segment`。核心提供日、周和月，但接口允许以后注册季度、财务周或个人周期；只要新周期
   可由已允许的锚点、周期长度和边界算子描述，就属于描述符扩展，否则必须提供时间适配器。
   例如“昨天”可解析为 `day/-1/full`，“上周”为 `week/-1/full`。
2. **滚动窗口**：`rolling_window` 使用正数 `value` 与已注册时长单位；核心提供小时和天，
   以后可以增加分钟或周。终点始终是插件可信当前时间。
3. **明确本地范围**：用户明确给出日期或时间段时，传本地起止值，由插件附加用户时区并
   转为 UTC；Agent 不拼接时区偏移。

`segment` 来自 `temporal-scopes` 注册表，而不是写死在 Python 条件分支中。每个 segment
声明当地起止、是否跨日、适用日历单位、语言别名和冲突优先级。发布配置可提供常见时段，
用户可以调整边界或增加“健身后”“夜宵时段”等个人窗口；算法只解析描述符。“昨晚”只是
某个本地别名解析到 `day/-1/<跨日 segment>` 的实例，不是独立动作。

既有单日、相对日历、滚动和明确范围四种输入模式互斥。当前或尚未结束的窗口以上界
`min(窗口结束, 可信当前时间)` 查询，避免返回未来记录。响应必须返回：

- 实际使用的 UTC 起止时间；
- 对应的本地起止时间和 `timezone_name`；
- 解析后的窗口类型与 segment；
- `complete`，说明该时间范围是否已经完整扫描。

返回范围内所有正式记录，不把自然时间词等同于餐次类型。例如“昨晚”“今天下午”“昨天”
都按时间范围返回晚餐、加餐、饮料和补剂；只有用户明确要求“只看晚餐”时才额外使用
`meal_type` 过滤。

### 6.3 工具调用预算

每个完整用户意图从 `intent-routes` 注册表取得一个私有执行计划和预算。预算值不散落在
Skill prose 中；表中数值是核心路线的发布默认值，不是未来场景的封闭上限：

| 意图 | 默认预算 | 合法调用形状 |
| --- | ---: | --- |
| 单一明确读取 | 1 | 一个对应领域查询 |
| 明确、事实完整的普通写入 | 1 | 一个原子写入 |
| 需要商品句柄的库存操作 | 2 | 一次定向搜索加一次写入 |
| 可定位的修正或撤销 | 2 | 一次目标读取加一次修正/撤销 |
| 份量估算首轮 | 最多 2 | 取得一份证据化估算并形成非写入预览 |
| 用户确认估算 | 1 | 使用原预览句柄提交一次，不重新估算 |
| 可修复结构化错误 | 按路线声明恢复成本 | 只修复工具明确点名且现有证据可证明的字段 |

成功和终止性业务结果立即结束。失败处理读取路线的 `retry_policy`：确定性错误默认零重试，
瞬态错误只有在错误返回了新的等待/状态证据且路线允许时才能继续。相同失败指纹永远不得
重试；不能用“换一个工具”重置指纹或预算。Diet 工具失败不得扩张到 Exec、绝对路径、SQL
或文件遍历。只有路线声明分页能力且响应返回可验证的未完成游标时才允许继续；每次必须推进
游标或覆盖新范围。

预算、步骤和转移条件是 Skill 行为合同和轨迹门禁，不伪装成数据库会话字段，也不保存用户
会话标识。新增批量、图片提取或跨领域场景时注册新路线，不修改已有路线来偷偷扩大权限。

### 6.4 完整库存状态报告

`diet_report expiring` 是通用库存状态报告的一个预设。报告通过 `report-taxonomy` 声明数据
集合、状态分类、时间范围、排序、分页和完整性，不把“过期/临期/可用”永远写死为全部分类。
当前预设查询所有状态仍可用且剩余数量大于零的带到期时间批次：

- 所有 `expiry_state=expired` 的批次，不设历史日期下界；
- `expiring_soon` 和 `usable` 只返回截至 `within_days` 的未来窗口；
- 按 `expires_at`、批次 ID 稳定排序；
- 返回 `complete`、各已注册状态计数、实际范围和分页证据。

分类器可以增加“缺少到期日、冷冻、已开封、需要盘点”等新状态，但同一批次的事实字段不
因此改变。报告只读，不自动把任何分类变成丢弃、消费或库存调整。Skill 只有在范围、筛选、
分页和来源都证明完整时才能使用“完整”或“只有这些”一类结论；否则必须说明缺口，并仅按
已声明路线继续获取缺失范围。

### 6.5 可确认的通用事实估算

份量是通用事实解析信封的第一个落地场景。行为由“是否存在用户确认的明确事实及可追溯
证据”决定，不由几个中文词的封闭名单决定：

| 输入状态 | 行为 |
| --- | --- |
| 用户给出精确数量、包装数量、已绑定规格或已确认个人规则 | 事实完整时直接写入 |
| 事件已明确发生，但数量是“一小把、普通碗、一点、一些、几口”等非明确表达 | 先形成估算预览，用户确认前零业务写入 |
| 现有证据连有界范围都无法形成，或不同解释会造成明显不同的库存/营养结果 | 展示缺失原因和可选范围，询问一个数量问题，零业务写入 |

估算器从 `quantity-evidence` 注册表选择适用提供者。发布时可包含个人规则、包装/餐具规格、
食品规则和有界家用份量；以后可以增加称重设备、图片测量或餐厅标注等提供者。每个提供者
声明适用对象、单位、置信边界、版本和冲突规则。不得为了给出数字而把模型常识伪装成已确认
事实，也不得因为加入新提供者而降低已有强证据的优先级。

个人规则、包装规格和已有算子能表达的家用份量属于描述符实例；称重设备、图片测量或新的
外部标注来源只有在对应适配器已经实现并注册后才能使用。注册表只负责选择和约束提供者，
不把尚不存在的数据采集或推理能力凭空变成可用能力。

估算预览至少包含：原始表达、建议记录量和单位、可用时的上下界、证据类型、明确的“估算”
标记、营养与库存影响预览，以及 `requires_confirmation:true`。低置信度不是自动写入许可；
它决定展示更宽的范围或要求用户选择，而不是静默采用一个看似精确的克数。

任何表示“事件已发生但某个事实不精确”的说法默认都走估算预览，而不是直接落库或机械
追问；中文量词只是测试样例。存在适用证据时可给出建议中心值和范围；没有可信证据时可展示
候选解释并问用户更接近哪一项，但不得捏造唯一精确值。相同解析信封以后可用于油量、可食
部分、混合菜比例或图片提取事实，但每种 subject 必须注册自己的证据提供者和确认政策。

用户纯确认时，只用原预览句柄提交一次；用户改成“其实 5g”时废弃旧预览，以新明确事实
重新评估。成功回执继续标记估算项，并使用最终提交返回的营养、进度和库存结果。

### 6.6 可扩展库存 lineage

原料批次、做饭事务和熟食批次保持不同事实。公共库存结果增加向后兼容的 provenance 投影，
但不把未来库存永远限制成 `raw|prepared` 两类：

- `inventory_kind`：受注册表校验的开放类型；核心可提供原料批次和熟食批次；
- `relations[]`：受注册表校验的有向关系，例如来源、拆分、合并、转化、包装或调整；
- 每条关系携带可证明的事务证据、数量守恒信息和公开摘要；
- 只有当前成功事务的 `inventory_effects` 可以表示原料已扣减或熟食已增加。

查询到“22 个鸡蛋”和“3 个水煮蛋”时，Agent 不得自行相加或相减，也不得推定是否包含。
存在正式 lineage 时陈述事务事实；不存在时分别陈述库存事实并询问用户，不做写入。未来的
分装、解冻、复热、混合、拆包或批次合并通过注册 relation 扩展，不靠模型自行发明关系。
v0.7.3.6 只投影现有事务已经能证明的关系，不为泛化而伪造历史 lineage，也不新增 migration。

### 6.7 正式事实来源与安全降级

忌口只是正式事实读取的一个场景。`fact-authority` 为目标、时区、过敏、忌口、稳定偏好、
个人份量和其他用户事实声明权威来源、可接受证据等级和允许的降级来源。稳定饮食偏好使用
正式偏好工具；一次成功结果立即回复。正式来源失败时，不能切换到 Exec、文件搜索、聊天
猜测或通用记忆来冒充同等权威事实。

若某事实类型注册了低权威的建议来源，可以明确标为“未确认线索”并请求确认，但不能用于
医疗/过敏安全判断或直接写入。公开回复只说明正式事实暂时不可用或需要确认，不包含工具名、
命令、路径、错误载荷或维护步骤。新增事实类型只需注册权威政策，不复制一套新的降级文字。

### 6.8 宿主流式问题

“停止生成后下一轮续写”和“同一回复整段重复”需要 OpenClaw 消息 ID、流式事件和最终消息
证据。v0.7.3.6 的实机清单会复测这些现象；在证据表明 Skill 产生两个业务回复以前，不修改
SQLite 事务和回复模板，也不把该问题列为已修复。

## 7. 数据流与错误边界

1. Skill 把原始表达分解成待解析 subject，并加载最小相关 reference。
2. 解析器从注册表选择适用证据与策略，生成一个或多个 `resolution`。
3. 计划器只为已满足前置条件的 resolution 生成有界能力步骤和预算。
4. TypeScript Schema 检查信封形状、互斥模式和扩展标识的基本界限；Python 对照当前注册表
   验证 policy key、证据引用、时间范围、单位和关系。
5. Python 业务核心使用可信时钟、目标时区、正式库存事务和 SQLite 事实执行计划步骤。
6. 服务响应返回 resolution、实际查询范围、完整性和 provenance，不删除既有字段。
7. Skill 仅从最终成功或正式终止结果生成一个业务回复，不进行计划外能力扩张。

输入错误返回结构化 `field/reason/expected`；是否允许修复及修复成本由当前路线声明。只有既有
证据足以形成新 resolution 时才继续；范围、目标或事实仍不清楚时返回候选或询问，不猜测。
所有失败保持零业务写入。

## 8. 泛化验收标准

除实机原句外，每项能力必须通过“等价新场景”测试。描述符扩展验证只增加合法条目即可
工作；适配器扩展验证只增加符合合同的适配器即可接入；核心语义扩展必须触发新的设计和版本
门禁。只修改关键词列表才能通过，或把需要适配器的能力假装成纯配置，均视为失败。

### 组合推理

- 一个同时包含相对时间、模糊份量和家庭库存对象的写入，只生成一个汇总预览；确认前所有
  业务表保持不变。
- 一个同时查询餐食、饮水和体重的时间范围，各领域复用同一已解析 scope，不分别用宿主时间
  重算。
- 两个低置信候选与一个高权威事实冲突时，高权威事实保留；两个同等级冲突候选要求用户选择。
- 测试加入设计文档未列出的组合句，系统通过 descriptor 组合处理，而不是增加专用 if 分支。
- “昨天本来想吃一些花生但没吃”由否定的事件状态阻止写入，也不生成无意义的份量确认；
  “刚吃了一点花生”则形成一次包含份量和库存影响的汇总预览。
- 测试加入未列出的计划、假设和不确定说法，均依据事件状态合同零写入，而不是靠新增关键词。

### 时间与查询

- “刚喝了蛋白粉”调用中不含模型构造的 `occurred_at`。
- 上海 22:37 和 01:25 均以正确当地日期显示，数据库仍保存对应 UTC。
- “昨晚吃了什么”使用配置的跨日 `night` 窗口，覆盖晚餐、加餐、饮料和补剂。
- “今天上午、昨天下午、昨天、上周、最近 3 小时”均由同一解析器生成可信本地范围，
  不依赖 Agent Session Status 时区。
- 用户调整命名时间段边界后，查询算法无需修改即可使用新边界。
- 测试注册一个设计文档未列出、但可由现有锚点/周期算子表达的时间单位或 segment，解析器
  无需增加条件分支即可生成窗口；引用未知算子的条目加载失败且不执行查询。

### 调用次数

- 单一读取不超过一次工具调用。
- 商品定向库存操作不超过两次。
- 相同错误不重复；不同错误是否继续由路线和 retry policy 决定，不调用 Exec 或遍历文件。
- 测试用既有 capability 注册一个三步且每步都有新证据的合法路线，以及一个两步中第二步不
  产生新证据的非法路线；前者按声明完成，后者立即停止。

### 数据正确性

- 昨天过期且仍有剩余的 3 个水煮蛋出现在完整过期清单中。
- 报告只有在 `complete:true` 时才能声称结果完整。
- “随手吃了点花生”先返回带范围和估算标记的非写入预览；确认前不写餐食、不扣库存。
- “吃了几口、一些、一小把、普通碗”使用同一证据化估算流程，不按关键词分叉成互相矛盾
  的写入规则。
- 无可信份量证据时展示可选范围并询问一个数量问题，不伪造唯一精确克数。
- 用户纯确认后只提交原估算一次；用户修改数量时旧预览不得提交。
- 测试增加一个由已有算子表达的新份量规则，以及既有 subject 下的新事实规则实例；只增加
  描述符与测试即可进入通用解析与确认流程。
- 测试接入一个新的外部证据适配器；只新增适配器、Schema 和合同测试，计划器与核心状态机
  无需修改。未安装该适配器时相同请求保持 `unresolved` 和零写入。
- 水煮蛋与原鸡蛋关系没有 lineage 时不自行扣减。
- 测试注册一个由现有守恒算子表达、且设计文档未列出的库存 relation；查询可以展示已证明
  关系，写入权限不因此扩大。新守恒语义必须走适配器或核心语义扩展。
- 忌口读取失败时不暴露内部命令或文件路径。
- 测试注册一个新的正式事实类型；其来源失败时应用同一权威与降级边界。
- 用户配置尝试覆盖固定不变量或正式事实来源时加载失败；同优先级冲突、未知 operator、悬空
  policy key 和循环引用都 fail closed，且业务表零写入。

### 兼容回归

- v0.7.3.5 的固定六项进度回执完全不变。
- 饮水新增/修改/撤销、体重 kg 默认、否定事件零写入、包装单位、蛋白粉勺换算、餐食修正
  与库存共同回滚、原子做饭和公开撤销继续通过既有门禁。
- migration 仍为 001–021；v0.7.3.5 数据目录可直接升级，失败时可停止实例后回退 v0.7.3.5。

## 9. 测试策略

每个设计单元独立执行 RED–GREEN–REFACTOR：

1. Python 服务契约：解析信封、注册表校验、时间投影、日历/滚动/明确窗口、配置化 segment、
   报告 taxonomy、正式来源和 lineage。
2. TypeScript Schema：互斥时间参数、扩展标识边界、信封结构、响应兼容和包内容。
3. Skill 静态合同：解析—计划—执行流程、估算预览、确认提交、预算、失败终止和权威降级。
4. 行为轨迹：对“昨晚、今天上午、昨天、最近几小时”和多种模糊份量原句验证调用次数、
   参数、预览、确认与停止条件。
5. 压力场景：分别使用陌生时间说法、跨日窗口、无明确份量、重复错误、成功后继续探测和
   文件降级诱因。
6. 全量 Python、TypeScript、构建与可安装包隔离测试。
7. 扩展性变形测试：新增一个未知于原实现的策略条目，验证只增加数据与测试即可生效；非法
   条目必须 fail closed。

宿主流式问题只记录实机证据和测试结论，不以缺少本地复现为由修改无关回复内容。

## 10. 非目标

- 不新增医疗建议、菜谱推荐或营养算法。
- 不重写 SQLite 时间或库存 schema。
- 不自动修正现有用户数据；如实机确认已有错误时间记录，另行设计显式预览与修正流程。
- 不自动上传、安装、启用或重启 OpenClaw。
- 不在没有证据时宣称修复 OpenClaw 宿主的中断或流式重复问题。
- 不允许用户配置执行代码、SQL、命令或任意表达式；扩展仅限受 Schema 约束的声明式数据。
- 不为了“泛化”预先实现没有真实场景和合同测试的插件系统；本版提供稳定描述符、注册表和
  一个跨类型解析接口，未来扩展按需要增加条目。

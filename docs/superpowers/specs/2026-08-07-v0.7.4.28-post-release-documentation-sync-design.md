# v0.7.4.28 发布后文档同步设计

## 1. 背景与目标

`v0.7.4.28` 已经作为公开正式版发布，但公开仓库中仍有部分治理文档保留着发布前或旧版本快照。此次工作只同步已经发生且可以从 GitHub Release、本地发布 manifest 和 Git 历史验证的事实，让普通 OpenClaw 用户、其他智能体和后续维护者能够快速判断当前正式版本、安装入口、发布证据和不可变边界。

这不是新的产品迭代，不改变 Skill、工具契约、安装包、数据库、迁移、运行时行为或用户交互，也不产生 `0.7.4.29`。

## 2. 不可变边界

以下对象保持原样：

- `E:\codx\食序管家\0.7.4.28` 封存目录及其全部文件和哈希；
- Git 标签 `v0.7.4.28` 及其指向的提交；
- 已发布 GitHub Release 的正文、五个资产、资产名称和资产内容；
- 产品版本 `0.7.4.28`、技术包版本 `0.8.28`；
- `package.json`、`openclaw.plugin.json`、`pyproject.toml`、`src/`、`diet_mcp/`、`skills/`、`migrations/` 和测试代码；
- 总约束中的 CORE、SAFE、GOV、UI 和 Good Flag 行为定义。

公开仓库 `main` 可以在标签之后增加治理文档提交。该提交描述已完成 Release 的状态，不重新定义或替换标签内的发布内容。

## 4. 事实来源与冲突处理

文档中的发布事实按以下优先级核对：

1. GitHub Release API 返回的 tag、可见性和资产列表；
2. 远端 annotated tag 解引用后的提交；
3. 封存目录中的 `release-manifest.json` 和 `SHA256SUMS`；
4. 构建输出与合并后的 Git 历史；
5. 既有说明文档。

若任意来源之间不一致，停止更新并报告差异，不选择对文档更好看的数值。不得重新打包、覆盖 Release、移动标签或修改封存目录来消除冲突。

## 5. 实施与发布方式

1. 在独立分支 `codex/v0.7.4.28-post-release-docs` 上修改。
2. 仅暂存本设计列出的文档文件，不使用无范围的全量暂存。
3. 运行文档版本/链接检查、发布事实比对、敏感信息扫描和 `git diff --check`。
4. 确认不存在运行时代码、包元数据、迁移、测试或 Release 资产变更。
5. 提交并推送分支，创建仅含文档的 PR。
6. PR 差异和验证结果符合本设计后合并到 `main`；不创建新 Tag 或新 Release。

GitHub Actions 如果再次因为同一账户账单锁在零步骤处失败，必须如实记录为外部阻塞；不得称为测试失败或 CI 通过。文档检查以本地可复核命令作为合并证据。

## 6. 验收标准

- 公开仓库存在一份可直接访问的 v0.7.4.28 发布实录；
- README、CONTEXT、工作流文档和发布手册不再把当前状态描述成旧版本或待发布；
- 中英文入口指向同一个固定 Release 和同一份发布实录；
- 文档中的提交、版本、资产名、测试统计和哈希与 GitHub/manifest/SHA256SUMS 一致；
- `E:\codx\食序管家\0.7.4.28` 的文件集合与哈希未改变；
- Git 差异只包含计划内文档；
- 敏感信息扫描为零；
- 不创建 `0.7.4.29`、新 Tag、新 Release，不部署 OpenClaw，不读取或修改用户业务数据。

## 7. 非目标

本轮不处理 GitHub 账单、OpenClaw 安装、WebUI、模型配置、Skill 行为、测试用例、依赖、版本号或产品路线图。后续发现任何运行时问题时，仍需按总约束先做多场景 UAT，并在新的产品版本目录中实施。

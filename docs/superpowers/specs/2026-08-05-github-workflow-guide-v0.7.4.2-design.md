# 食序管家 GitHub 工作流入口文档设计（v0.7.4.2）

## 1. 背景

食序管家已经具备 GitHub 仓库、分支、Draft PR、CI、Release 工作流、发布构建器、敏感信息扫描和本地候选归档，但相关规则分散在 README、发布手册、产品行为约束、安装文档和历史设计中。后续维护者或 AI 如果只读取其中一部分，容易混淆“提交代码”“合并 PR”“创建 Tag”“发布 Release”和“安装到 OpenClaw”，也可能遗漏版本迭代、数据保护或不可覆盖制品等硬约束。

本轮在项目根目录增加一个面向维护者和后续 AI 的单一入口文档 `GITHUB-WORKFLOW.zh-CN.md`。该文档负责导航、决策和执行边界，不替代各专项权威文档，也不改变食序管家的业务行为。

## 2. 版本与变更身份

- 基线产品版本：`0.7.4.1`
- 基线技术包版本：`0.8.1`
- 新产品版本：`0.7.4.2`
- 新技术包版本：`0.8.2`
- 实施分支：`codex/github-workflow-guide-v0.7.4.2`
- 数据库 migration：保持 `001–021`，本轮不新增、不修改
- 业务逻辑、七类工具、公开动作和受保护回复：全部保持不变

新增根目录文档属于项目约束定义的实质修改，因此不能继续沿用已经交付为候选的 `0.7.4.1 / 0.8.1` 身份。旧分支、旧候选目录和旧制品必须保持原样。

## 3. 目标

1. 为后续维护者和 AI 提供唯一的 GitHub 操作入口。
2. 让执行者在修改前先判断变更是否真正改善项目，而不是机械迭代。
3. 明确从本地修改到 GitHub Release 的各阶段边界、授权要求和停止条件。
4. 把版本迭代、测试、敏感信息保护、制品不可覆盖和生产数据隔离变成可执行清单。
5. 提供可以直接复制给后续 AI 的任务输入模板与交接记录模板。
6. 降低重复读取整套历史设计的成本，同时保留到权威文档的准确链接。

## 4. 非目标

- 不修改饮食、饮水、体重、库存、报告、时间范围、估算或回复模板逻辑。
- 不新增、删除或修改 migration。
- 不读取、迁移或写入生产 `dataDir`。
- 不改变仓库当前可见性。
- 不在本轮自动合并 PR、创建或推送 Tag、创建 GitHub Release、发布 npm 包或部署 OpenClaw。
- 不把根目录入口文档变成第二份完整发布手册，不复制容易漂移的大段命令实现。
- 不覆盖 `C:\path\to\personal-diet-pantry\0.7.4.1` 或任何同名历史制品。

## 5. 文档定位与单一事实来源

根目录 `GITHUB-WORKFLOW.zh-CN.md` 是“先读入口”，回答四个问题：

1. 现在处于什么版本、分支和发布阶段？
2. 本次请求是否值得修改，授权边界是什么？
3. 下一步应执行本地修改、推送、PR、合并、Tag、Release 还是部署中的哪一段？
4. 完成后如何验证、留痕和交接？

专项事实仍由以下文件负责：

| 事实 | 权威文件 |
|---|---|
| 不可回退产品行为和强制版本规则 | `docs/PRODUCT-BEHAVIOR-INVARIANTS.zh-CN.md` |
| 正式发布顺序、Tag 和 Release 门禁 | `docs/RELEASING.md` |
| 当前版本发布合同与说明 | `RELEASE.zh-CN.md`、`UPDATE-v0.7.4.2.zh-CN.md` |
| 安装、升级、备份和回滚 | `docs/INSTALLATION.zh-CN.md`、`docs/UPGRADING.md` |
| 可复制给 OpenClaw 的安装与验收提示词 | `docs/AI-PROMPTS.zh-CN.md` |
| 用户入口与项目定位 | `README.md`、`README.en.md` |

入口文档引用这些文件，不重新定义与它们冲突的规则。若入口文档与产品行为约束冲突，以产品行为约束为准；若发布命令细节冲突，以发布手册和当前工作流实现为准。发现冲突必须停止并修正文档，不能自行选择更方便的版本。

## 6. 根目录文档结构

`GITHUB-WORKFLOW.zh-CN.md` 使用以下固定结构：

1. **用途与适用对象**：说明这是维护者和 AI 的 GitHub 操作入口。
2. **60 秒快速入口**：给出固定读取顺序、仓库定位命令和最短决策路径。
3. **当前项目状态**：记录仓库、默认分支、当前开发基线、版本、发布状态；将易变化信息标为“必须现场核对”，避免把快照当永久事实。
4. **不可越过的边界**：产品约束、版本不可覆盖、敏感信息、生产数据和权限范围。
5. **修改价值门槛**：区分真实缺陷、体验改善、纯猜测和无收益重构；要求先写用户可观察结果、风险和最小验证。
6. **授权矩阵**：明确只读检查、本地编辑、分支/提交/推送、PR、合并、Tag、Release、仓库可见性和生产部署各自需要什么授权。
7. **标准工作流**：从预检、分支、最小实现、测试、版本同步、提交、推送、PR、合并到正式发布逐段说明。
8. **版本治理**：产品版本与技术包版本同时递增，历史候选不可变，文档变更也必须迭代。
9. **验证与发布制品**：列出应调用的项目脚本、CI、可复现构建、SHA-256 和五类 Release 资产。
10. **安全与隐私检查**：禁止提交数据库、日志、备份、凭据、绝对生产路径和真实个人记录。
11. **失败与停止条件**：测试失败、版本冲突、Tag/Release 已存在、敏感扫描命中、哈希不一致和授权不足时 fail-closed。
12. **GitHub 与 OpenClaw 部署边界**：说明推送成功不代表发布成功，发布成功也不代表生产安装成功。
13. **标准任务模板**：提供给用户或 AI 的最小任务输入格式。
14. **交接与留痕模板**：记录分支、提交、PR、版本、测试、制品、哈希、远端状态、部署状态和未验证项。
15. **常用命令索引**：只收录稳定的检查/提交/推送命令，复杂发布细节链接到专项手册。

## 7. 授权模型

入口文档必须把各阶段拆开，不能把“上传 GitHub”解释为无限授权。

| 操作 | 默认处理 |
|---|---|
| 查看本地 Git 状态、差异、历史和远端信息 | 可直接执行，只读 |
| 修改用户指定范围内的文件、运行测试和构建 | 用户提出“修改/生成/修复”后可执行 |
| 创建符合规范的新分支 | 属于正常实现步骤，可执行 |
| 提交、推送、创建或更新 PR | 用户明确要求上传、推送或发布到 GitHub 后执行 |
| 合并 PR | 必须取得明确授权 |
| 创建/推送 Tag、创建正式 Release、上传 Release 资产 | 必须取得明确发布授权，并通过全部门禁 |
| 改变仓库 Public/Private 状态、删除分支/Tag/Release | 必须取得针对目标的明确授权 |
| 安装或更新生产 OpenClaw、重启服务 | 必须取得明确上线授权并先备份 |
| 删除、重建或迁移真实业务数据 | 不从一般 GitHub 或部署授权中推断，需单独明确授权 |

## 8. 修改价值门槛

后续执行者在写文件前必须记录：

- 用户遇到的真实场景或维护目标；
- 当前行为及其证据；
- 期望的用户可观察结果；
- 不修改会造成的影响；
- 修改可能破坏的既有能力；
- 能证明改善的最小测试或检查。

若问题只有猜测、没有可观察收益，先做只读验证。若修复成本和回归风险明显高于收益，向用户说明并建议不改。不得以“代码更漂亮”“模型认为更合理”或“为了发新版”为唯一理由创建变更。

## 11. 失败处理

- 发现工作区存在非本轮用户改动：保留并隔离，无法安全隔离时停止。
- 发现版本、分支或权威文档冲突：停止修改，先解析真实基线。
- 发现相同版本目录、Tag 或 Release 已存在：停止，不覆盖、不重建。
- 发现测试或敏感扫描失败：不得打包、推送为完成状态或上线。
- 发现需新增 migration 或改变受保护行为：超出本轮授权，停止并向用户请求明确授权。
- 远端操作未获授权：只保留本地分支与提交，并明确报告未推送。

## 12. 完成定义

只有满足以下条件，本轮才能报告完成：

- 自动化测试、敏感扫描、发布审计和可复现构建通过。
- `0.7.4.1` 分支、候选目录和制品未被修改。
- 未经额外授权，不推送、不合并、不创建 Tag/Release、不安装生产 OpenClaw。

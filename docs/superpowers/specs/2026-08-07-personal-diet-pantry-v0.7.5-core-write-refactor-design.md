# 食序管家 v0.7.5 核心写入链路重构设计

## 1. 结论

v0.7.5 不再延续 v0.7.4.x 的逐句补丁方式。保留已经由 SQLite、事务和合同测试证明可靠的账本底座，重写位于用户口语和七类业务工具之间的写入决策层。

本版的产品目标只有四个：

1. 记录用户已经吃了、喝了什么；
2. 记录体重；
3. 管理家中库存；
4. 基于目标、库存和临期状态回答“该吃什么”。

任何不能直接改善上述四件事的能力都不在本次重构中扩张。

## 2. 为什么必须重构

v0.7.4.0 至 v0.7.4.28 在三天内连续增加了活动预览、确认句柄、上下文目标、回执接管、查询接管和大量正则特例。自动化测试可以证明各局部规则按预期执行，却不能阻止真实口语在这些层之间发生以下失配：

- “刚啃了根玉米”没有命中旧的“吃了”正则，因此从明确事实降级为模糊对话；
- 明确餐食同时允许 `record` 与 `preview_record`，模型可以自行选择确认流程；
- “刚称了下106.8”虽已属于体重事实，提示层仍允许模型追问单位和再次确认；
- Pantry Schema、TypeScript 归一化和 Python 服务共同强制到期日，Skill 文案又指导模型追问，导致一个错误要求在多层互相强化；
- 存放位置没有统一默认值引擎，模型把不同食品随意写成“厨房”；
- 测试大量覆盖内部句柄和分支，却没有把用户真实会说的整句作为发布阻断入口。

根因不是单个正则缺词，而是“模型决定业务路径、四层分别补规则”。继续打补丁会制造更多组合状态。

## 3. 历史能力取舍

| 历史能力 | v0.7.5 处理 | 原因 |
|---|---|---|
| SQLite 单一事实源、UTC 存储、用户时区投影 | 保留 | 已形成可信账本基础 |
| 营养 basis、未知值不写零、证据快照 | 保留 | 数据正确性的核心 |
| Meal/Pantry 原子联动、撤销返库、剩菜事务 | 保留 | 已有高价值事务能力 |
| 七个顶层工具与现有数据库迁移 | 保留兼容 | 避免重写稳定底层和破坏安装 |
| 固定六项双行餐食回执 | 保留并作为渲染合同 | 用户明确锁定 |
| 纯水精简双行回执 | 保留并作为渲染合同 | 用户明确锁定 |
| 明确餐食预览后再确认 | 从普通路径删除 | 与 CORE-01 冲突 |
| 普通入库必须提供生产/到期日 | 删除 | 用户没有提出，且阻断正常入库 |
| 模型自行决定存放位置和默认到期日 | 删除 | 结果不可重复、不可信 |
| 同一语义散落在 Skill、正则、Schema、服务四层 | 收口 | 防止相互抵消 |
| WebUI 新会话/分支异常 | 不处理 | UI-01 独立归因 |

## 4. 新架构

### 4.1 五段式单向流程

每个用户回合只经过一次以下流程：

1. **事实识别**：只判断查询、否定/计划/他人、明确已发生、真正模糊、定向纠正、复合写入；
2. **确定性路由**：产出唯一业务域、唯一 action 和必要默认值；
3. **参数归一化**：中文计数、自然单位、时间、位置、到期估算在代码边界统一；
4. **一次执行**：普通单域写入只允许一次正式调用，失败即停止；
5. **正式回执**：只输出提交结果自带的渲染文本，不由模型重新组织数值。

模型负责从口语提取食物名称和用户明确提供的事实，不再负责选择 `record` 还是 `preview_record`、猜库存位置或决定是否必须追问到期日。

### 4.2 明确事实与模糊事实

明确已发生且具有自然计数或精确物理量时直接写入。例如：

- “刚啃了根玉米” → Meal `record`；
- “吃了个苹果” → Meal `record`；
- “刚喝了500毫升水” → Water `record`；
- “刚称了下106.8” → Weight `record`，在明确称重语境下缺省单位为 kg；
- “刚买了俩苹果，放冰箱了” → Pantry `add`。

“一点、一些、几口、几粒、差不多一把”等开放份量仍先给出有用估算并只问一个问题，确认前零写入。存在自然计数但营养需要常见可食部估算，不属于模糊写入授权。

### 4.3 Pantry 默认值引擎

普通入库不再要求生产日期或到期日：

- `added_at` 缥缺时使用服务端当前用户时区时间；
- 用户明确给出位置时，规范化为冷藏、冷冻或常温并优先采用；
- 未给位置时，按食品名称、类别和形态的确定性规则推断；
- 用户明确给出到期时间时原样保存；
- 未给到期时间时，从入库日期、食品类别和存放方式估算；
- 自动值必须保存来源，查询和回执标注为“系统估算”，不得冒充包装事实。

需要新增迁移 022，为库存批次保存 `storage_location_source` 与 `expiry_source`。既有记录迁移后标记为 `legacy_unknown`，不反向假定为用户事实。

### 4.4 复合写入

v0.7.5 不在模型层假装实现跨工具原子事务。复合写入在没有统一后端事务前继续整句失败关闭，保持所有业务表不变，并用一句普通话说明当前没有写入。该边界满足 SAFE-06，但不是最终体验目标；后续只有在服务层拥有真正统一事务时才能放开。

## 5. 影响面与发布阻断

### 5.1 本轮允许改变

- CORE-01：明确摄入必须唯一走 `record`；
- CORE-02：玉米等自然计数保留并展示可食部估算；
- CORE-04：模糊量只保留一个澄清入口；
- CORE-07：入库日期、存放位置和到期估算默认值；
- SAFE-05：普通写入唯一 action、一次调用、失败停止；
- Skill 中与上述行为冲突的确认和必填日期说明；
- 产品版本 `0.7.5`、技术包版本 `0.9.0`、迁移 022 和对应文档。

### 5.2 必须保持不变

- CORE-03、CORE-05、CORE-06、CORE-08、CORE-09、CORE-10；
- SAFE-01 至 SAFE-07 的安全结果；
- GOV-01、GOV-02、UI-01；
- GF-001 至 GF-005。

### 5.3 主要回归风险

- 扩大摄入动词后误把计划、否定或他人行为写入；
- 收窄预览后把真正模糊份量直接写入；
- 默认 kg 误用于没有称重语境的裸数字；
- 位置或到期估算覆盖用户明确事实；
- 新库存来源字段影响导入、导出、备份和旧数据迁移；
- 正式回执接管影响纯水短回执或六项双行餐食回执。

每一项风险都必须先有失败测试，再实施代码。

## 6. 验收场景

至少用以下口语逐条验证：

1. “刚啃了根玉米”——直接写一次，回执包含 `1根` 或用户原自然单位、`可食部（玉米粒）约90克（估算）`，六项双行；
2. “吃了个玉米”——直接写一次并保留 `1个`；
3. 紧接“其实是80克”——一次原子更新，不确认，80克不标估算；
4. “吃了点花生”——只问一个有用问题，数据库零变化；
5. “刚称了下106.8”——按 kg 直接记录一次；
6. “刚喝了137毫升水”——直接记录，只显示饮水双行；
7. “刚买了俩苹果，放冰箱了”——不问日期，保存 2 个、冷藏和估算到期来源；
8. “买了袋大米”——不问日期，推断常温并保存估算来源；
9. “买了两袋速冻水饺”——推断冷冻；
10. “明早想吃个苹果”“差点吃了个苹果”“我老婆吃了个苹果”——全部零写入；
11. “刚称了106.5公斤，又喝了300毫升水”——整句不写入且清楚说明未提交；
12. 相对时间查询、库存联动、推荐过期过滤、删除和撤销——全部保持原合同。

## 7. 回退

代码回退基线为 v0.7.4.28，数据库回退必须同时恢复安装 v0.7.5 前制作并校验的冷备份。由于 v0.7.5 新增 migration 022，不允许只降级代码后继续打开已迁移数据库。

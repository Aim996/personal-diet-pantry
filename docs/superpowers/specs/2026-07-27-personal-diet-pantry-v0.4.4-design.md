# 食序管家 v0.4.4 保质期设计

## 目标

让每一笔新入库食品都带有具体的 `expires_at`，并在查询库存时直接显示“剩余几天”“剩余几小时”或“已过期”。保质期由模型结合食品状态和储存条件估算，系统负责校验、保存和确定性计算剩余时间。

本版本沿用现有 SQLite 数据库和 `pantry_batches.expires_at` 列，不清空、不重建现有库存、营养表、饮食记录或事务。

## 已确认的产品规则

1. 用户或包装标签给出明确日期时，以明确日期为准。
2. 没有明确日期时，模型必须估算一个具体时间，不把“冷藏约 3～5 天”这样的范围直接写入数据库。
3. 估算必须以本次入库时间为起点，并综合：
   - 食品类别；
   - 生鲜、熟食、剩菜、预包装等状态；
   - 冷藏、冷冻、常温等储存位置；
   - 是否开封、是否烹饪、是否解冻；
   - 包装说明和用户补充信息。
4. 所有新入库路径都遵守同一规则，包括普通商品、熟食和一顿饭产生的剩菜。
5. 旧库存中 `expires_at` 为空的数据允许通过专用补全流程更新，不影响数量和营养数据。
6. 保质期是管理提示，不代替对异味、外观、包装鼓胀等实际状态的判断。

## 数据模型

继续使用现有字段：

- `added_at`：入库时间；
- `expires_at`：具体到期时间；
- `storage_location`：储存位置；
- `status`：库存状态。

不增加新的 SQLite 列。来源属于调用语义：

- 用户或标签明确给出的日期直接写入；
- 模型估算的日期同样写入 `expires_at`，回复中用“估算”简短标注；
- 后续查询只展示到期时间和剩余时长，不额外消耗模型重新估算。

这样可以保留现有数据库兼容性，也避免每次读库存时再次推理。

## 写入契约

### 普通入库

`diet_pantry add` 和 `preview_add` 的公开 schema 继续允许省略 `expires_at`，避免 provider 在插件执行前产生不可解释的红色参数错误；但插件执行边界把它视为业务必填项。

如果缺少，返回一次安全且可恢复的诊断：

```json
{
  "code": "INVALID_INPUT",
  "message": "The request is invalid",
  "field": "expires_at",
  "reason": "required",
  "expected": "a concrete ISO 8601 expiry estimated from the item state and storage",
  "retryable": true
}
```

Skill 收到该提示后只允许根据当前食品信息补齐并重试一次，不追问用户，也不盲试数量或单位。

服务层仍严格要求 `expires_at`，且必须晚于 `added_at`。失败发生在预览、事务或库存写入之前，保证零写入。

### 剩菜和熟食

Meal item 中只要声明了 `leftover`，就必须带有具体 `leftover.expires_at`。公开 schema 允许请求进入插件边界，插件递归检查所有剩菜并返回精确字段路径，例如：

`items[0].leftover.expires_at`

只有完全补齐后才调用 Python。Python 服务和 prepared-food 层继续做严格校验，防止绕过插件。

### 明确日期与估算日期

Skill 的优先级固定为：

1. 用户明确日期；
2. 包装或营养标签日期；
3. 结合上下文的模型估算。

模型不能用固定的全局天数替代判断，也不能因为不确定就二次询问。信息有限时应给出合理、偏保守的具体估算，并在对用户的简短回复中标注“估算”。

## 旧库存补全

扩展现有 `preview_update_metadata` / `commit_update_metadata` 工作流，使其可以只更新 `expires_at`，也可以与重量元数据一起更新。

`diet_pantry query` 增加 `missing_expiry_only: true` 过滤，只返回仍在库且缺少到期时间的紧凑记录。补全流程为：

1. 分页读取缺少到期时间的在库批次；
2. 模型按每个批次的名称、入库时间、状态和储存位置估算具体日期；
3. 对目标批次使用现有预览—提交工作流更新 `expires_at`；
4. 不改库存数量、营养关联、饮食记录或其他元数据。

该流程只在升级补全、用户明确要求检查保质期，或相关库存记录被实际使用时触发；不在每次饮食记录后扫描完整库存。

## 查询与展示

库存查询继续返回保存的 `expires_at`，并由 Python 使用当前可信时间计算：

- `expiry_state: "usable"`：超过 24 小时；
- `expiry_state: "expiring_soon"`：大于 0 且不超过 24 小时；
- `expiry_state: "expired"`：已经到期；
- `expiry_state: "missing"`：旧数据尚未补全。

同时返回简短的 `expiry_display`：

- 24 小时及以上：`剩余5天`；
- 少于 24 小时：`剩余18小时`；
- 已到期：`已过期5小时` 或 `已过期2天`；
- 尚未补全：`待补保质期`。

天数按完整天向下取整，小时数向上取整且最少为 1 小时。计算只发生在读取结果层，不写回状态，也不改变库存扣减顺序。现有 FEFO 仍优先消耗更早到期批次。

默认紧凑查询只增加这两个短字段，不返回完整库存详情、内部编号或推理过程。

## 回复规则

入库成功时只需在原有简短回复中增加一项，例如：

`已入库：冷藏煎蛋2枚，预计可存至 7月30日（估算）🥚`

查询库存时可写：

`冷藏煎蛋 2枚｜剩余18小时 ⚠️`

饮食记录若只发生库存扣减，仍按既定格式显示扣减内容和剩余数量，不因为存在保质期就返回完整库存。

## 错误与安全

- 缺少或非法到期时间统一返回安全 `INVALID_INPUT`，不泄露路径、SQL、内部编号或堆栈。
- 自动修正最多一次；仍失败就停止，不连续调用工具。
- 明确的过期食品不会自动被标记为“已吃”或自动清空；是否丢弃仍由用户意图决定。
- `expires_at` 更新必须走现有预览—提交与版本检查，避免覆盖刚被其他操作修改的批次。

## 测试

1. 普通入库缺少 `expires_at` 时，provider schema 放行，插件返回一次字段级诊断且 Python/SQLite 零写入。
2. 模型补齐具体时间后，入库一次成功并保存原值。
3. `expires_at <= added_at` 被 Python 拒绝，所有正式表零写入。
4. 剩菜缺少到期时间时返回精确字段路径；补齐后原料扣减、饮食记录和剩菜入库仍保持原子性。
5. 旧库存可以只更新到期时间，数量、营养关联和其他元数据不变。
6. `missing_expiry_only` 只返回仍在库且缺少日期的批次，并支持分页。
7. 固定当前时间下，分别验证剩余 5 天、18 小时、已过期 5 小时和缺失日期的展示。
8. 紧凑库存查询不返回内部编号、完整营养表或推理说明。
9. 现有 FEFO 扣减顺序和全部回归测试继续通过。

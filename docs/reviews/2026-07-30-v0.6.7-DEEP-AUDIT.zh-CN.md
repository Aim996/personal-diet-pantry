## 1. 结论先行

v0.6.7 已经形成一套可继续发展的本地饮食与库存系统，餐食、饮水、体重、库存、事务、基础报告这些旧主线没有必要推倒重写。当前最值得做的不是继续横向堆新功能，而是先把 v0.6.7 新增层的可信度补齐。

新问题主要聚集在五个区域：

1. 隐私删除与事务历史之间没有真正闭环；
2. 维护、恢复和旧备份缺少可长期使用的恢复入口；
3. 菜谱、采购、成本和趋势的对外能力超过了当前实现深度；
4. Skill 文档存在互相冲突的路由规则；
5. 当前“24/24 Skill 评测”只是静态文档检查，不能证明真实口语行为正确。

因此，本次审计给出两个不同口径的判断：

- 作为本地饮食、饮水、体重和库存记录器：约 **7.5/10**；
- 按 v0.6.7 已公开承诺的完整稳定版来评价：约 **5.8/10**；
- 当前稳定发布可信度：约 **5.6/10**，完成本文 P1 项后预计可回到 **7.5–8.0/10**。

这里的低分不是说核心不可用，而是“新增层已经存在，但关键边界还没有被真实行为测试证明”。

## 2. 审计方法

本次不是单轮浏览，而是按以下五轮互相校验：

### 第一轮：版本承诺与文件矩阵

- 对照 v0.6.7 设计、实施计划、更新说明、72 动作清单和迁移 001–018；
- 确认本次相对基线涉及 90 个文件、约 10,686 行新增；
- 区分“已经承诺”“已经有表”“已经有 action”“真实用户可完成”四种不同成熟度。

### 第二轮：数据与状态机

- 检查事务 undo/redo、导入、删除、预览句柄、维护互斥锁和恢复；
- 检查不可逆操作是否真正绑定到用户看过的精确预览；
- 检查删除后数据是否还可能残留在历史快照和预览 JSON。

### 第三轮：领域正确性

- 检查菜谱库存筛选、过期食品、成本守恒、趋势分桶和时区；

### 第五轮：测试与发布门禁

### 证据强度说明

本文把证据分成三类，不把静态推理伪装成已经完成的现场复现：

- **运行通过/失败**：测试或命令已经在本轮实际执行并得到结果；

## 5. P1：应在继续扩功能前解决的问题

### F-01｜`all_business` 删除后仍可能在预览和事务历史中残留事实

**证据**

- `python/personal_diet_pantry/data_erasure.py:17-56`
- `python/personal_diet_pantry/data_erasure.py:97-126`
- `python/personal_diet_pantry/data_erasure.py:175-195`
- `python/personal_diet_pantry/data_erasure.py:455-507`
- `python/personal_diet_pantry/data_erasure.py:655-692`

`all_business` 的删除目标没有包含 `operation_previews`。其中 `request_json`、`result_json` 和 source text 可以继续保存已经删除的餐食、库存、体重或偏好事实。

事务清理又只根据当前业务行挂着的 `transaction_id` 收集目标。历史 create/update/undo 事务及其快照不一定仍被当前行引用，因此也可能保留下来。

**用户可见风险**

用户看到“全部业务数据已删除”，但数据库内仍可恢复部分原始事实。这不是展示问题，而是隐私承诺不准确。

**修复方向**

- 为删除范围建立统一的 provenance 索引，不只从当前行反查事务；
- `all_business` 必须处理 `operation_previews.request_json/result_json/source_text`；
- 明确哪些审计字段允许保留，保留字段只能是不可逆摘要；
- 删除后执行一次 residue verifier，并把结果写入删除凭证。

**验收**

用独特标记写入餐食、体重、库存、偏好、预览和多轮事务，删除后对全部业务表、预览 JSON、事务快照和 FTS/缓存全文搜索，标记出现次数必须为 0。

### F-02｜导入或部分删除后，撤销可以“显示成功但什么都没恢复”

**证据**

- `python/personal_diet_pantry/data_import.py:88-170`
- `python/personal_diet_pantry/transactions.py:206-250`
- `python/personal_diet_pantry/transactions.py:663-712`
- `python/personal_diet_pantry/data_erasure.py:597-629`

导入完成后会创建一个 committed `record_correction` 事务，但 before/after snapshot 都是 `[]`。普通 undo 候选查询仍会把它列为可撤销。

部分隐私删除还可能把仍被其他行引用的事务快照清成 `[]`。随后 undo 会把事务状态改成 reverted 并返回成功，却没有任何行被恢复。

**证据状态：确定代码路径，尚未取得独立服务回执。**

**用户可见风险**

“已撤销”成为假回执，导入的数据仍在，或被删的数据没有回来。

**修复方向**

- 导入和隐私删除使用明确的 non-undoable 事务类型；
- 或记录真实、完整且可应用的变更集合；
- undo 候选必须排除空快照和不可撤销事务；
- undo 返回成功前必须验证至少有一个状态变化，或返回明确的 `NOT_UNDOABLE`。

**验收**

- 导入后说“撤销”不能返回虚假成功；
- 删除后普通 undo 不能声称恢复隐私删除；
- 每次 undo 的 `affected_rows` 与实际数据库差异完全一致。

### F-03｜进程中断后，维护互斥状态可能永久阻断后续操作

**证据**

- `python/personal_diet_pantry/service.py:277-283`
- `python/personal_diet_pantry/maintenance_control.py:272-322`
- `control-migrations/001_maintenance_control.sql:1-43`

`reconcile_interrupted()` 已经实现，但服务启动只构造控制器，没有调用核对。若 restore/import/delete/migrate 执行到一半进程死亡，状态可能永久停留在 `running`。

控制库的唯一条件索引会继续把这个状态视为活跃 exclusive operation，后续维护全部被挡住。

另外，`maintenance_artifacts` 和 `maintenance_checks` 虽然建表，但生产路径基本没有写入，导致核对缺少可证明的证据。

**修复方向**

- 服务启动和首次维护请求前都执行一次幂等 reconciliation；
- 为每个阶段写入开始/完成 marker、artifact hash 和数据库一致性检查；
- 区分“可自动恢复”“需人工确认”“已失败但已解除互斥”；
- 对控制库本身损坏提供只读诊断和有限恢复入口。

**验收**

在 restore/import/delete 的每个阶段强制杀进程，重启后不能永久锁死，且不得把未验证操作标为成功。

### F-04｜不可逆删除的摘要校验发生在取得写锁之前

**证据**

- `python/personal_diet_pantry/data_erasure.py:153-175`

当前流程先重建并比较 preview digest，再执行 `BEGIN IMMEDIATE`。两者之间仍允许其他写入发生。

**风险**

用户确认的是 A 数据集合，真正删除时数据库已经变成 B。对于不可逆删除，这违背“确认精确预览”的设计目标。

**修复方向**

先取得写锁，再在同一事务内重建 plan、比较 digest、执行删除。任何差异都应使旧 handle 失效并要求重新预览。

### F-05｜旧备份存在，但公开工具几乎无法恢复它

**证据**

- `python/personal_diet_pantry/service.py:2476-2508`
- `python/personal_diet_pantry/service.py:2520-2570`
- `python/personal_diet_pantry/service.py:5031-5067`
- `src/schemas.ts:945-956`
- `config/behavior.yaml:9`

backup 完成后只返回一个短期 `backup_reference` handle；restore 只接受这个 handle。所有 workflow handle 又共用约 15 分钟的超时时间。

当前没有 `list_backups`、`query_backup` 或 `preview_restore` 公共动作。因此昨天、上周或更早的保留备份，正常用户几乎无法再次取得可恢复句柄。

**修复方向**

增加：

1. `list_backups`：只读列出安全元数据；
2. `preview_restore`：针对选定备份生成恢复摘要和独立 handle；
3. `restore`：只提交该精确 handle；
4. 备份完整性、版本兼容和可恢复性检查。

### F-06｜Asia/Shanghai 零点附近的成本/浪费趋势可能直接消失

**证据**

- `python/personal_diet_pantry/service.py:2329-2357`
- `python/personal_diet_pantry/trends.py:55-59`
- `python/personal_diet_pantry/trends.py:79-83`

服务先用用户本地日期计算 UTC 查询范围，但趋势模块再直接截取 UTC 时间字符串的 `YYYY-MM-DD` 或 `YYYY-MM` 作为桶键，输出标签却是本地日期。

例如上海时间 7 月 30 日 00:30 对应 UTC 7 月 29 日 16:30。该事件可能进入 `2026-07-29` 桶，而输出只创建 `2026-07-30` 标签，最终整条数据被漏掉。月初同样会跨月漏算。

**证据状态：最小运行反例已复现。** 向 UTC 范围写入 `2026-07-29T16:30:00Z` 的 123 CNY consume 和一次 discard，再请求上海本地 `2026-07-30`，实际返回：

```json
{
  "period": "2026-07-30",
  "waste_event_count": 0,
  "currencies": []
}
```

`cost_summary`/`waste_summary` 的范围总计不受该分桶错误影响，受影响的是按日/月返回的 trend buckets。

**修复方向**

所有事件先转换到 profile timezone，再生成本地日/月 bucket；不要混用 UTC 截断与本地标签。

**验收**

至少覆盖上海 00:00、00:30、23:59、月初、年初和 DST 时区边界。

### F-07｜菜谱建议会把已过期库存当作“临期优先使用”

**证据**

- `python/personal_diet_pantry/recipes.py:145-158`
- `python/personal_diet_pantry/recipes.py:197-223`

菜谱库存状态只过滤 active/opened/frozen/thawed 和 remaining > 0，没有排除 `expires_at <= now`。随后所有 `expires_at <= now + 3 天` 都被标为“优先使用临期食材”。

**风险**

已过期且状态仍 active 的食材可能提高菜谱分数。这是食品安全和建议可信度问题。

**修复方向**

- 默认排除已过期批次；
- 单独返回“已过期，请检查/丢弃”的库存风险；
- 冷冻、解冻、保质期暂停或重算必须有明确领域规则；
- 菜谱理由中不得把过期写成临期。

### F-09｜凭据脱敏不识别常见 camelCase 字段

### F-12｜Skill 中存在会直接造成错记、漏记或 INVALID_INPUT 的矛盾

#### 12.1 否定作用域过大

主 Skill 把 denial/non-occurrence 提升为整句零调用：

- `skills/personal-diet-pantry/SKILL.md:16-21`
- `skills/personal-diet-pantry/SKILL.md:88-91`
- `skills/personal-diet-pantry/SKILL.md:109`

反例：

- “早饭没吃，中午吃了一碗面”；
- “刚才不是 105，是 104.6”；
- “没喝水，是喝了豆浆”。

正确规则应是“否定只绑定被否定的事件”，纠错句还要进入 update/correction 流程。

#### 12.2 `per_unit` 与真实 schema 冲突

- `references/meal-and-nutrition.md:7` 使用 `per_unit`；
- `SKILL.md:162-167` 与 `src/schemas.ts:276-320` 只接受 `per_serving`。

模型按 reference 构造请求会直接得到 `INVALID_INPUT`。

#### 12.3 做饭路由要求有剩菜，导致“全吃完”走错路径

- `SKILL.md:112` 只在“做饭、吃了且保存剩菜”时使用 `record_cooking`。

“煎了 6 个鸡蛋，全吃了”也应走 cooking，完整扣除原料，只是 leftover 为空。

#### 12.4 reference 承诺 schema 无法表达的做饭情况

- `references/cooking-and-leftovers.md:3,13`
- `src/schemas.ts:387-397`
- `python/personal_diet_pantry/meals.py:995-1004`

reference 说只做饭、全部留存、制作损耗都可记录；真实 schema 要求 consumed_quantity > 0，且没有 preparation loss 字段。

#### 12.5 “买了”既被要求入库，又被禁止视作入库

- `SKILL.md:114`
- `SKILL.md:320,338`
- `references/pantry-and-expiry.md:7,21-22`

“买了两盒鸡蛋，还在车里”不应创建家中库存。必须把 purchase、possession、stocked 三个状态分开。

#### 12.6 外食地点与库存来源被混为一件事

- `SKILL.md:315`
- `references/meal-and-nutrition.md:3-5`

“在公司吃了从家里带的便当”同时具有外食地点和家庭库存来源。需要把 consumption location 与 inventory provenance 分离。

#### 12.7 多意图一句话可能静默丢事件

“午饭吃了面，喝 500ml 水，体重 104.6，又买了鸡蛋”跨越多个领域。现规则偏向一个 decisive action、最多两个 reference，没有定义事件拆分、顺序、部分失败和多回执。

当前工具也没有跨域原子事务。因此必须诚实地逐事件执行并返回逐项结果，不能假装整句原子成功。

## 6. P2：功能已出现，但还没有达到公开描述的完整度

### F-13｜recipe → shopping 并未形成完整闭环

设计目标包括：

- 内置、保存、复用的菜谱；
- 营养目标、偏好、时间、份数、剩菜和临期的联合评分；
- `planned → purchased → stocked`；
- shopping item 与 pantry batch 的可追踪链接。

当前实现主要是：

- 按库存覆盖率和临期程度给菜谱打分；
- meal_type 被接收但没有真正参与选择；
- shopping list 为 active/cancelled/completed；
- shopping item 为 pending/purchased/cancelled；
- 没有公开的 item-level purchased/stocked action；
- 没有 `shopping_item_links`；
- 没有完整内置菜谱目录，也没有从真实做饭记录沉淀为可复用菜谱草稿。

这部分应在 v0.6.8 补完，不宜继续把它描述成完整闭环。

### F-14｜菜谱解释还不是真正的个人化决策

当前“为什么推荐”主要能解释库存覆盖和临期。尚未稳定纳入：

- 用户营养目标和当日缺口；
- 忌口、偏好、过敏和不喜欢；
- 可用烹饪时间；
- 份数与计划剩菜；
- 冷冻/解冻准备时间；
- 最近重复频率和多样性。

建议把 scoring 拆成可观察的分项分数，并返回事实依据，而不是只输出一句自然语言理由。

### F-15｜0.6.6/0.6.7 报告指标只实现了基础部分

现有成本和浪费底层能返回 purchase/consume/waste/adjustment 与时间桶，但路线图还包括：

- 临期处理率；
- 采购频率；
- 使用波动；
- 库存周转；
- 缺货频率；
- 营养覆盖率及趋势；
- 可重建的 metric snapshots；
- 更细的 waste classification。

建议先定义每项指标的单位、窗口、分母、排除项和缺数据状态，再实现 UI/回复。

### F-16｜“单一动作契约源”目前只统一了动作元数据

`contracts/tools.yaml` 已经统一 action、mode、confirmation、retry、handler 和测试映射，这是进步。但输入字段、默认值、完整约束、公开输出白名单和 Skill reference 仍然分散维护。

`per_unit`/`per_serving` 漂移正是这种部分单一源造成的。

下一版 contract IR 应能生成或至少校验：

- TypeScript input schema；
- Python dispatcher/action 集；
- public response allowlist；
- Skill action/reference 表；
- mutation/confirmation/retry 分类；
- 文档参数表与示例。

### F-17｜`service.py` 仍是超大编排器，领域边界没有真正下沉

`service.py` 已超过 5,600 行。v0.6.7 虽然增加 recipes、shopping、costs、trends 等文件，但 application/domain/adapter 分层仍未形成。

这不是要求为了“文件短”而拆文件，而是要把变化原因隔离：

- intake normalization；
- portion resolution；
- inventory planning；
- transaction policy；
- maintenance orchestration；
- privacy deletion graph；
- report query model。

每个深模块应提供少量稳定接口，并隐藏 SQLite 和句柄细节。

### F-18｜Skill 的动作发现和 reference 覆盖不足

72 个 action 中约有 33 个 action 名没有出现在主 Skill 或任何 reference，包括部分 pantry preview/commit、购物查询/取消、维护状态/历史和数据库验证动作。

主 Skill 又要求运行时只加载最多两个 reference，模型很容易不知道真实 action 是否存在。

应从 `contracts/tools.yaml` 自动生成并随 Skill 打包一个按领域分组的轻量动作表。

### F-19｜主 Skill 与 reference 的进度/体重回执格式互相竞争

主 Skill 要求固定六项、每项两行；water reference 又要求整体压缩为两行。体重示例也有两套格式。

格式规范只能有一个权威来源。建议由后端返回稳定 view model，Skill 只决定简洁或详细模式。

### F-20｜裸数字记体重应保留，但要变成显式的个人偏好

用户已经明确要求“105”这种裸数字可以直接记录体重，因此不能简单删掉。

更稳妥的设计是：

- 默认个人配置允许裸数字体重；
- 用合理区间、近期对话和当前领域辅助判断；
- 在共享群组或无身份上下文渠道可单独关闭；
- “刚才不是 105，是 104.6”必须识别为纠错，而不是新增；
- 该行为必须进入真实 Telegram 多轮测试。

### F-21｜安装包端到端测试缺少阶段超时和离线确定性

`tests/integration/test_installable_e2e.py:16-30` 的外部进程没有 timeout。测试还会执行 npm install，可能受网络、peer dependency 或 npm 状态影响并无限等待。

建议：

- 每个子进程有明确 timeout；
- 只安装本地产物并禁用不必要的在线解析；
- 超时时输出当前阶段和 stderr；
- 在 CI 中区分“包内容测试”“离线安装测试”“真实 OpenClaw smoke”。

## 7. 最值得补充的真实行为测试

以下测试应执行真实 Skill/模型轨迹并检查数据库，而不是只检查 YAML：

1. `早饭没吃，中午吃了一碗牛肉面`
   只记录午餐，不能整句零调用。
2. 先记 `105`，再说 `刚才不是105，是104.6`
   必须更新上一条，不得新增第二条。
3. `买了两盒鸡蛋，还在后备箱`
   不得创建家中库存。
4. `煎了6个鸡蛋，全吃了`
   使用 cooking，扣 6 个鸡蛋，无 leftover。
5. `煮了一锅粥，没吃，全部冷藏`
   要么由新 schema 正确支持，要么明确说明当前不支持，不能构造无效请求。
6. `70.4kg，刚喝了500ml水`
   两个已发生事件都落库，并给两个真实结果。
7. 新 Telegram 会话只有 `确认`，但没有 live handle
   零工具调用，不得确认上一会话的过期操作。
8. `在公司吃了从家里带的便当`
   地点是公司，库存来源是家里；按明确策略扣减。
9. `把购物清单里的牛奶标记为已购买`
   使用正式 item action；未实现前不能用 pantry add/cancel 冒充。
10. 上海时间 00:30 产生消费成本
    日报和月报都必须落入本地当天/当月。
11. 已过期但 status=active 的牛奶
    不得出现在推荐菜谱的可用食材中。
12. all_business 删除带唯一标记的数据
    预览 JSON、事务快照、业务表、缓存全文检索结果均不得残留。
13. 导入后立刻“撤销”
    不得返回空成功。
14. restore/import 执行中强制杀进程
    重启后 maintenance 不得永久锁死。
15. 创建一天前的备份并重启
    用户仍能列出、预览、验证并恢复。

## 8. 推荐迭代路线

### v0.6.7.1：可信度修复版

目标：不增加大功能，只修复会污染数据、虚假成功、隐私残留、无法恢复和食品安全的问题。

范围：

1. 删除 residue graph、事务清理和锁内 digest；
2. 导入/删除后的 non-undoable 语义；
3. maintenance 启动核对和中断恢复；
4. `list_backups + preview_restore + restore`；
5. 趋势按 profile timezone 分桶；
6. 菜谱排除过期批次；
7. self_check 覆盖 016–018；
8. camelCase 凭据 scrub 与真实 source archive 扫描。

发布门禁：

- 本文 F-01 至 F-10 的运行级反例全部通过；
- 删除后 residue verifier 为 0；
- 不再出现 affected_rows=0 的成功 undo；
- 所有维护中断点均可恢复或安全解除互斥；
- 上海跨日/月测试全绿。

### v0.6.7.2：Skill 真实行为版

目标：让“口语好用”有可验证证据。

范围：

1. 统一主 Skill、reference 与 schema；
2. `per_serving`、购买/入库、外食/来源、批次策略统一；
3. 分句级否定与否定式纠错；
4. cooking 支持范围与 schema 对齐；
5. 多意图事件拆分、顺序、部分失败和回执；
6. 保留裸数字体重，但变为显式个人偏好；
7. 当前评测改为 lint，新增真实 tool trace + DB state + reply evaluator；
8. 从正式 contract 生成动作路由 reference。

发布门禁：

- 至少 50 个真实行为案例；
- 安全类案例 100%；
- 重复写入、漏事件、错误 action、无效 payload 均为 0；
- WebUI 与 Telegram 各跑一组连续和新会话案例。

### v0.6.8：补完菜谱、采购、成本与浪费闭环

目标：把已经公开但只完成骨架的能力补成真实产品闭环。

范围：

1. 菜谱份数、营养、替代项、来源、版本和时间；
2. 内置菜谱、用户保存菜谱、从做饭记录生成草稿；
3. pantry/expiry/goal/preferences/time/leftover 联合评分；
4. `planned → purchased → stocked/cancelled` item-level 状态机；
5. shopping item 与 pantry batch 的链接；
6. 缺失的周转、缺货、使用波动、临期处理率和营养覆盖指标；
7. 可重建的 metric snapshots 与浪费分类；
8. 推荐理由返回可验证事实，不编造。

### v0.6.9：架构与长期智能化

目标：降低继续迭代时的同步成本和回归风险。

范围：

1. contract v2 作为 schema、public output、docs 和 Skill action 表的真正 IR；
2. 把 service 拆成 application/domain/adapter 深模块；
3. 确定性 public view model，包括 `measured_at_local + timezone`；
4. 版本化 import adapter，允许升级旧导出；
5. 数据质量/健康报告：schema、隐私残留、撤销能力、营养完整性、价格覆盖、备份可恢复性；
6. 长周期报告性能、故障注入、并发和恢复测试。

## 9. 不建议现在做的事

1. 不建议立刻增加更多顶层工具；
2. 不建议先做复杂 AI 菜谱生成而不修过期库存过滤；
3. 不建议继续用静态 24/24 作为 Skill 已稳定的证明；
4. 不建议把所有新能力一次性塞进 v0.6.8 而跳过 v0.6.7.1/2 门禁；
5. 不建议重写餐食、饮水、体重和库存旧核心；
6. 不建议让 Skill 文档继续手工复制 schema 枚举和字段名。

## 10. 最终判断

v0.6.7 的正确定位应当是：

> 核心饮食与库存记录已经成熟，新增的菜谱采购、成本趋势、隐私删除和维护恢复进入了“可运行但未完全可信”的阶段。

最优策略不是推倒重做，也不是继续堆功能，而是：

> **连续规划，分段验证：先做 v0.6.7.1 数据可信度，再做 v0.6.7.2 Skill 真实行为，随后由 v0.6.8 补齐业务闭环，最后在 v0.6.9 深化架构。**

完成前两步后，v0.6.7 的基础足够支撑后续长期迭代；如果跳过它们直接增加智能化，旧问题会被更复杂的推理放大，而不是被解决。
